# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**How to use it.** This is an index of rules, not the reasoning behind them. Nearly every rule here is explained at length in a comment at the code it governs — the source is 30–47% comments by line, and those comments are the authority. Each entry below names the function or file to read. When you change something, update the comment at the code first; update this file only when the *rule* changes.

## What this repo is

A personal static site (`melbostads.com`) whose only real application is **`myffl.html`** — a fantasy football dashboard aggregating ~18 leagues across MyFantasyLeague (MFL), ESPN, and Sleeper. Every other page is a stub, an iframe wrapper around a Google Sheet, or a redirect. `myffl_v1.html` is the retired predecessor, kept for reference.

There is **no build step, no test framework, no linter, and no dependencies**. `package.json` exists only to set `"type": "module"` for the `.mjs`/`.js` files under `scripts/` and `api/`. Do not add `npm test`/`npm run build` scripts expecting them to be wired to anything. Tests are plain `node scripts/test-*.mjs` files run by `syntax-check.yml`; every one of them is expected to be listed there.

## Two deployment targets, one repository

This is the single most important thing to understand before changing anything:

| Path | Deploys to | Serving |
| --- | --- | --- |
| `*.html`, `data/`, images | GitHub Pages | `melbostads.com` (see `CNAME`) |
| `api/*.js` | Vercel | `shamrock84-github-io.vercel.app` |

`myffl.html` is served from Pages but calls Vercel by **absolute URL** (constants near the top of its script block). Every request is therefore cross-origin; `api/lib/cors.mjs` carries the shared allowlist and preflight handling that every endpoint imports.

Consequences that bite:

- **Secrets exist in two independent places.** GitHub Actions secrets power the scheduled sync; Vercel project environment variables power the API functions. They are not shared. Adding a credential means setting it in both, or deciding which half needs it. (The Upstash Redis credentials for `api/plans.js` are Vercel-only — the sync never touches plans.)
- **`vercel.json`'s `ignoreCommand` skips the Vercel build** unless the commit touched `api/`, `scripts/lib/providers.mjs`, or `config/leagues.json`. If you make `api/` import a *new* shared module (say `scripts/lib/fantasypros.mjs`, which today only the sync uses), you **must** add that path to `ignoreCommand` or Vercel will silently skip deploys that need to ship. This is why `attachInjuryDetail` lives in `fetch-rosters.mjs` rather than `providers.mjs` — it needs `normalizePlayerName` from `fantasypros.mjs`, which is not on that list.

## Two data paths, deliberately separate

**Slow path — snapshot, committed to the repo.** `sync-fantasy-rosters.yml` runs every 4 hours (and on demand), executes `scripts/fetch-rosters.mjs`, and commits the result to `data/rosters.json`. This carries rosters, standings, scoring, lineups, the FantasyPros ranking pools and each league's free agents. `myffl.html` fetches that file directly with a cache-buster — the whole file, on every page load, which is the budget any new field is spending.

**Fast path — live, never written down.** `api/live-scoring.js` is polled roughly every 30s while the Scoring tab is open. It only answers requests; it writes nothing. It keeps a module-level cache (MFL cookie ~20 min, franchise names ~1 hour) that survives warm invocations and resets on cold start.

Both paths import the same fetch logic from **`scripts/lib/providers.mjs`**. `fetch-rosters.mjs` is orchestration only — provider quirks belong in `providers.mjs`.

`api/trigger-sync.js` bridges the two: the page's "Last synced" link dispatches the sync workflow via a repo-scoped PAT, behind a 2-minute cooldown so the button can't be used to hammer MFL/ESPN.

## `config/leagues.json` is the control plane

Adding, removing, or reclassifying a league is a config edit, never a code edit — and usually not even a repo edit: the **Admin tab** in `myffl.html`, visible once logged in, edits this file through `api/save-leagues.js` and commits it. Prefer pointing the user at that tab over hand-editing on their behalf.

That endpoint is the only write path in the project that **bypasses pull requests entirely and commits straight to `main`**, so the syntax-check workflow never sees it. Its server-side validation is therefore the only guardrail, and `scripts/test-save-leagues.mjs` is what keeps that validation honest — extend the tests alongside any change to the schema.

The file's own `_readme` array is the authoritative schema — **read it before touching anything league-shaped, and update it when you change the schema.** Array order is display order across every tab.

Rules that live here rather than in the schema:

- `mergeLeague` passes through fields it doesn't recognise. Without it, any field added to the config later would be silently erased the first time someone pressed Save.
- `serialize` keeps one league per line, so an Admin-tab commit is reviewable as a one-line diff. A nested-object value (`historyLeagueIds`) gets the same spaced-out treatment, so a readable hand-edit survives a save byte-for-byte.
- `RETIRED_KEYS` in `api/save-leagues.js` is the mechanism for removing a config field permanently — the unknown-key passthrough would otherwise preserve it forever. It currently strips `format` and `commishEmail`.
- **`type: 'bestball'` was renamed to `'draftonly'`** and nothing in the UI or config says "best ball" as a type any more. Best Ball is a scoring system several salary-cap leagues use, and it lives in `tags`. This rename has no code left to point at, which is why it is recorded here.
- `type` carries one behaviour beyond display: `salarycap` renders the Salary/Yrs columns and the cap summary, and makes the sync fetch the cap and salary adjustments at all.
- Three providers are supported: `mfl` (the default when `provider` is omitted), `espn`, and `sleeper`. Provider selection is a three-way ternary repeated at each stage of `fetch-rosters.mjs` (roster, standings, scoring, lineup), so adding a fourth means updating `providers.mjs` *and* each of those call sites.

## Invariants worth preserving

Grouped by subsystem. Each is the rule; the named function carries the reasoning.

### Sync, seasons and rate limits

- **The sync degrades, it never fails.** `fetch-rosters.mjs` wraps every league in try/catch and falls back to the previous `data/rosters.json` entry (`previousById`), recording an `error` field the page renders. One dead league must never blank out the other seventeen. FantasyPros rankings are layered on last and are likewise never allowed to fail the run.
- **Every MFL entry point paces its requests, each at its own interval.** `setMflRequestInterval`/`paceMflRequest` in `providers.mjs`, pinned by `test-mfl-request-pacing.mjs`. The 429s are a *burst* problem — the sync had no send-rate floor at all until this existed, and 24 of 29 committed snapshots carried at least one 429, clustered at the tail of each pass. `mflGet`'s retry is only the reactive half; the gate is the half that decides whether MFL refuses in the first place. Three rules here:
  - **It is off by default and opt-in per entry point, and the interval is per entry point too** — that difference is the design, not an inconsistency. `MFL_REQUEST_INTERVAL_MS` (300ms) in `fetch-rosters.mjs`, shared by both backfill scripts, because an unattended cron can spend wall-clock freely. `LIVE_SCORING_MFL_INTERVAL_MS` (75ms) in `api/live-scoring.js`, because that one fans out across every league at once on a ~30s poll and pays the interval in latency on a user-facing tab — and because no `maxDuration` is set in `vercel.json`, so a cold start (which pays it twice, names then scoring) has to stay a rounding error against the default ceiling. **Don't collapse the two numbers, and don't make the gate global.**
  - **It serializes request *starts* on a promise chain, not with a "has enough time passed?" check.** `fetchLeagueRoster` and `fetchStandings` both issue through `Promise.all`, and the naive check lets concurrent callers all read the same timestamp and send the exact burst being prevented. That case is the load-bearing assertion in the test.
  - **Both numbers are starting points, not measured limits.** MFL publishes no rate limit and nothing here captures what its 429 carries (no `Retry-After` handling exists anywhere in the project). Moving either should follow a probe.
- **The login retries transient failures; a cookieless 200 does not.** `fetchWithTransientRetry`/`mflLogin` in `providers.mjs`, pinned by `test-mfl-login-retry.mjs`. "The sync degrades, it never fails" is a per-league property, and `mflLogin` runs before any of that machinery — a real scheduled run died 27 seconds in on a ten-second `UND_ERR_CONNECT_TIMEOUT`, before one league was attempted, costing a four-hour cycle. So a transport failure (fetch rejecting, with the useful code on `err.cause`) and a 429/5xx are retried on a deliberately generous 2/4/8s backoff — longer than `mflGet`'s, since the alternative to waiting is not a stale league but no sync at all. **A 4xx and a 200 carrying no session cookie are answers, not hiccups**: the second is what wrong credentials look like, and dressing it up as a network problem would cost fourteen seconds and mislabel a misconfiguration. `mflLoginForImport` deliberately does *not* use this — it backs an interactive lineup write where a fast, clear error is better and the person can just click again.
- **`TYPE=league` is read once per MFL league per run.** `fetchMflLeagueData`/`mflFranchiseNames` in `providers.mjs`, threaded through `mflNamesById` in `fetch-rosters.mjs`, pinned by `test-mfl-request-pacing.mjs`. The roster, standings and scoring passes all want the same franchise-id → name map and each used to fetch it for itself — three identical requests per league, better than a fifth of the whole budget, spent in exactly the passes the 429s were landing in. `fetchStandings` and `fetchScoring` both take the cached map as an optional trailing argument and **fetch their own when handed nothing**, which is what keeps standings working for a league whose roster pass failed before caching one. The map is a local in `main()`, never a field on the result object — everything there is serialized into `data/rosters.json` and fetched whole by every visitor on every page load.
- **The season is per league, resolved by availability, not by the calendar.** `resolveSeason` in `fetch-rosters.mjs`; `seasonOf(league)` in `providers.mjs` is how every league-scoped call picks it up, which is why none of them take a year. Global lookups (player map, byes, injuries) stay on `YEAR` deliberately. Only a *definitive* absence may move a league — never a 429 or an ESPN 401. Sleeper is never probed. Pinned by `test-season-rollover.mjs`; the MFL/ESPN 404 behaviour it rests on is verified by `probe-league-season.yml`, worth re-running whenever leagues look stuck on the wrong season.
  - ESPN caveat that survives: its reads are cookie-authenticated, so expired `espn_s2`/`SWID` make every season read as absent and an ESPN league would silently never roll over. The probe treats a false *control* season as a hard failure for this reason.
- **Scoring format is read from the league, not assumed.** `detectScoringFormat` in `providers.mjs`, verified by `probe-league-scoring.yml`, pinned by `test-scoring-format.mjs`. A rate that isn't exactly 1, 0.5 or 0 returns `null` rather than rounding — guessing puts the ECR column silently on the wrong list. In `config/leagues.json`, blank `scoring` means "detect it"; pin `PPR` explicitly for the old behaviour.
- **The availability pass is last, is once-a-day, and must not be folded back into the roster fetch.** `availabilityIsFresh`/`fetchMflRosteredNames` in `fetch-rosters.mjs`. Widening the roster fetch to the whole league looks free and is not — it cost enough of MFL's rate limit to 429 three scoring fetches and a lineup fetch behind it. Availability is the least important thing here, so it goes last and is what gives way under a rate limit. Sleeper is exempt (it already had every roster); ESPN needs its own call regardless.
- **A `draftonly` league stops having its roster read once its draft is confirmed finished.** `draftonlyRosterIsSettled` in `fetch-rosters.mjs`, pinned by `test-draftonly-freeze.mjs`. These are eight of the fifteen MFL leagues and were spending three requests each per sync — the franchise roster plus this season's and last season's player scores — on a list that does not change again; across fourteen consecutive snapshots every draft-only roster was byte-identical for as long as its draft was finished. **Only the roster block freezes.** `TYPE=league` stays (standings and scoring need the name map off it, so skipping it just moves two fetches downstream), and **standings and live scoring are fetched every sync as always** — they move every week and are what these leagues are read for. Freezing them would quietly stop a league scoring mid-season, which is why the test reads the source to confirm neither call site is gated on the freeze.
  - The gate inherits `draftIsSettled`'s season keying, so **a rollover unfreezes the league by itself** — without that, a draft-only league would serve last season's roster forever with nothing on screen saying so. An errored or empty previous entry is never frozen, and `REFRESH_AVAILABILITY` forces a real read, which makes the sync workflow's existing button the manual way to pull one forward.
  - **A draft-only roster that appears to grow after its draft is almost certainly still drafting — check `draftInProgress` before concluding otherwise.** Worlds Collide gained three players over two days and looked like a league taking free agents post-draft; `draftInProgress` was `true` for every one of those snapshots and flipped to `false` only once the roster settled. Slow drafts run for days here, so roster growth alone says nothing. This gate never applies while a draft is live, which is exactly why that league was never at risk.
  - Identity fields (`name`, `type`, `url`) are re-applied from the config on every entry, frozen or not, so an Admin-tab rename still lands. A `type` edit un-freezes the league on the spot, since the gate reads the config.
- **A league mid-draft is skipped and its `available` cleared, not carried forward.** `draftStatusFromResults`, verified by `probe-draft-status.yml`, pinned by `test-draft-status.mjs`. Zero picks means "couldn't tell", never "unfinished". Every draft unit must be finished, since a league can run one per division. The check runs ahead of the freshness rule on every sync, and is free in the steady state because a finished draft never unfinishes (`draftIsSettled`, keyed to the season).
  - **`TYPE=league` cannot answer this — don't try again.** Its `draftTimer`, `draft_kind` and `draftLimitHours` are settings, not state: two long-finished leagues both report `draftTimer: "ONS"`. That is the only reason this costs a request at all. Sleeper answers free on the league object the roster fetch already has (`pre_draft`/`drafting`); ESPN is exempt and unverified.
- **The manual workflows are `workflow_dispatch`-only, deliberately. Never add a `schedule` trigger to any of them.** `test-set-lineup.yml`, `test-login-endpoint.yml`, and every `probe-*.yml`. Each exists because the API it asks about is unreachable from a sandbox — reaching for a new field on a provider response starts with a probe here, not with code that assumes the field is there.

### Rankings, projections and power

- **The automatic ranking set is on a calendar, not a constant.** `nflSeasonPhase`/`automaticRankingType` in `fantasypros.mjs`, pinned by `test-season-phase.mjs`. `ROS` from kickoff through the Super Bowl, `DYNASTY`/`DRAFT` otherwise. Two consequences: the FantasyPros season year is *not* `YEAR` between New Year and the Super Bowl, and `myffl.html` carries a deliberate second copy of the in-season rule purely to word the Admin tab's note — the sync decides, the page only describes. Setting `rankingType` opts a league out entirely.
- **A player's FantasyPros URL is read off the rankings response, never built from the name.** `playerPageUrl` in `fantasypros.mjs`. The site disambiguates two players sharing a name (`josh-allen.php` vs `josh-allen-lb.php`) and `normalizePlayerName` drops suffixes some slugs keep. No URL means no link. Confirmed by `probe-fantasypros-player-url.yml`.
- **Three things are deliberately duplicated across the sync boundary.** The page has no build step and no imports, so the alternative to a second copy is shipping the value inside `data/rosters.json` for every player. Know these before editing either side — a drift is silent in all three cases, and all three are pinned:
  - `normalizeName` + `NAME_SUFFIX` (`myffl.html`) vs `normalizePlayerName` (`fantasypros.mjs`) — the join between a pool entry and a rostered player. A drift shows a player you hold as one you don't. Pinned behaviourally over a name corpus in `test-top-available.mjs`, which is why `NAME_SUFFIX` is deliberately left unexported.
  - `POWER_POSITIONS` — must be **identical** in `myffl.html` and `fantasypros.mjs`.
  - `POSITION_ORDER` — must **not** be identical. `providers.mjs` carries the IDP positions too; the page lists only what its leagues actually roster, so the rule is that the page's list is the sync's filtered down — same members, same relative order. Nothing in this config rosters an IDP player today, and an unlisted position falls to one shared rank at the end rather than erroring, so adding an IDP league would sort its whole defense as an undifferentiated block. `test-shared-constants.mjs` pins the last two, and additionally checks every position the committed snapshot carries against the page's list, which is the assertion that fires the day an IDP league is added.
- **Power ranks are homegrown; the FantasyPros question is settled.** Nothing team-shaped exists behind the partner API key (`probe-fantasypros-power-rank.yml` — every candidate endpoint 403'd while the consensus-rankings control answered 200). Projections *are* reachable. `computePowerScore`/`computeLeaguePower` in `fantasypros.mjs`, pinned by `test-power-rank.mjs`.
  - **MFL joins by player id** (roster ids *are* the projections' `mflid`); Sleeper and ESPN join by normalized name, and a Sleeper id must never touch the id join — both id spaces are small numeric strings, so a wrong join renders a plausible column crediting franchises with other people's players. A name collision tombstones to null.
  - The score is a **floor, not a roster valuation**: bench depth counts for nothing, kicker/defense slots are dropped from the valuation (their minimums still count against MFL's `starters.count`), and scores are comparable only *within* a league — which is why the page shows the rank ordinal and keeps the score in a tooltip.
  - ESPN is valued against `DEFAULT_POWER_SLOTS`; its real slot counts live in an mSettings view this project has never probed. Uniform-across-the-league is the property that matters, and reaching for the real counts starts with a probe.
  - Power rides the availability pass's *same* league-wide read, never a second request, so it inherits its cadence, its mid-draft skip, and its carry-forward.
  - **`computeLeaguePower` returns null when no franchise seated a player**, and `fetchProjections` **throws** on an empty position rather than computing on it — either would otherwise rank every team first, or overwrite good ranks with a uniform lie.
- **The Power Rankings card carries two sub-lines per league, Studs and Sleepers**, both rendered by `powerPlayersLine`. Studs (`STUDS_RANK_THRESHOLD`) reads `p.ecr.rank`, the same field the Rosters tab's ECR column uses, so "adjusted to ROS in season" is free. Sleepers (`SLEEPER_RANK_THRESHOLD`) reads a second, independent FantasyPros list attached by `attachSleepers`, pinned by `test-sleepers.mjs`. **The `type` parameter is `SLEEPERS`, plural** — FantasyPros silently serves the Draft list back for an unrecognised type rather than 4xx-ing, so a typo ships a line that quietly means something else. Re-run `probe-fantasypros-sleepers.yml` before touching that literal. The two thresholds are separate constants on purpose; each is a display filter expected to move independently. Both lines are omitted rather than printed empty, and both are suppressed on a row with no basis at all.
- **Team Needs is the same power data read one level deeper** (`byPosition`), rendered right after Power Rankings and built by calling `computeMyPowerRows` outright — every gate that function applies has to apply here identically or the two cards would disagree about which leagues are rankable. `hasByPosition` requires *every* team in a league to carry the shape before any position is ranked there. It flags **every position ranked below the league's own average**, not just the single worst — a real 14-team league turned up last at both WR and TE at once, and picking one would have implied a difference the numbers don't support. A team clearing the average everywhere falls back to its own weakest position(s); a team tied at every position has nothing relatively weaker and is left unflagged. Flagged positions get a sub-line under the league name, never inside the cell — a cell growing taller than its neighbours throws off every column on that row. Pinned by `test-team-needs.mjs`.
- **Projections are not available year-round, so the score has a second basis.** `ecrValue`/`buildEcrIndex` in `fantasypros.mjs` value players from the ranking pools instead, so the fallback is current exactly in the window the primary basis is dark. Pool depth is the **deepest rank present, not the entry count**. The two bases can order the same teams differently, which is why `powerUsesRankings` puts a line on the card saying which ruler was used.
- **`week=0` in season is the open question, and it is not yet answered.** The season year is phase-aware; the week is not. Frozen August projections would render as plausible ranks and say nothing, so each power object records the slot and phase it was computed under and `powerUsesPreseasonProjections` turns that into a conditional card note. It is phase-and-slot rather than a freshness date because the projections endpoint carries no `last_updated` at all. Re-run `probe-fantasypros-power-rank.yml` after kickoff; if it shows frozen numbers, switching that case to `TBD` is a one-line change.
- **Roster-limit violations are computed, never read off a verdict** — `probe-roster-validity.yml` established MFL exposes no such field. `parseRosterLimits` (`providers.mjs`) + `rosterLimitProblems` (`myffl.html`). Sitting *at* a limit is not a violation; a roster can breach several at once, so each gets its own row. **A `"0-0"` position entry means the cap isn't configured, not a cap of zero** — the same sentinel `startingSlotCounts` treats as an off-switch. This shipped without it once and flagged two auction leagues for being "3 over the 0 limit" at every position.

### The Analytics cards

- **Top Available reads the *rankings*, not our rosters**, and needs two things rosters can't supply: `rankingPools` at the top level of `data/rosters.json` (the top `RANKING_POOL_SIZE` of each list actually used, keyed by `rankingPoolKey`, URLs stored **site-relative**, `team` normalised to `'FA'`), and `available` per league. Depth is paid for by every visitor on every page load. **Kickers and defenses are dropped from the pool** (`WIRE_EXCLUDED_POSITIONS`, filtered *before* truncation), never from `buildRankingIndex` — a kicker on your own roster still gets his ECR. Pinned by `test-ranking-pool.mjs` and `test-top-available.mjs`.
- **`available: null` means "couldn't tell" and `[]` means "nothing free"; only the second belongs in a denominator.** ESPN's league-wide read fails quietly, and counting a league that was never asked would report a free agent as available in 1 of 2 leagues. The card's **Free In** and **Own In** share one denominator on purpose, so a row reads as a partition of the same leagues.
- **A redrafting league still on last season is excluded from the page, not the sync** (`awaitingRollover`, type-gated on `REDRAFTING_TYPES`). A dynasty league carries its roster across the offseason, so one trailing during the rollover window is stale rather than wrong. Both halves of the season comparison must be present — `NaN < year` is false, so nothing is dropped on missing data.
- **Don't reintroduce `ANALYTICS_GROUP`.** Analytics briefly folded redraft in with dynasty and salary-cap as one "Active" tab. That reasoning holds for the two exposure cards and breaks for Top Available, which is *ordered by consensus rank*: dynasty and redraft span two FantasyPros lists that disagree by a hundred places about the same player, and the median across them describes neither. Because that median weights by league count, the merged tab also let a portfolio holding more redraft leagues rank its dynasty wire on redraft logic. This grouping no longer exists in the code, which is why the prohibition is recorded here. Sub-tabs come from `SUBTAB_GROUP` in every view.
- **The three exposure cards share a denominator (`exposureLeagues`) but deliberately not a page size or a sort.** Player Exposure pages eight (`PLAYER_EXPOSURE_PAGE_SIZE`), Injury Exposure and Loss Exposure six each (`ANALYTICS_PAGE_SIZE`), because an injury/loss row is three lines deep against the player card's two, so the cards come out level side by side. **The two numbers are a pair** — anything changing how tall a row of either shape is has to move both.
- **Injury Exposure and Loss Exposure are one designation vocabulary split into two cards by `INJURY_SETTLED`, not one card sorted by it.** `computeInjuryExposure`/`computeLossExposure` in `myffl.html` share the aggregation (`collectInjuryDesignations`) and differ only in which side of `INJURY_SETTLED` they keep: Injury Exposure gets P/Q/D/O/DTD/COVID and anything unrecognised — this week's question; Loss Exposure gets `IR`/`IR R`/`PUP`/`NFI`/`SUSP`/`HOL`/`NA`/`RET` — a standing fact, decided for months. `IR R` is MFL's own short-term/return-designated reserve code, distinct from a plain `IR` placement in how likely a return this season is. They used to be one card with settled designations demoted to the bottom rather than filtered out, because severity alone let a one-league IR outrank a whole card of live Questionables and hold the top row from August to February. Splitting them made that demotion structural: a player who settles leaves Injury Exposure for Loss Exposure rather than sinking within it. **The two cards read `INJURY_SEVERITY` in opposite directions.** It is one continuous badness scale, least to most (`sortByWorstFirst`/`sortByBestChanceFirst`): Injury Exposure sorts worst-first — Out, Doubtful, Questionable, Probable, Day-to-Day, then COVID (rare enough now to sit below all four rather than lead the card) — and Loss Exposure sorts by *best chance of returning* first — `IR R`/`PUP`/`NFI` (same shape, cluster together), then a suspension (defined end date), a holdout (open-ended), the Commissioner Exempt list (`NA`), a plain `IR` placement, and `RET` last of all (no chance of returning). **`INJURY_SEVERITY` is emphatically not re-ranked to express the settled/live split** — it still has to mean one continuous scale for its other job: picking which designation shows when two providers disagree, where the higher index always wins regardless of which card either status belongs to. An unrecognised code is absent from `INJURY_SETTLED` on purpose and ranks below `COVID` in severity, which puts it on Injury Exposure, at the bottom, never on Loss Exposure. The digest (below) reads the same scale too, which is why `DIGEST_ALSO_FLAGGED` exists — COVID's new low rank stopped it clearing the digest's own severity floor on its own.
- **The injury detail is a sub-line under the name, never a column, on both cards** — the shared table already carries six, and a seventh of variable-length prose is the first thing to break on a phone. `Undisclosed` is dropped at sync time; `exp_return` crosses the sync as MFL's own string; it shows only inside `INJURY_RETURN_HORIZON_DAYS`. Sleeper is not consulted, and **don't go back for it**: `probe-injury-detail.yml` found `injury_body_part` merely duplicates MFL's `details` at a lower fill rate (87% vs 100%), and the fields that would have made a genuine *news* line possible — `practice_participation`, `practice_description`, `injury_start_date` — came back empty on all 586 of its injured players. There is no beat-writer text in either feed, which is why the cards say what the injury is and never claim to be an update. `attachInjuryDetail` only ever *fills in* a detail, never replaces the by-id one, and attaches nothing to a player carrying no designation.
- **Every table that names a player appends the NFL team through `appendTeamSuffix`** rather than spending a column on it. On the exposure cards it comes off the rostered player (so `LVR` from MFL sits beside `LV` from Sleeper); on Top Available off the ranking pool, the only source for a player nobody holds.
- **These cards' mistakes are all silent** — nothing on screen tells you a denominator is off. That is why so many of them are pinned by tests that run the page's own script block in a `vm`.

### History, placements and payouts

- **The History tab does not split by league type** — one Results card and one Finances card span every league at once. A dynasty finish and a draft-only finish are the same kind of fact. Both cards only ever show a league with at least one backfilled year. Gated behind login the same way Analytics is — to keep the page uncluttered for a visitor who isn't the manager, not to protect the data, which is public either way (see the login-gate note under Auth).
- **A final placement had to be derived; MFL's standings order is regular-season seeding only.** `probe-league-history.yml` confirmed a real league's 2025 champion entered the bracket as the 3-seed. ESPN by contrast exposes `rankCalculatedFinal` directly (and `rankFinal` is a same-shaped always-zero decoy — never use it). Sleeper is out of scope. `computeMflSeasonPlacements` in `history.mjs`, pinned by `test-history.mjs`. The mechanism is `TYPE=playoffBrackets` (plural) to list a season's brackets, then `TYPE=playoffBracket` per bracket — and **the parameter is `BRACKET_ID`**: `ID`, `bracket_id` and `bracketId` all fail with the same error the endpoint gives for no id at all, confirmed against an id the listing had just proven valid.
- **Bracket names are commissioner-chosen free text, so classification is by keyword, not an enum.** `bracketFamily`/`isConsolationBracket` check both `name` and `bracketWinnerTitle` — one real league ran "MNMx Dynasty Losers Bracket" with no "toilet" in the name, and only its `bracketWinnerTitle` said what it was. **Both families are scored identically; a Toilet Bowl is not scored backwards.** Two or more unplaceable leftovers, or a family with no bracket, falls back to regular-season order and is flagged `guessed: true`, which the card renders in red rather than presenting an estimate as fact.
- **A `guessed: true` result stays retry-eligible; only `guessed: false` permanently retires a year.** This distinction is load-bearing: MFL is often already near its rate limit when the backfill starts, and a rate-limited year written in as a permanent guess could never self-correct. `fetchMflSeasonBracketData` re-throws on 429 rather than starving the year down to a guess, and a confirmed 429 abandons the rest of that run's MFL backfill (`mflRateLimited`). None of this applies to ESPN, which never produces a guess.
- **The backfill is a one-time cost, budgeted separately from everything else, and must never compete with rosters/standings/scoring for MFL's rate limit.** A league's full history taking several syncs is the intended shape, not a bug to fix by raising the budget. `HISTORY_MFL_PER_LEAGUE_BUDGET` stops one league's long tail from starving every league behind it — **except when `LEAGUE_ID` targets exactly one league**, where the cap is lifted to the run-wide budget, since there is no other league to protect and the cap would otherwise fight the one thing `LEAGUE_ID` exists to do.
- **`backfill-history.yml` and `backfill-scoring.yml` run outside the regular sync** for that same contention, and share the `rosters-data-write` concurrency group with `sync-fantasy-rosters.yml` because all three commit to `data/rosters.json`. `backfill-history.mjs` trusts whatever season is already on record and does not re-resolve; a league that rolled over since the last sync is a bounded gap the next sync closes.
- **`history.league[]` can be wrong, not just absent, and there is no automatic recovery.** `historyLeagueIds` in `config/leagues.json` is the manual escape hatch, and an override **wins outright** even for a year the chain already lists. Override-covered years sort ahead of naturally-discovered ones in the backfill queue — without that, three permanently-unresolvable years nearer the present spent the whole budget every run and the override-covered years were never reached.
- **`draftonly` leagues run no playoff bracket at all** and rank by total points through week 17 (`computeMflSeasonPlacementsByPoints`). **Never a guess** — `guessed` is hardcoded false, since every rank is a hard sum over fetched data, so existing guessed years self-correct with no migration. All-or-nothing per year. Needs its own larger budget (`HISTORY_MFL_DRAFTONLY_PER_LEAGUE_BUDGET`), since one year can take 18 requests.
- **The weekly-high payout is awarded fresh every week, not once a season.** This shipped wrong once. `results[].scoring` holds `weeklyHighs` (an array, one entry per week) and `seasonHigh` (a single record). The fetch window is a fixed **weeks 1–18**; the season *total* sums only weeks 1–17. Both cutoffs are asserted by the user, not inferred. `leagueStandings.pf` is not a shortcut — it folds in playoff scoring with no usable cutoff.
- **A franchise with no head-to-head game that week is a flat entry under `weeklyResults.franchise`, not inside `.matchup`.** Reading only `.matchup` silently dropped it — and on MNMx 2021 week 15 the dropped franchise held the true weekly high. `parseMflWeekScores`, pinned by `test-weekly-scores.mjs` with that exact fixture.
- **Division Winner is a third axis, for the best regular-season record, and costs nothing extra** — `mflDivisionWinner` reads index 0 of the `regularSeasonOrder` the placement backfill already has; ESPN reads `playoffSeed === 1`. Stamped as a sibling of `rank` in the same write. Unset for `draftonly`, which never fetches standings. Shipping it late needed an exception in `yearsNeedingHistoryBackfill` so confirmed years missing the field get re-fetched once; it can't loop, since a re-fetched year always sets it.
- **`startYear` is a manager-declared floor on how far back a league's history is theirs.** A franchise slot routinely predates the current manager, and a year before they joined is a correctly-computed answer about the wrong person — worse than missing data. `isBeforeStartYear` in `myffl.html` is the authoritative gate (it works against data backfilled before the field existed); the sync-side skip is a budget optimization. Blank excludes nothing.
- **The Results card averages `rank`, never the raw fraction** — a 12-team league's numbers must not swamp a 10-team league's. Rows render most-recent-first; leagues sort by best average finish.

### The page

- **A league's display name is `leagueDisplayName(league)`, never `league.name` directly.** `league.leagueName` is the live synced name; `league.name` is the static config fallback for a provider that can't be reached. Reading `league.name` alone renders whatever placeholder the config was created with — real ESPN leagues default to names like `ESPN League 1`, which shipped to production twice. Every card, popover, digest row and export names a league through that one function.
- **The header login control renders unconditionally.** It used to appear only when some league had a lineup editor. It must not go back to that: logging in is also what reveals the Admin tab, so gating the control on league data would mean switching lineups off everywhere hides the login box, which hides the tab you'd use to switch them back on.
- **The problems digest flags only what would change what you do.** `computeLeagueProblems`/`computeProblemsDigest` in `myffl.html`, pinned by `test-problems-digest.mjs`. Its failure mode is noise, not error — a strip opening on fourteen benign rows trains the eye to skip the one that matters. So: `scoringError`/`standingsError`/`lineupError` never appear (only the roster-level `error` does, since that one means the whole card is stale fallback); Questionable starters are not flagged; absence of lineup data reads as "not asked", never as an empty lineup; each starter yields at most one row, worst problem first; an unresolvable starter id is skipped silently. The required-starters check uses the *minimum* implied by `startingLineup`, so it can miss a one-short lineup but never flag a legal one. When nothing is wrong the strip is absent entirely — an all-clear banner would train the eye to skip the spot where real problems appear.
  - Roster-limit checks run *before* the lineup-data early return, deliberately: a salary-cap or draft-only league with no lineup pilot still has a roster that can go over its limits.
- **Cut planning is gated to Dynasty leagues and to `duringWeeks1Through17`** — its own boundary, deliberately narrower than the `nflInSeason` rule the Admin tab's note reuses. From Week 17's end through the Super Bowl (`duringIrClearingWindow`) IR players count against `cutdownRosterSize` too, and the Cut dropdown extends onto the IR table to match. `cutdownRosterSize` is a manual per-league config value: MFL's own `rosterLimits.size` describes what MFL will currently tolerate, not what the league's rules require, since commissioners routinely raise it for the offseason. Boundary math pinned by `test-cut-planning-window.mjs`.
  - The Cut control is a two-option dropdown, not a checkbox, because the lineup editor already spends a checkbox column on who's starting and a mis-click there is a real MFL write.
- **`submit-lineup.js` uses an allowlist, not a denylist.** It accepts a league only if `lineupPilot` is set *and* the provider is MFL or unset. Sleeper leagues can carry `lineupPilot: true` (their starters render read-only). A future read-only provider must fail closed by default. **Do not invert this.**
- **Click-to-sort is one implementation, `makeTableSort`, shared by the three tables that have it.** Three rules, each silent when broken: the card's own order is a fourth state (natural → reverse → back to default), ties fall back to that order, and `missingLast` holds a missing value at the bottom in **both** directions. Sorting is per card and per visit, never persisted. Pinned by `test-analytics-sort.mjs`, `test-power-rank.mjs` and `test-team-needs.mjs`, each driving a DOM stub since the state lives in a closure.
- **Popovers are one implementation, `makePopover`, with four instances.** Each keeps its own element and its own `.<name>-popover` class hook; only the show/hide/anchor/dismiss machinery is shared, and content stays at the call site as the `{title, rows}` handed to `open()`. **A popover must be positioned before it is shown** — a `position: fixed` element with no top/left falls back to its static position at the end of `<body>`, lengthens the page, and fires the scroll its own dismiss handler acts on. That bug made the first click on a salary link do nothing. Deliberate dismissal (toggle, Escape, outside click) is never suppressed; only the incidental kind is.
- Every Analytics card carries the same one-line `Across N leagues` subtitle and nothing else. A group whose number looks short is explained here rather than on screen. The one exception is the conditional preseason-projections note, which is an alert rather than a standing explanation.

### Auth, plans and writes

- **Auth is stateless and password-free after login.** `SITE_PASSWORD` gates `api/login.js`, which returns an HMAC-signed 30-day token (`api/lib/auth.mjs`) replayed as a Bearer token on writes. There is no session store. MFL credentials live only on the server and are never sent to the browser.
- **Planning values sync through `api/plans.js`; everything else the page stores is device-local.** Contract lengths, salaries, cuts and result overrides round-trip through Upstash Redis over its REST API with plain `fetch`, so the no-dependency property holds. It must be Upstash rather than the marketplace's "Redis" entry, which hands back a `redis://` string needing a client library. `resolveStore` accepts either credential naming. `myfflView`/`myfflLeagueType` and the auth token stay device-local.
- **A merge is a union, so it cannot express a deletion — that is the axis the whole design turns on.** A device merges exactly once (its introduction to the store) and reads with a plain GET every load after, recording that in `myfflPlanSynced`. Merging on *every* load makes a cleared plan impossible to propagate, and the device that made the clear looks correct the whole time, which is why a single-device test cannot see it. `localStorage` is the store's cache plus `myfflPlanPending`, a persisted log where `''` is a tombstone, laid back over every answer the store gives. `doLogout` drops the pending log but keeps `myfflPlanSynced`. Pinned by `test-plans.mjs` and `test-plan-sync.mjs`, the latter driving two page instances against one store — the two-device cases are the only ones that can see this class of bug.
- **The login gate is an intended access measure. Keep it, and don't weaken it.** `isLoggedIn()` decides which cards render, and hiding Analytics, History, the ECR column and the lineup checkboxes from a logged-out viewer is the point, not incidental tidiness. Every one of those gates is deliberate; adding a card that reads roster, ranking, finance or lineup data means gating it the same way.
- **Know its limit, though, and don't mistake it for a hard boundary.** It is a deterrent that works on the realistic threat — a league mate opening the URL — and not on anyone willing to look further, because the underlying data is also in `config/leagues.json` and `data/rosters.json`, which are committed to a public repo and served openly (dues and payouts for 17 leagues, every backfilled placement and high-score win, and `starters[]` for the four pilot leagues). Accepted deliberately: none of it is worth a server round-trip. Two consequences, and they pull in opposite directions on purpose — **don't re-file the public-file part as a bug or move that data behind `api/` on privacy grounds**, and equally **don't put anything genuinely sensitive behind this gate alone**. Something that must not leak belongs where plans already are.
- **Plans are the one exception, and the reason for it is different.** They are not kept in the repo the way `config/leagues.json` is: a plan is strategy about leagues other people play in, so it goes to Upstash rather than into a public file. That distinction — plans out of the repo, everything else in it — is the whole of the privacy model.

When a rule above needs its "why", read the code:

| Subsystem | Read |
| --- | --- |

| Rankings, projections, power scoring, sleepers | `scripts/lib/fantasypros.mjs` |

The `probe-*.mjs` headers are the primary record of what each API really returns, run by run. `scripts/probe-league-history.mjs` in particular carries the full history of how MFL's bracket endpoints were reverse-engineered.

## Verifying changes

Network egress from a cloud sandbox is restricted: **`myfantasyleague.com` and `api.sleeper.app` are unreachable here, though `api.github.com` is.** You therefore cannot run `node scripts/fetch-rosters.mjs` end-to-end locally, which is exactly why the manual workflows exist. Verify against real providers by dispatching `test-set-lineup.yml` or `test-login-endpoint.yml` from GitHub Actions, or by triggering `sync-fantasy-rosters.yml`.

What *does* work locally:

```bash
node --check scripts/fetch-rosters.mjs        # syntax
for f in scripts/test-*.mjs; do node "$f"; done   # all but test-set-lineup (network write)
python3 -m http.server 8000                   # then open /myffl.html
```

Serve over HTTP rather than opening the file directly — `myffl.html` fetches `data/rosters.json` with a relative URL, which fails under `file://`. The committed `data/rosters.json` is real synced data, so the page renders fully offline; pure rendering changes can be checked this way without any provider access.

To exercise the logged-in UI (the lineup editors and the whole Admin tab) without the site password or any network access, set the token the page looks for before loading it — `isLoggedIn()` only checks that one exists:

```js
localStorage.setItem('mflAuthToken', 'anything');
```

Everything renders and behaves normally; only the calls that actually reach Vercel will fail. This is the practical way to drive the Admin tab in a headless browser. Chromium is available for that; install Playwright with `--no-save` and remove `node_modules` afterwards, since the repo is dependency-free by design and `node_modules` is not gitignored.

## Front-end conventions

`myffl.html` is a single ~8,000-line file: vanilla JS, no framework, no bundler, styles and markup and logic all inline. Match the existing idiom rather than introducing a framework or a build step — the no-toolchain property is what lets GitHub Pages serve this directly.

Rendering is a set of `renderCard` / `renderStandingsCard` / `renderScoringCard` / `renderAnalyticsCard` / `renderInjuryExposureCard` / `renderTopAvailableCard` / `renderPowerRankCard` / `renderTeamNeedsCard` / `renderResultsCard` / `renderFinancesCard` functions, driven by a tab and sub-tab system built from the league list at runtime. The sub-tab strip is derived at render time from the `data-league-type` of the cards actually present, so a group with no leagues simply doesn't get a tab. Tabs themselves are derived from the cards that exist, which is why logging out removes the Analytics, History and Admin tabs with no extra work.

Shared machinery, and what is deliberately *not* shared:

- All three Analytics cards share `appendAnalyticsTable` — one paginated table behind a handful of flags rather than three copies free to drift.
- `makeTableSort` and `makePopover` hold the sort and popover machinery for every card that has one. Content stays at the call site.
- The four popovers keep separate *instances* — they show unrelated content from unrelated tables — but share their CSS through `.popover`, with `.<name>-popover` left as a per-instance hook.
- Two features sharing a visual form otherwise get separate classes throughout this file (`.results-*` vs `.finances-*`), since there is nothing to gain from coupling them beyond a shape they duplicate on purpose.
- A clickable number that opens a popover is an established idiom: `.salary-link`, `.needs-link`, `.starters-link`, `.finances-link`.

Colour conventions worth knowing: `--accent` purple means "notable" wherever it appears on a player line; gold marks a taxi-squad player, using `--gold-chip-text` (the token for gold text on the card background) rather than `--gold-text` (the dark foreground meant *for* a bright gold chip, which is nearly invisible in dark mode). IR red (`--ir-text`) means "needs a look" — a planned cut, an estimated finish.
