# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**How to use it.** This is an index of rules, not the reasoning behind them. Nearly every rule here is explained at length in a comment at the code it governs — the source is 30–47% comments by line, and those comments are the authority. Each entry below names the function or file to read. When you change something, update the comment at the code first; update this file only when the *rule* changes.

**Keep entries short.** An entry states the rule, names what to read, and says how it fails silently — three or four sentences. It does not re-explain the reasoning; that lives at the code and going there is the point. This file is loaded in full at the start of every session, so length here is a tax on every task. It had drifted to 95KB with one bullet at 9,400 characters, all of it duplicating comments that already said it better.

## What this repo is

A personal static site (`melbostads.com`) whose only real application is **`myffl.html`** — a fantasy football dashboard aggregating ~18 leagues across MyFantasyLeague (MFL), ESPN, and Sleeper. Every other page is a stub, an iframe wrapper around a Google Sheet, or a redirect. `myffl_v1.html` is the retired predecessor, kept for reference.

There is **no build step, no test framework, no linter, and no dependencies**. `package.json` exists only to set `"type": "module"` for the `.mjs`/`.js` files under `scripts/` and `api/`. Do not add `npm test`/`npm run build` scripts expecting them to be wired to anything. Tests are plain `node scripts/test-*.mjs` files run by `syntax-check.yml`; every one of them is expected to be listed there.

## Two deployment targets, one repository

This is the single most important thing to understand before changing anything:

| Path | Deploys to | Serving |
| --- | --- | --- |
| `*.html`, `data/`, images | GitHub Pages | `melbostads.com` (see `CNAME`) |
| `api/*.js` | Vercel | `shamrock84-github-io.vercel.app` |

`myffl.html` is served from Pages but calls Vercel by **absolute URL** (constants near the top of its script block). Every request is therefore cross-origin; `api/lib/cors.mjs` carries the shared allowlist and preflight handling that every endpoint imports.

Consequences that bite:

- **Secrets exist in two independent places.** GitHub Actions secrets power the scheduled sync; Vercel project environment variables power the API functions. They are not shared. Adding a credential means setting it in both, or deciding which half needs it. (The Upstash Redis credentials for `api/plans.js` are Vercel-only — the sync never touches plans.)
- **`.vercelignore` keeps the deployment down to what `api/` actually needs, and that is a quota, not a tidiness preference.** Vercel uploads and stores the whole repo per deployment; this repo is ~172MB of working tree, almost all of it `mfl/` and `images/` static art that only Pages serves. Unignored, a free team's 10GB of deployment storage is gone in under a hundred deployments — and the roster sync commits every four hours. It hit that ceiling once. The file cuts a deployment to ~0.7MB. **`ignoreCommand` does not help with this**: it skips the *build*, not the source upload, so a skipped deployment costs the same storage as a real one. Two rules: anything the functions read at runtime must stay (today `config/leagues.json` and `scripts/lib/providers.mjs`, both loaded by path rather than bundled), and the `!scripts/lib/` negation stays — `scripts/*.mjs` only matches the top level under gitignore semantics, but under looser globbing it would swallow `providers.mjs` and take live-scoring and submit-lineup with it. Verify a change with `git ls-files -i -c --exclude-from=.vercelignore`.
  - Known, accepted: `data/` is excluded, so the unused `vercel.app` copy of `myffl.html` can no longer fetch `data/rosters.json`. The page is served from Pages at `melbostads.com`, where the relative fetch resolves normally. Nothing depends on the Vercel copy.
- **`vercel.json`'s `ignoreCommand` skips the Vercel build** unless the commit touched `api/`, `scripts/lib/providers.mjs`, `scripts/lib/fantasypros.mjs`, or `config/leagues.json`. **If you make `api/` import a new shared module you must add it to `ignoreCommand`**, or Vercel silently skips deploys that need to ship. `fantasypros.mjs` is on the list because `api/live-scoring.js` imports it directly, and `.vercelignore`'s `!scripts/lib/` negation is what keeps the file in the upload at all. `attachInjuryDetail` by contrast stays in `fetch-rosters.mjs`: it needs `normalizePlayerName` too, but only the sync calls it, so there was never a reason to cross that boundary.

## Two data paths, deliberately separate

**Slow path — snapshot, committed to the repo.** `sync-fantasy-rosters.yml` runs every 4 hours (and on demand), executes `scripts/fetch-rosters.mjs`, and commits the result to `data/rosters.json`. This carries rosters, standings, scoring, lineups, the FantasyPros ranking pools and each league's free agents. `myffl.html` fetches that file directly with a cache-buster — the whole file, on every page load, which is the budget any new field is spending. **All three writers of that file go through `serializeSnapshot` in `fetch-rosters.mjs`** (this script and both backfills import it) — top-level keys one per line and **one line per league**, the same trade `serialize` makes for `config/leagues.json`. Not `JSON.stringify(..., null, 2)`, which spent 1.32MB to say what 617KB says, and not fully minified either: the extra 42 gzipped bytes are not worth losing a readable `git diff` on a file a bot rewrites six times a day.

**Fast path — live, never written down.** `api/live-scoring.js` is polled roughly every 30s while the Scoring tab is open. It only answers requests; it writes nothing. It keeps a module-level cache (MFL cookie ~20 min, franchise names ~1 hour) that survives warm invocations and resets on cold start.

Both paths import the same fetch logic from **`scripts/lib/providers.mjs`**. `fetch-rosters.mjs` is orchestration only — provider quirks belong in `providers.mjs`.

`api/trigger-sync.js` bridges the two: the page's "Last synced" link dispatches the sync workflow via a repo-scoped PAT, behind a 2-minute cooldown so the button can't be used to hammer MFL/ESPN.

## `config/leagues.json` is the control plane

Adding, removing, or reclassifying a league is a config edit, never a code edit — and usually not even a repo edit: the **Admin tab** in `myffl.html`, visible once logged in, edits this file through `api/save-leagues.js` and commits it. Prefer pointing the user at that tab over hand-editing on their behalf.

That endpoint is the only write path in the project that **bypasses pull requests entirely and commits straight to `main`**, so the syntax-check workflow never sees it. Its server-side validation is therefore the only guardrail, and `scripts/test-save-leagues.mjs` is what keeps that validation honest — extend the tests alongside any change to the schema.

The file's own `_readme` array is the authoritative schema — **read it before touching anything league-shaped, and update it when you change the schema.** Array order is display order across every tab.

Rules that live here rather than in the schema:

- `mergeLeague` passes through fields it doesn't recognise. Without it, any field added to the config later would be silently erased the first time someone pressed Save.
- `serialize` keeps one league per line, so an Admin-tab commit is reviewable as a one-line diff. A nested-object value (`historyLeagueIds`) gets the same spaced-out treatment, so a readable hand-edit survives a save byte-for-byte.
- `RETIRED_KEYS` in `api/save-leagues.js` is the mechanism for removing a config field permanently — the unknown-key passthrough would otherwise preserve it forever. It currently strips `format` and `commishEmail`.
- **`type: 'bestball'` was renamed to `'draftonly'`** and nothing in the UI or config says "best ball" as a type any more. Best Ball is a scoring system several salary-cap leagues use, and it lives in `tags`. This rename has no code left to point at, which is why it is recorded here.
- `type` carries one behaviour beyond display: `salarycap` renders the Salary/Yrs columns and the cap summary, and makes the sync fetch the cap and salary adjustments at all.
- Three providers are supported: `mfl` (the default when `provider` is omitted), `espn`, and `sleeper`. Provider selection is a three-way ternary repeated at each stage of `fetch-rosters.mjs` (roster, standings, scoring, lineup), so adding a fourth means updating `providers.mjs` *and* each of those call sites.

## Invariants worth preserving

Grouped by subsystem. Each is the rule; the named function carries the reasoning.

### Sync, seasons and rate limits

- **The sync degrades, it never fails.** `fetch-rosters.mjs` wraps every league in try/catch and falls back to the previous `data/rosters.json` entry (`previousById`), recording an `error` field the page renders. One dead league must never blank out the other seventeen. FantasyPros rankings are layered on last and are likewise never allowed to fail the run.
- **Every MFL entry point paces its requests, each at its own interval.** `setMflRequestInterval`/`paceMflRequest` in `providers.mjs`, pinned by `test-mfl-request-pacing.mjs`. The 429s are a *burst* problem — the sync had no send-rate floor at all until this existed, and 24 of 29 committed snapshots carried at least one 429, clustered at the tail of each pass. `mflGet`'s retry is only the reactive half; the gate is the half that decides whether MFL refuses in the first place. Three rules here:
  - **It is off by default and opt-in per entry point, and the interval is per entry point too** — that difference is the design, not an inconsistency. `MFL_REQUEST_INTERVAL_MS` (300ms) in `fetch-rosters.mjs`, shared by both backfills, because an unattended cron can spend wall-clock freely. `LIVE_SCORING_MFL_INTERVAL_MS` (300ms, raised twice from 75ms after real production 429s from cold-start bursts) in `api/live-scoring.js`, because that one fans out across every league at once and pays the interval in latency on a user-facing tab. The two numbers matching now is coincidence, not the constraints merging — this file's real limit was always "a cold burst has to fit inside the execution ceiling", which is why `api/live-scoring.js` carries its own explicit `maxDuration: 30` rather than trusting Vercel's undocumented default. **Still don't make the gate global** — each entry point opting in separately is what let this one move without touching the sync's number.
  - **It serializes request *starts* on a promise chain, not with a "has enough time passed?" check.** `fetchLeagueRoster` and `fetchStandings` both issue through `Promise.all`, and the naive check lets concurrent callers all read the same timestamp and send the exact burst being prevented. That case is the load-bearing assertion in the test.
  - **Both numbers are starting points, not measured limits.** MFL publishes no rate limit and nothing here captures what its 429 carries (no `Retry-After` handling exists anywhere in the project). Moving either should follow a probe.
- **The login retries transient failures; a cookieless 200 does not.** `fetchWithTransientRetry`/`mflLogin`, pinned by `test-mfl-login-retry.mjs`. "The sync degrades, it never fails" is a per-league property and `mflLogin` runs before any of it — a real run died 27 seconds in on a connect timeout, before one league was attempted, costing a four-hour cycle. So a transport failure and a 429/5xx retry on a deliberately generous 2/4/8s backoff, longer than `mflGet`'s, since the alternative to waiting is no sync at all. **A 4xx and a 200 carrying no session cookie are answers, not hiccups** — the second is what wrong credentials look like. `mflLoginForImport` deliberately does not use this: it backs an interactive write where a fast, clear error is better.
- **`TYPE=league` is read once per MFL league per run for names, roster limits and lineup slots.** `fetchMflLeagueData`/`mflFranchiseNames`, threaded through `mflFranchiseInfoById`, pinned by `test-mfl-request-pacing.mjs`. The roster, standings and scoring passes each used to fetch the same franchise-id → name map — three identical requests per league, better than a fifth of the whole budget, spent in exactly the passes the 429s landed in. **`fetchStandings` and `fetchScoring` take the cached `{ nameById, ownerById }` pair as an optional trailing argument and fetch their own when handed nothing**, which keeps standings working for a league whose roster pass failed first. **The pair is a local in `main()`, never a field on the result object** — everything there is serialized into `data/rosters.json` and downloaded by every visitor.
  - **`ownerById` is the one exception, and it costs a second request per MFL league.** `fetchMflOwnerNames` re-reads `TYPE=league` but sends it to that league's OWN regional host (`baseURL`, e.g. `www43.myfantasyleague.com`) rather than the generic `api.myfantasyleague.com` every other MFL call here uses. This project long believed `owner_name` was gated by commissioner access; that verdict inferred access from the field's own presence and never checked it independently. The manager confirmed the opposite on several leagues, and `probe-mfl-owner-name.mjs` run #3 caught the set changing between two reads the same day. Run #4 found the cause: **`mflGet`'s hardcoded generic host unreliably recognizes even a genuinely privileged session** — the same host-routing failure `mflLoginForImport` already fixed for writes, never applied to reads. Against its own `baseURL`, every league returned real owner names. Rendered as "Team Name (Owner)" by `teamNameWithOwner`, same as ESPN's `espnOwnerName` and Sleeper's `display_name`.
- **The season is per league, resolved by availability, not by the calendar.** `resolveSeason` in `fetch-rosters.mjs`; `seasonOf(league)` in `providers.mjs` is how every league-scoped call picks it up, which is why none of them take a year. Global lookups (player map, byes, injuries) stay on `YEAR` deliberately. Only a *definitive* absence may move a league — never a 429 or an ESPN 401. Sleeper is never probed. Pinned by `test-season-rollover.mjs`; the MFL/ESPN 404 behaviour it rests on is verified by `probe-league-season.yml`, worth re-running whenever leagues look stuck on the wrong season.
  - ESPN caveat that survives: its reads are cookie-authenticated, so expired `espn_s2`/`SWID` make every season read as absent and an ESPN league would silently never roll over. The probe treats a false *control* season as a hard failure for this reason.
- **Scoring format is read from the league, not assumed.** `detectScoringFormat` in `providers.mjs`, verified by `probe-league-scoring.yml`, pinned by `test-scoring-format.mjs`. A rate that isn't exactly 1, 0.5 or 0 returns `null` rather than rounding — guessing puts the ECR column silently on the wrong list. In `config/leagues.json`, blank `scoring` means "detect it"; pin `PPR` explicitly for the old behaviour.
- **The availability pass is last, is once-a-day, and must not be folded back into the roster fetch.** `availabilityIsFresh`/`fetchMflRosteredNames` in `fetch-rosters.mjs`. Widening the roster fetch to the whole league looks free and is not — it cost enough of MFL's rate limit to 429 three scoring fetches and a lineup fetch behind it. Availability is the least important thing here, so it goes last and is what gives way under a rate limit. Sleeper is exempt (it already had every roster); ESPN needs its own call regardless.
- **A `draftonly` league stops having its roster read once its draft is confirmed finished.** `draftonlyRosterIsSettled`, pinned by `test-draftonly-freeze.mjs`. Eight of the fifteen MFL leagues, three requests each per sync, on a list that does not change again — fourteen consecutive snapshots had every draft-only roster byte-identical while its draft was finished. **Only the roster block freezes.** `TYPE=league` stays (standings and scoring need its name map), and **standings and live scoring are fetched every sync as always** — freezing those would quietly stop a league scoring mid-season, which is why the test reads the source to confirm neither call site is gated on the freeze.
  - The gate inherits `draftIsSettled`'s season keying, so **a rollover unfreezes the league by itself** — otherwise it would serve last season's roster forever with nothing on screen saying so. An errored or empty previous entry is never frozen, and `REFRESH_DRAFTONLY_ROSTERS` forces a real read. **That flag is deliberately separate from `REFRESH_AVAILABILITY`** — they shared one, and a forced availability refresh was spending three needless MFL requests per draft-only league re-reading rosters this gate proves don't change, exactly the load that tips MFL into 429s during an already-heavy manual run.
  - **A draft-only roster that appears to grow after its draft is almost certainly still drafting — check `draftInProgress` before concluding otherwise.** Worlds Collide gained three players over two days and looked like a league taking free agents post-draft; `draftInProgress` was `true` for every one of those snapshots and flipped to `false` only once the roster settled. Slow drafts run for days here, so roster growth alone says nothing. This gate never applies while a draft is live, which is exactly why that league was never at risk.
  - Identity fields (`name`, `type`, `url`) are re-applied from the config on every entry, frozen or not, so an Admin-tab rename still lands. A `type` edit un-freezes the league on the spot, since the gate reads the config.
- **A league mid-draft is skipped and its `available` cleared, not carried forward.** `draftStatusFromResults`, verified by `probe-draft-status.yml`, pinned by `test-draft-status.mjs`. Zero picks means "couldn't tell", never "unfinished". Every draft unit must be finished, since a league can run one per division. The check runs ahead of the freshness rule on every sync, and is free in the steady state because a finished draft never unfinishes (`draftIsSettled`, keyed to the season).
  - **`TYPE=league` cannot answer this — don't try again.** Its `draftTimer`, `draft_kind` and `draftLimitHours` are settings, not state: two long-finished leagues both report `draftTimer: "ONS"`. That is the only reason this costs a request at all. Sleeper answers free on the league object the roster fetch already has (`pre_draft`/`drafting`); ESPN is exempt and unverified.
- **Every workflow checks out blobless and sparse, with the same five directories, and a new one must copy that block.** `filter: blob:none` plus a cone-mode `sparse-checkout` of `api scripts config data .github` in all 30 workflows; the reasoning and the measured numbers are in `sync-fantasy-rosters.yml`'s own comment. The repo is ~172MB of working tree and ~121MB of objects at the tip, nearly all of it `mfl/PSD` and `images/` that no workflow reads — and `actions/checkout`'s default depth-1 does *not* avoid it, since a shallow clone still downloads every blob in the tip tree. Trimming the list per job saves nothing worth the divergence; `.github` in particular is what the registration guard below reads, and cone mode is what keeps `myffl.html` and `package.json` present without listing them.
- **Every `scripts/test-*.mjs` must be listed as a step in `syntax-check.yml`, and that is now enforced rather than remembered.** The "Check every test is registered in this workflow" step fails the run on an unregistered test. `test-set-lineup.mjs` is the one permanent exception — it performs a real MFL lineup write, so it stays `workflow_dispatch`-only. Before this existed, a new test simply never ran and the suite stayed green.
- **The manual workflows are `workflow_dispatch`-only, deliberately. Never add a `schedule` trigger to any of them.** `test-set-lineup.yml`, `test-login-endpoint.yml`, and every `probe-*.yml`. Each exists because the API it asks about is unreachable from a sandbox — reaching for a new field on a provider response starts with a probe here, not with code that assumes the field is there.

### Rankings, projections and power

- **The automatic ranking set is on a calendar, not a constant.** `nflSeasonPhase`/`automaticRankingType` in `fantasypros.mjs`, pinned by `test-season-phase.mjs`. `ROS` from kickoff through the Super Bowl, `DYNASTY`/`DRAFT` otherwise. Two consequences: the FantasyPros season year is *not* `YEAR` between New Year and the Super Bowl, and `myffl.html` carries a deliberate second copy of the in-season rule purely to word the Admin tab's note — the sync decides, the page only describes. Setting `rankingType` opts a league out entirely.
- **A player's FantasyPros URL is read off the rankings response, never built from the name.** `playerPageUrl` in `fantasypros.mjs`. The site disambiguates two players sharing a name (`josh-allen.php` vs `josh-allen-lb.php`) and `normalizePlayerName` drops suffixes some slugs keep. No URL means no link. Confirmed by `probe-fantasypros-player-url.yml`.
- **Three things are deliberately duplicated across the sync boundary.** The page has no build step and no imports, so the alternative to a second copy is shipping the value inside `data/rosters.json` for every player. Know these before editing either side — a drift is silent in all three cases, and all three are pinned:
  - `normalizeName` + `NAME_SUFFIX` (`myffl.html`) vs `normalizePlayerName` (`fantasypros.mjs`) — the join between a pool entry and a rostered player. A drift shows a player you hold as one you don't. Pinned behaviourally over a name corpus in `test-top-available.mjs`, which is why `NAME_SUFFIX` is deliberately left unexported.
  - `POWER_POSITIONS` — must be **identical** in `myffl.html` and `fantasypros.mjs`.
  - `POSITION_ORDER` — must **not** be identical. `providers.mjs` carries the IDP positions too; the page lists only what its leagues actually roster, so the rule is that the page's list is the sync's filtered down — same members, same relative order. Nothing in this config rosters an IDP player today, and an unlisted position falls to one shared rank at the end rather than erroring, so adding an IDP league would sort its whole defense as an undifferentiated block. `test-shared-constants.mjs` pins the last two, and additionally checks every position the committed snapshot carries against the page's list, which is the assertion that fires the day an IDP league is added.
- **Power ranks are homegrown; the FantasyPros question is settled.** Nothing team-shaped exists behind the partner API key (`probe-fantasypros-power-rank.yml` — every candidate endpoint 403'd while the consensus-rankings control answered 200). Projections *are* reachable. `computePowerScore`/`computeLeaguePower` in `fantasypros.mjs`, pinned by `test-power-rank.mjs`.
  - **MFL joins by player id** (roster ids *are* the projections' `mflid`); Sleeper and ESPN join by normalized name, and a Sleeper id must never touch the id join — both id spaces are small numeric strings, so a wrong join renders a plausible column crediting franchises with other people's players. A name collision tombstones to null.
  - The score is a **floor, not a roster valuation**: bench depth counts for nothing, kicker/defense slots are dropped from the valuation (their minimums still count against MFL's `starters.count`), and scores are comparable only *within* a league — which is why the page shows the rank ordinal and keeps the score in a tooltip.
  - ESPN is valued against `DEFAULT_POWER_SLOTS`; its real slot counts live in an mSettings view this project has never probed. Uniform-across-the-league is the property that matters, and reaching for the real counts starts with a probe.
  - Power rides the availability pass's *same* league-wide read, never a second request, so it inherits its cadence, its mid-draft skip, and its carry-forward.
  - **`computeLeaguePower` returns null when no franchise seated a player**, and `fetchProjections` **throws** on an empty position rather than computing on it — either would otherwise rank every team first, or overwrite good ranks with a uniform lie.
- **The Power Rankings card carries two sub-lines per league, Studs and Sleepers**, both rendered by `powerPlayersLine`. Studs (`STUDS_RANK_THRESHOLD`) reads `p.ecr.rank`, the same field the ECR column uses, so "adjusted to ROS in season" is free. Sleepers (`SLEEPER_RANK_THRESHOLD`) reads a second list attached by `attachSleepers`, pinned by `test-sleepers.mjs`. **The `type` parameter is `SLEEPERS`, plural** — FantasyPros serves the Draft list back for an unrecognised type rather than 4xx-ing, so a typo ships a line that quietly means something else. Re-run `probe-fantasypros-sleepers.yml` before touching that literal. The two thresholds are separate constants on purpose. Both lines are omitted rather than printed empty.
- **Team Needs is the same power data read one level deeper** (`byPosition`), built by calling `computeMyPowerRows` outright — every gate that function applies has to apply here identically or the two cards would disagree about which leagues are rankable. `hasByPosition` requires *every* team in a league to carry the shape before any position is ranked. **It flags every position below the league's own average, not just the single worst** — a real 14-team league turned up last at both WR and TE, and picking one would imply a difference the numbers don't support. A team clearing the average everywhere falls back to its own weakest; a team tied everywhere is left unflagged. **Flagged positions go in a sub-line under the league name, never inside the cell** — a taller cell throws off every column on that row. Pinned by `test-team-needs.mjs`.
- **Projections are not available year-round, so the score has a second basis.** `ecrValue`/`buildEcrIndex` in `fantasypros.mjs` value players from the ranking pools instead, so the fallback is current exactly in the window the primary basis is dark. Pool depth is the **deepest rank present, not the entry count**. The two bases can order the same teams differently, which is why `powerUsesRankings` puts a line on the card saying which ruler was used.
- **In season, `fetchProjections` asks FantasyPros for `ros=true`, not `week=0`.** Confirmed live 2026-09-16 after `week=0` was confirmed frozen (byte-identical pre- and post-kickoff) and an initial premium-tier-gate misread of `ros=true`'s response was corrected by FantasyPros support — see fetchProjections' own history comment in `fantasypros.mjs` for the full story. `powerUsesPreseasonProjections` (`myffl.html`) stays as a regression guard: `week: '0'` with `inSeason: true` and no `ros` flag on the meta is now specifically the signature of this fix breaking, not the everyday state.
- **Roster-limit violations are computed, never read off a verdict** — `probe-roster-validity.yml` established MFL exposes no such field. `parseRosterLimits` (`providers.mjs`) + `rosterLimitProblems` (`myffl.html`). Sitting *at* a limit is not a violation; a roster can breach several at once, so each gets its own row. **A `"0-0"` position entry means the cap isn't configured, not a cap of zero** — the same sentinel `startingSlotCounts` treats as an off-switch. This shipped without it once and flagged two auction leagues for being "3 over the 0 limit" at every position.

### The Analytics cards

- **Top Available reads the *rankings*, not our rosters**, and needs two things rosters can't supply: `rankingPools` at the top level of `data/rosters.json` (the top `RANKING_POOL_SIZE` of each list actually used, keyed by `rankingPoolKey`, URLs stored **site-relative**, `team` normalised to `'FA'`), and `available` per league. Depth is paid for by every visitor on every page load. **Kickers and defenses are dropped from the pool** (`WIRE_EXCLUDED_POSITIONS`, filtered *before* truncation), never from `buildRankingIndex` — a kicker on your own roster still gets his ECR. Pinned by `test-ranking-pool.mjs` and `test-top-available.mjs`.
- **`available: null` means "couldn't tell" and `[]` means "nothing free"; only the second belongs in a denominator.** ESPN's league-wide read fails quietly, and counting a league that was never asked would report a free agent as available in 1 of 2 leagues. The card's **Free In** and **Own In** share one denominator on purpose, so a row reads as a partition of the same leagues.
- **A redrafting league still on last season is excluded from the page, not the sync** (`awaitingRollover`, type-gated on `REDRAFTING_TYPES`). A dynasty league carries its roster across the offseason, so one trailing during the rollover window is stale rather than wrong. Both halves of the season comparison must be present — `NaN < year` is false, so nothing is dropped on missing data.
- **Don't reintroduce `ANALYTICS_GROUP`'s mistake for Top Available specifically.** Analytics briefly folded redraft in with dynasty and salary-cap as one "Active" tab. That grouping was reverted whole because Top Available broke: it's *ordered by consensus rank*, and dynasty and redraft span two FantasyPros lists that disagree by a hundred places about the same player, so the median across them describes neither. Worse, the median weights by league count, so a portfolio that happens to hold more redraft leagues would silently rank its dynasty wire on redraft logic. That hazard is real only for Top Available — see the next bullet for why every other Analytics card was safe to re-merge. Top Available alone still gets one card per group, shown or hidden by the sub-tab pills rather than recomputed by them, and it never gets one for Draft Only at all: those leagues run a single draft and never open a waiver wire, so there's no free agent for the card to mean anything by (`renderGrid`'s Top Available loop skips `groupKey === 'draftonly'` outright).
- **Dynasty and Salary Cap are separate sub-tab pills everywhere — Rosters, Standings, Scoring, Analytics, History, Admin — via `SUBTAB_GROUP`, except on Top Available, which is the one place they stay one card.** Top Available reads its own `TOP_AVAILABLE_GROUP` map rather than the pill grouping, because the ranking-list hazard above is about Redraft vs. everything else — Dynasty and Salary Cap read the same FantasyPros list, so splitting them would rank the same free agents twice. **That card therefore carries both keys comma-joined in `data-league-type`** (`dynasty,salarycap`) and stays visible if either pill is checked — the one card `updateVisibility` matches against more than one. `typesInGroupMap`/`presentGroupsFor` are the shared plumbing, so a third grouping reuses them rather than copying the filter again.
- **Power Rankings, Team Needs, Bye Weeks, Player Exposure, Injury Exposure and Loss Exposure are the opposite: one card apiece, spanning whichever sub-tabs are checked (Draft Only included), live-recomputed on every toggle.** They are exempt from Top Available's hazard because none compares a raw list position across leagues — they read a within-league ordinal (`competitionRanks`, via `leaguePowerRanks`) or a plain roster count. `mergedAnalyticsCards()` returns all six with their DOM ids and render functions, in display order; `refreshMergedAnalyticsCards` rebuilds them after `#merged-analytics-anchor`, `appendMergedAnalyticsCards` seeds them once from `renderGrid`, and all three share `unionTypesForGroups`/`analyticsPresentGroups` so they cannot disagree about a selection. Two traps:
  - **These six carry no `data-league-type`** — the established way (shared with History/Admin) to opt out of the pills' show/hide filter. So Analytics cannot read present sub-tabs off a rendered card the way other views do; `renderSubTabs` and `renderGrid` both call `analyticsPresentGroups(leagues)` computed from league data instead.
  - **`searchAwareRefreshers` entries carry `{card, fn}`, not a bare closure**, and `updateVisibility` prunes any whose card has left the document. Otherwise every sub-tab toggle leaks a stale closure rendering into a detached table forever.
- **The Analytics tab's card order flips on `nflInSeason()`, and Top Available moves with it.** In season, `mergedAnalyticsCards()` returns `MERGED_ANALYTICS_ORDER_IN_SEASON` (Injury Exposure, Loss Exposure, Bye Weeks, Power Rankings, Team Needs, Player Exposure — the weekly action cards ahead of the roster-construction ones, Loss Exposure kept beside Injury Exposure since the two share one designation vocabulary) and `renderGrid` renders Top Available *before* that block, since a fresh wire beats even the weekly cards. Off-season it's `MERGED_ANALYTICS_ORDER_OFFSEASON` (Team Needs, Power Rankings, Player Exposure, then the three weekly cards pushed to the bottom, since none of them means anything without games), and Top Available trails the whole block instead. Both orders are read by `appendMergedAnalyticsCards` and `refreshMergedAnalyticsCards` alike, so a mid-session rollover (Analytics stays open across the Thursday-after-Labor-Day or Super-Bowl boundary) reorders on the very next sub-tab toggle rather than waiting for a reload.
- **The three exposure cards share a denominator (`exposureLeagues`) but deliberately not a page size or a sort.** Player Exposure pages eight (`PLAYER_EXPOSURE_PAGE_SIZE`), Injury Exposure and Loss Exposure six each (`ANALYTICS_PAGE_SIZE`), because an injury/loss row is three lines deep against the player card's two, so the cards come out level side by side. **The two numbers are a pair** — anything changing how tall a row of either shape is has to move both.
- **Injury Exposure and Loss Exposure are one designation vocabulary split into two cards by `INJURY_SETTLED`, not one card sorted by it.** `computeInjuryExposure`/`computeLossExposure` share the aggregation (`collectInjuryDesignations`) and differ only in which side they keep: Injury Exposure gets P/Q/D/O/DTD/COVID and anything unrecognised (this week's question), Loss Exposure gets `IR`/`IR R`/`PUP`/`NFI`/`SUSP`/`HOL`/`NA`/`RET` (a standing fact). Splitting them made the old demotion structural — a player who settles leaves one card for the other rather than sinking within it.
  - **The two cards read `INJURY_SEVERITY` in opposite directions** (`sortByWorstFirst`/`sortByBestChanceFirst`) — Injury Exposure worst-first, Loss Exposure best-chance-of-returning-first. **It is emphatically not re-ranked to express that split**: it still has to mean one continuous scale for its other job, picking which designation wins when two providers disagree. An unrecognised code is absent from `INJURY_SETTLED` on purpose, ranks below `COVID`, and so lands at the bottom of Injury Exposure, never on Loss Exposure. The digest reads the same scale, which is why `DIGEST_ALSO_FLAGGED` exists.
- **The injury detail is a sub-line under the name, never a column, on both cards** — the shared table already carries six, and a seventh of variable-length prose is the first thing to break on a phone. `Undisclosed` is dropped at sync time; `exp_return` crosses as MFL's own string and shows only inside `INJURY_RETURN_HORIZON_DAYS`. **Sleeper is not consulted, and don't go back for it** — `probe-injury-detail.yml` found `injury_body_part` merely duplicates MFL's `details` at a lower fill rate, and the three fields that would have made a real *news* line possible came back empty on all 586 of its injured players. The cards say what the injury is and never claim to be an update. `attachInjuryDetail` only ever *fills in* a detail, never replaces the by-id one, and attaches nothing to a player with no designation.
- **Every table that names a player appends the NFL team through `appendTeamSuffix`** rather than spending a column on it. On the exposure cards it comes off the rostered player (so `LVR` from MFL sits beside `LV` from Sleeper); on Top Available off the ranking pool, the only source for a player nobody holds. Every starter in the Scoring drawer gets one too, defenses included — see the next bullet on why that isn't a repeat.
- **These cards' mistakes are all silent** — nothing on screen tells you a denominator is off. That is why so many of them are pinned by tests that run the page's own script block in a `vm`.

### History, placements and payouts

- **The History tab does not split by league type** — one Results card and one Finances card span every league at once. A dynasty finish and a draft-only finish are the same kind of fact. Both cards only ever show a league with at least one backfilled year. **Unlike Analytics/Admin, it renders logged out too** — the login gate never protected this data (it's public either way, in `config/leagues.json` and `data/rosters.json`; see the login-gate note under Auth), so gating it only cost the manager a login to check their own history. Editing a guessed finish in place is still login-only (`buildResultRankCell`).
- **A final placement had to be derived; MFL's standings order is regular-season seeding only.** `probe-league-history.yml` confirmed a real league's 2025 champion entered the bracket as the 3-seed. ESPN by contrast exposes `rankCalculatedFinal` directly (and `rankFinal` is a same-shaped always-zero decoy — never use it). Sleeper is out of scope. `computeMflSeasonPlacements` in `history.mjs`, pinned by `test-history.mjs`. The mechanism is `TYPE=playoffBrackets` (plural) to list a season's brackets, then `TYPE=playoffBracket` per bracket — and **the parameter is `BRACKET_ID`**: `ID`, `bracket_id` and `bracketId` all fail with the same error the endpoint gives for no id at all, confirmed against an id the listing had just proven valid.
- **Bracket names are commissioner-chosen free text, so classification is by keyword, not an enum.** `bracketFamily`/`isConsolationBracket` check both `name` and `bracketWinnerTitle` — one real league ran "MNMx Dynasty Losers Bracket" with no "toilet" in the name, and only its `bracketWinnerTitle` said what it was. **Both families are scored identically; a Toilet Bowl is not scored backwards.** Two or more unplaceable leftovers, or a family with no bracket, falls back to regular-season order and is flagged `guessed: true`, which the card renders in red rather than presenting an estimate as fact.
- **A `guessed: true` result stays retry-eligible; only `guessed: false` permanently retires a year.** This distinction is load-bearing: MFL is often already near its rate limit when the backfill starts, and a rate-limited year written in as a permanent guess could never self-correct. `fetchMflSeasonBracketData` re-throws on 429 rather than starving the year down to a guess, and a confirmed 429 abandons the rest of that run's MFL backfill (`mflRateLimited`). None of this applies to ESPN, which never produces a guess.
- **The backfill is a one-time cost, budgeted separately from everything else, and must never compete with rosters/standings/scoring for MFL's rate limit.** A league's full history taking several syncs is the intended shape, not a bug to fix by raising the budget. `HISTORY_MFL_PER_LEAGUE_BUDGET` stops one league's long tail from starving every league behind it — **except when `LEAGUE_ID` targets exactly one league**, where the cap is lifted to the run-wide budget, since there is no other league to protect and the cap would otherwise fight the one thing `LEAGUE_ID` exists to do.
- **`backfill-history.yml` and `backfill-scoring.yml` run outside the regular sync** for that same contention, and share the `rosters-data-write` concurrency group with `sync-fantasy-rosters.yml` because all three commit to `data/rosters.json`. `backfill-history.mjs` trusts whatever season is already on record and does not re-resolve; a league that rolled over since the last sync is a bounded gap the next sync closes.
- **`history.league[]` can be wrong, not just absent, and there is no automatic recovery.** `historyLeagueIds` in `config/leagues.json` is the manual escape hatch, and an override **wins outright** even for a year the chain already lists. Override-covered years sort ahead of naturally-discovered ones in the backfill queue — without that, three permanently-unresolvable years nearer the present spent the whole budget every run and the override-covered years were never reached.
- **`draftonly` leagues run no playoff bracket at all** and rank by total points through week 17 (`computeMflSeasonPlacementsByPoints`). **Never a guess** — `guessed` is hardcoded false, since every rank is a hard sum over fetched data, so existing guessed years self-correct with no migration. All-or-nothing per year. Needs its own larger budget (`HISTORY_MFL_DRAFTONLY_PER_LEAGUE_BUDGET`), since one year can take 18 requests.
- **The weekly-high payout is awarded fresh every week, not once a season.** This shipped wrong once. `results[].scoring` holds `weeklyHighs` (an array, one entry per week) and `seasonHigh` (a single record). The fetch window is a fixed **weeks 1–18**; the season *total* sums only weeks 1–17. Both cutoffs are asserted by the user, not inferred. `leagueStandings.pf` is not a shortcut — it folds in playoff scoring with no usable cutoff.
- **Every points value in `results[].scoring` is rounded to two decimals as it is written.** `computeSeasonScoringRecords` in `history.mjs`. These are sums of per-player scores, so binary floating point left trailing garbage on them — 36% of the committed weekly-high records read `151.29999999999998` rather than `151.3`, about 8KB of noise in a file every visitor downloads whole. Fantasy points are two-decimal quantities by construction (largest deviation measured: 5.7e-14), and rounding is also what lets a genuine tie compare as one. A `salaryAdjustments` value like `7.338` is NOT this and must not be rounded — that is real precision from MFL, not a summation artifact.
- **A franchise with no head-to-head game that week is a flat entry under `weeklyResults.franchise`, not inside `.matchup`.** Reading only `.matchup` silently dropped it — and on MNMx 2021 week 15 the dropped franchise held the true weekly high. `parseMflWeekScores`, pinned by `test-weekly-scores.mjs` with that exact fixture.
- **Division Winner is a third axis, for the best regular-season record, and costs nothing extra** — `mflDivisionWinner` reads index 0 of the `regularSeasonOrder` the placement backfill already has; ESPN reads `playoffSeed === 1`. Stamped as a sibling of `rank` in the same write. Unset for `draftonly`, which never fetches standings. Shipping it late needed an exception in `yearsNeedingHistoryBackfill` so confirmed years missing the field get re-fetched once; it can't loop, since a re-fetched year always sets it.
- **`startYear` is a manager-declared floor on how far back a league's history is theirs.** A franchise slot routinely predates the current manager, and a year before they joined is a correctly-computed answer about the wrong person — worse than missing data. `isBeforeStartYear` in `myffl.html` is the authoritative gate (it works against data backfilled before the field existed); the sync-side skip is a budget optimization. Blank excludes nothing.
- **The Results card averages `rank`, never the raw fraction** — a 12-team league's numbers must not swamp a 10-team league's. Rows render most-recent-first; leagues sort by best average finish.

### The page

- **A league's display name is `leagueDisplayName(league)`, never `league.name` directly.** `displayName || leagueName || name`: `displayName` is a manual override, `leagueName` is the live synced name, `name` is the static config fallback for an unreachable provider. Reading `league.name` alone renders whatever placeholder the config was created with — real ESPN leagues default to `ESPN League 1`, which shipped to production twice. Every card, popover, digest row and export goes through that one function. **Don't confuse `displayName` with `nickname`** — `nickname` only renders in the cramped quick-link toolbar (Admin tab: "Toolbar Label") and should be as short as possible; `displayName` ("Display Name") is the full name everywhere else.
- **The Admin tab's league card groups its fields by what each one affects, not by what shape it is.** Four `.admin-section` captions inside `renderAdminCard`'s field grid — League, Rosters & lineups, Naming, History & payouts. Two consequences for anything added later: **a new field goes in the section whose subsystem reads it** (which is why `startYear` sits with the payouts, not beside `season`), and **a caption is full-width via `grid-column: 1 / -1`, never `span N`** — a span conjures implicit columns at phone widths and brings back the sideways scroll this layout exists to remove. Same trap is why `.admin-field-mid` sits behind a `min-width: 40rem` media query while `.admin-field-wide` can use `1 / -1` unguarded.
- **The Admin tab tells you what's unsaved, in three places driven by one comparison.** `adminComparable`/`adminPendingChanges`, pinned by `test-admin-dirty.mjs`: a dot on an edited league, a count on both Save buttons, and a `beforeunload` guard armed only when something is outstanding. **The comparison must normalise before it compares** — the tab's text inputs hand back strings where the config stores real numbers, and a key the draft adds lands in a different position — so a raw `JSON.stringify` reports edits that save to a byte-identical file. It agrees with `mergeLeague`'s drop-the-empties rule on purpose. **Save is never disabled on a zero count**: a false negative here would be a Save button that refuses to save. Array order counts as its own change. Repainting goes through `refreshAdminDirtyState` rather than a re-render, which would throw focus away mid-word.
- **The collapsed league row shows what deviates from the default, never the default itself.** `Automatic rankings` was on all eighteen rows and said nothing; `Rules link` duplicated the 📝 icon beside it; a Toolbar Label equal to the Display Name it falls back to was doing nothing. **Scoring is the deliberate keeper** — its value really does differ per league and decides which FantasyPros list the ECR column reads, so only its annotation follows the rule (a pin says so, a detected format prints bare). **The money summary is always last and always present**, including `No dues or payouts set`, because "which leagues haven't had payouts entered" needed all eighteen cards opened; an em-dash marks a missing place, since unset reads as $0 on the Finances card. **The season chip in the head is the exception and stays always-on.**
- **The Leagues card's Save row is `position: sticky`; the Quick Links card's is not.** Eighteen collapsed leagues stand between a typo fixed near the top and the button that commits it. It's a modifier (`.admin-sticky-actions`) on `.lineup-editor-actions` rather than a change to that class, which the real lineup editor on the Rosters tab shares and where a pinned bar would be wrong; Quick Links is four rows tall, so its own copy of the row is already on screen next to what it saves.
- **A field the current `type` can't act on is hidden, never disabled and never cleared.** Commissioner contact is Salary Cap only (no other type produces a contract summary), Cutdown roster size is Dynasty only (`cutsNeededFor` is gated to that type), and Division winner is hidden on `draftonly` — those leagues rank by total points and never fetch head-to-head standings, so `divisionWinnerFranchiseId` is unset for them by construction and the payout could never be won. The value stays in the config when the type changes, and `api/save-leagues.js` validates all three on shape rather than on type, so switching Type to look at the dropdown can't silently discard something typed under the old one.
- **The header login control renders unconditionally.** It used to appear only when some league had a lineup editor. It must not go back to that: logging in is also what reveals the Admin tab, so gating the control on league data would mean switching lineups off everywhere hides the login box, which hides the tab you'd use to switch them back on.
- **The problems digest flags only what would change what you do.** `computeLeagueProblems`/`computeProblemsDigest`, pinned by `test-problems-digest.mjs`. **Its failure mode is noise, not error** — a strip opening on fourteen benign rows trains the eye to skip the one that matters. So: `scoringError`/`standingsError`/`lineupError` never appear (only the roster-level `error` does, since that one means the card is stale fallback); Questionable starters are not flagged; absence of lineup data reads as "not asked", never as an empty lineup; each starter yields at most one row, worst first; an unresolvable starter id is skipped silently. The required-starters check uses the *minimum* implied by `startingLineup`, so it can miss a one-short lineup but never flag a legal one. **When nothing is wrong the strip is absent entirely** — an all-clear banner would train the eye to skip the spot where real problems appear.
  - Roster-limit checks run *before* the lineup-data early return, deliberately: a salary-cap or draft-only league with no lineup pilot still has a roster that can go over its limits.
- **Cut planning is gated to Dynasty leagues and to `duringWeeks1Through17`** — its own boundary, deliberately narrower than the `nflInSeason` rule the Admin tab's note reuses. From Week 17's end through the Super Bowl (`duringIrClearingWindow`) IR players count against `cutdownRosterSize` too, and the Cut dropdown extends onto the IR table to match. **`cutdownRosterSize` is a per-league config value set by hand from the league's own rules** — MFL's `rosterLimits.size` describes what MFL will tolerate, not what the rules require, since commissioners routinely raise it for the offseason. Stored as a real JSON number, which is why `mergeLeague` converts the text input. Boundary math pinned by `test-cut-planning-window.mjs`.
  - The Cut control is a two-option dropdown, not a checkbox, because the lineup editor already spends a checkbox column on who's starting and a mis-click there is a real MFL write.
- **`submit-lineup.js` uses an allowlist, not a denylist.** It accepts a league only if `lineupPilot` is set *and* the provider is MFL or unset. Sleeper leagues can carry `lineupPilot: true` (their starters render read-only). A future read-only provider must fail closed by default. **Do not invert this.**
- **The Scoring tab's per-matchup detail drawer is live-only, and the snapshot deliberately carries nothing for it.** Each two-team pill opens a starter-by-starter breakdown of the two scores it shows. `appendMatchupDetail`/`pairStartersByPosition`, fed by the `players[]` array `fetchScoring`/`fetchEspnScoring`/`fetchSleeperScoring` already built for win probability. Pinned by `test-scoring-details.mjs`; per-provider shapes by `test-live-scoring-matchup.mjs` and `test-espn-sleeper-live-time.mjs`; points fields confirmed live by `probe-live-scoring-players.yml`.
  - **It costs zero extra per-league requests.** MFL's `liveScoring` already returns each franchise's whole roster (with a per-player `score`, present in the real capture `test-live-scoring-matchup.mjs`'s fixture is trimmed from), ESPN's `mRoster` view is already requested alongside `mScoreboard`, and Sleeper's `players_points` rides along on the matchup response. The one new cost is MFL names: `loadPlayerMap` is a **global** (not league-scoped) request, so `api/live-scoring.js` caches it at module level and fetches it once per poll *outside* the per-league fan-out. Never move it inside.
  - **`scripts/fetch-rosters.mjs` strips `players[]` before writing `data/rosters.json`** (`stripScoringPlayers`). That array is spent intermediate state by then — `attachWinProbabilities` has already reduced it to `winProb` — and the page has never read it from the snapshot. It is a page-load budget call: the id-only version was already 45KB of a then-1.6MB file every visitor downloads whole (617KB today, since `serializeSnapshot` stopped spending half of it on indentation), and the enriched version would roughly triple that to buy data the first live poll discards unread. So a drawer opened before the first poll answers says so rather than rendering an empty grid.
  - **A null `points` renders as a dash, never `0.00`.** "Hasn't played yet" and "played and scored nothing" are different facts, and every provider's points field is read defensively so an absent one degrades to the dash rather than a confident zero. A genuine `0` must survive as `0`. Same reasoning as `available: null` vs `[]` on the Analytics cards.
  - **Rows align by `position`, not by lineup slot** — ESPN's own scoreboard aligns by slot, and this deliberately can't: MFL supplies no slot label at all, and this project knows only two of ESPN's `lineupSlotId` values (bench and IR). Position is the one axis all three providers agree on. Each position group gets as many rows as the *deeper* side has, padding the shallower one, so a flex difference shows as an extra player opposite a gap instead of silently shifting every row below it out of alignment. Order within a group is the provider's own — re-sorting by points would pair "their best WR" against "your best WR", a matchup no lineup actually set.
  - **Login-gated, and skipped for a lone team.** It's every franchise's current lineup, a step past the team-level scores the pill itself shows, so it follows the same rule as the ECR column and the lineup checkboxes. A bye (or an odd team count) gets no drawer — there's no opposing column to lay a lineup against.
  - **A starter's score is a button opening a stat breakdown when `providers.mjs` found one, plain text otherwise.** `espnStatBreakdown`/`sleeperStatBreakdown`/`mflStatBreakdownFromBoxscore`, shown by `scoringDetailPopover`, pinned by `test-stat-breakdown.mjs` and `test-mfl-boxscore-breakdown.mjs`. ESPN's is free off the `view=mRoster` response already fetched. Sleeper's needs one new global request per poll (`fetchSleeperWeekStats`, cached like `loadSleeperPlayerMap`) crossed against the league's own `scoring_settings`, so a category earns a row only when the player recorded it *and* this league prices it. **Categories that are community-documented rather than confirmed against one of this project's own leagues are labelled as such, and kicking/team-defense are left out of the label map entirely rather than guessed at.**
    - **MFL's own API has no source for this at all, and it isn't a gap to close — it's the platform's own contractual limit.** MFL's Developers Program terms (the two PDFs in `mfl/`, see `mfl/README.md`) state outright that raw NFL player stats "can not and will not under any circumstance" be exposed, per their stats licensing agreement. `probe-live-scoring-players.yml` confirms this from the API side too, across every endpoint that could plausibly carry it: `updatedStats` (`TYPE=liveScoring`) reads as an empty string on every starter regardless of score; `TYPE=weeklyResults` carries only `id`/`status`; `TYPE=playerScores&RULES=1` carries only one recalculated total, no per-rule breakdown. **Don't spend another probe run chasing this on MFL — read `mfl/README.md` first.**
    - **What ships instead for MFL is built from a different provider entirely, so the ToS restriction above doesn't apply.** `mflStatBreakdownFromBoxscore` joins ESPN's PUBLIC site API (`fetchEspnBoxscore` — the same unauthenticated host `fetchNflGames` reads, never their fantasy API) against this league's own MFL rules (`fetchMflSkillPositionRates`, `TYPE=rules`). `addBoxscoreToStatIndex` folds every NFL game in play into one name-keyed index, GLOBAL and built once per poll, then joined per-league against a per-POSITION rate map (a TE-premium league prices a TE's catch differently than a WR's). **Scoped to skill-position offense only** — same boundary as the ESPN/Sleeper breakdowns, since no confident join exists for kicking or team defense. **Deliberately not reconciled against the real MFL score**: a probe found ESPN's own passing-yards line disagreeing with its team total by 10 yards, so an exact match isn't guaranteed even with every rate right. A boxscore is cached hard once `'post'`, re-fetched only while `'in'`.
  - **Names are abbreviated to a first initial; a team defense is cut to its mascot instead.** `abbreviatePlayerName`/`isTeamDefense`, pinned by `test-scoring-details.mjs`. A defense has no first name to cut, so it drops its city ("Baltimore Ravens" -> "Ravens") and lets `appendTeamSuffix`'s code carry it ("Ravens BAL"). **The cut is always the LAST word, never the first** — nine franchises have a two-word city and every current mascot is one word. ESPN's own "Eagles D/ST" has already dropped the city, so the trailing `D/ST` is stripped first rather than kept as the mascot. A given name that is already initials ("A.J. Brown") is left alone.
  - **The per-player game line ("@PIT Sun 12:00 PM") comes off the same NFL scoreboard the win-probability clocks already use.** `fetchNflGames` in `providers.mjs` is the richer read of that one request; `gameClocksFromGames` projects the clocks back out of it, so `fetchNflGameClocks` is now a thin wrapper and the line costs no extra request. `@` means away, matching ESPN's own convention. Once a game is underway the scoreboard's own `shortDetail` ("4:35 - 1st" live, "Final" once over — real shapes, confirmed by `probe-live-scoring-players.yml`) replaces the kickoff time, used verbatim rather than rebuilt from period/clock — which would mean reinventing how it words halftime and overtime.
    - **The kickoff crosses the wire as an ISO string and is formatted in the browser, never on the server.** Vercel runs in UTC, so any "Sun 12:00 PM" built there is wrong for whoever is reading it.
    - **The schedule rides once per response as a top-level `games` map, not stamped onto each of the ~1600 starters a poll covers.** The page joins it by the `team` already on every player.
    - **That map is keyed under every provider's spelling of each team** (`NFL_TEAM_ALIASES`). MFL pads its codes — `GBP`/`JAC`/`KCC`/`LVR`/`NEP`/`NOS`/`SFO`/`TBB` where the scoreboard says `GB`/`JAX`/`KC`/`LV`/`NE`/`NO`/`SF`/`TB` — so a map keyed only as the scoreboard published it would silently give no game line to every player on eight teams. Aliasing server-side rather than normalizing the player's `team` is deliberate twice over: that field is *displayed* (the `appendTeamSuffix` rule that MFL's `LVR` is meant to sit beside Sleeper's `LV`), and it leaves no alias table duplicated across the sync boundary to drift. **There is deliberately no `LA` alias** — it has meant both Rams and Chargers, and a wrong join puts a player in the wrong game, which reads as perfectly plausible.
  - **The drawer's row widths are measured, not guessed.** A name column gets ~103px at phone width against the ~97px the longest game line needs, which is why the middle columns are as tight as they are — every rem spent there comes straight out of the two name tracks. Their `min-width` is a floor on an `auto` grid track, so an unusual score still grows the column. The game line's time is joined with **non-breaking spaces** so its only breakable space is the one after the opponent: without that, the few pixels the widest combination overruns by on a desktop-width card strand a lone "PM" on its own line.
  - **Open state persists in `localStorage`, and that is load-bearing, not a convenience.** `rerenderScoringCards` tears down and rebuilds every Scoring card on each ~30s poll, so a drawer held only in the DOM would snap shut under the reader twice a minute. It stores *open* rather than *collapsed* — the opposite polarity from every other collapse on this page, all of which default open — so absence means closed. The key includes the matchup's own franchise ids, which is what makes it invalidate by itself when next week's pairings change. The body is filled lazily, since every league's card is built on every poll and only the sub-tabs' filter hides them.
  - **A second, nested "Show bench" toggle inside this drawer's own body opens the same grid built from `t.bench[]`** — everyone rostered but not currently starting. `appendBenchDetail` in `myffl.html`, reusing `pairStartersByPosition`/`appendDetailSide` wholesale rather than duplicating them, since a bench player renders no differently from a starter once you have one in hand. Its own open state is a second `localStorage` key (the starter drawer's own key plus a `:bench` suffix), independent of the starter drawer's — closing one leaves the other's key alone — and it never carries the starter toggle's `scoring-detail-live` gold flag: a bench player's own game being live has no bearing on this matchup's score, unlike a starter's. Pinned by `test-scoring-details.mjs`.
    - **All three providers get `bench` for free off the same read `players` already comes from — MFL included, after two wrong turns.** `espnTeamLiveStarters`/`sleeperTeamLiveStarters` just bucket a response that already carries the whole roster; MFL's plain `TYPE=liveScoring` does not (two probe runs found it carrying only the 9 starters, zero nonstarters), so the first version filtered that same list for `status === 'nonstarter'` anyway and shipped a drawer that said "waiting on the next live update" forever. **The fix is `DETAILS=1`**: `TYPE=liveScoring&DETAILS=1` returns nonstarters too, each carrying a real `score` — confirmed against real data (`probe-live-scoring-players.mjs` RUN 9: 148 of 148 nonstarter entries with a non-null score) — so `mflLiveStarters`/`mflNonstarterBench` in `providers.mjs` now split ONE response by `status` instead of making a second request. **Don't reintroduce a nonstarter filter over the plain (no-`DETAILS`) response — it will silently do nothing.**
    - **A second approach — joining `TYPE=rosters` (identity) against `TYPE=playerScores&RULES=1` (points), two extra per-league requests every poll a bench drawer was open — shipped, then was reverted twice.** First for a week mismatch (`playerScores` was asked for `api/live-scoring.js`'s own Sleeper-resolved "current week" rather than this response's own `live.week`, so it silently returned nothing for the wrong week). Then, after re-pointing it at the right week, for something worse: `probe-live-scoring-players.mjs` RUN 10 found `playerScores&RULES=1` itself unreliable for nonstarters regardless of week — of 137 ids present in both sources, only 8 agreed and 129 disagreed, every disagreement `playerScores` confidently reporting `0` for a player `DETAILS=1` showed a real, often large score. **Never resurrect `fetchMflLeagueRosterIds`/`fetchMflWeekPlayerScores`/`playerScores&RULES=1` for bench points** — the full history is in `mfl/README.md`'s `DETAILS=1` bullet and `test-mfl-bench.mjs`'s own header comment.
    - **Bench is therefore never gated, for any provider** — same posture as starters (`players`), which were never gated either since the Now Playing card reads every league's own `players` each poll. The two gated MFL requests above are gone; nothing replaced them, since `DETAILS=1` costs nothing extra.
    - **The poll cadence backs off when nothing is live, and pauses outright while the browser tab is backgrounded — for every provider, not just MFL.** `nextLiveScoringDelayMs` reads the LAST poll's `liveGames` for any game in state `'in'`: found one, `LIVE_SCORING_POLL_MS` (30s); found none, `LIVE_SCORING_IDLE_POLL_MS` (2 minutes, a starting point rather than a measured one). That made `liveScoringTimer` a self-rescheduling `setTimeout` chain (`scheduleLiveScoringPoll`) rather than a `setInterval`, gated on `liveScoringPollingEnabled` so a poll in flight when the reader leaves doesn't restart the chain. A dedicated `visibilitychange` listener — separate from the one flushing a pending plan push — calls the same start/stop pair `switchToView` uses, gated on `currentView === 'scoring'`.
- **The Scoring tab excludes `draftonly` leagues entirely**, same as Top Available does on Analytics and for the same reason: one draft, no head-to-head matchup, so there is no live scoring to mean anything by. `hasLiveScoring` in `api/live-scoring.js` drops them before any MFL request is spent — confirmed in production that every draftonly MFL league returned "No live scoring available yet" on every poll, spending a names + liveScoring pair each time, inside the same cold-start burst that trips the rate limit for every other league. `myffl.html`'s two Scoring-card render sites exclude them the same way. The Draft Only pill needs no separate removal: it is derived from the `data-league-type` values actually present.
- **Each provider's own "current week" signal is trusted blind, and that's a known gap, not an oversight.** ESPN's `currentMatchupPeriod` (`fetchEspnScoring`) and Sleeper's `/state/nfl` week (`fetchSleeperScoring`, via `resolveNflWeek`) both advance the moment the *previous* week is fully scored, regardless of whether the new week's games have started — confirmed live 2026-09-16: ESPN read `currentMatchupPeriod: 2` with every player at 0 while MFL's own un-parameterized `TYPE=liveScoring` call was still returning week 1's final scores days later. Holding ESPN/Sleeper on the prior week until kickoff was considered and declined — `fetchEspnScoring`'s own comment has the three real costs (unproven feasibility of re-reading a past scoring period, a freshness-vs-staleness tradeoff, and a cold-start problem that would make a naive cache silently stop working in exactly the window it's needed) and what a revisit should check first.
- **The NFL tab (Now Playing, Matchups, Depth Charts) is real NFL data and is ungated** — `VIEW_LABELS`. Pinned by `test-nfl-tab.mjs`. Depth Charts is no longer its own tab: `renderDepthChartCards` nests all 32 team cards in one collapsible wrapper, appended after the other two (`renderGrid` calls `renderNflCards` first for that reason). Rules that are silent when broken:
  - **The wrapper carries `data-view="nfl"` but `updateVisibility`'s generic per-card branches must skip it** (`data-depth-charts-wrap`) — each team card is a full `.card` too, so matching both double-processes every one. Its own visibility is decided after that loop, from whether any nested team card survived.
  - **The division pills and the search box live inside that card**, not the page-level bar (`renderDepthChartSubTabs`, `relocateSearchControls`). The search box is the SAME `.search-wrap` node every other view uses, re-parented rather than copied — a copy would strand the real listeners. **`renderGrid()` must rescue it back to `.controls` before its own `innerHTML` wipe**, since it may be living inside the card about to be destroyed.
  - **`buildNflGamesList` must collapse `liveGames` back to one row per game**, keyed by event id and paired by `isHome`. That map holds every alias of a team (`nflTeamKeys`) pointing at one entry, so getting this wrong silently double-lists any game with an aliased team. Both cards read that same map off `gamesOnly=1` — never a third scoreboard fetch.
  - Now Playing is every game kicking off on today's local calendar date, any state (`isGameToday` — compares local date, never UTC); Matchups is every state, every day this week. `formatGameWhen` shows kickoff time before a game starts and the scoreboard's own status after, and **a score never renders pre-kickoff** — ESPN's `0` there is a placeholder.
  - **The Stats drawer is player-level only** (`appendNflBoxscoreToggle` builds the toggle, `nflBoxscorePlayerLines` the lines, off `ESPN_BOXSCORE_TO_MFL_EVENT`'s own keys so the two can't scope-drift; no team totals — that shape has never been read). Fetched only for an open drawer via `boxscoreGames` (an ESPN request per game, worth gating unlike the Scoring tab's own bench, which now costs nothing extra), sharing `getEspnBoxscore`'s cache. **`fillNflBoxscoreBody` keeps three states apart** — pre-kickoff, not-answered-yet, and answered-with-nothing — and "not asked" must never read as "nothing happened". Open state persists per event id (`NFL_BOXSCORE_NS`, stores OPEN) because `rerenderNflCards` rebuilds every card each poll; its own poll loop (`startNflPolling`/`refreshNflScoreboard`) stays separate from the Scoring tab's.
  - **`BOXSCORE_EXCLUDED_LABELS` drops columns by ESPN's label text, not key name** (two different keys share the label `LONG`), and stats are positional — dropping a column re-indexes every remaining value.
  - **A rostered player's row is purple with an `(N)` own-link, and it is login-gated** unlike the rest of this tab. `nflBoxscoreOwnership()` calls `buildDepthChartOwnership` outright so the two tabs can't disagree about "owned", and returns an empty `Map` — never partial — when logged out.
- **Click-to-sort is one implementation, `makeTableSort`, shared by the three tables that have it.** Three rules, each silent when broken: the card's own order is a fourth state (natural → reverse → back to default), ties fall back to that order, and `missingLast` holds a missing value at the bottom in **both** directions. Sorting is per card and per visit, never persisted. Pinned by `test-analytics-sort.mjs`, `test-power-rank.mjs` and `test-team-needs.mjs`, each driving a DOM stub since the state lives in a closure.
- **Popovers are one implementation, `makePopover`, with nine instances.** Each keeps its own element and `.<name>-popover` class hook; only the show/hide/anchor/dismiss machinery is shared, and content stays at the call site. Two shapes: the eight read-only ones pass `{title, rows}`; the Tasks card's Edit Task popover passes a `(popoverEl) => {}` builder, since a form isn't a list of read-only rows. **A popover must be positioned before it is shown** — a `position: fixed` element with no top/left falls back to its static position at the end of `<body>`, lengthens the page, and fires the scroll its own dismiss handler acts on. That bug made the first click on a salary link do nothing. Deliberate dismissal is never suppressed; only the incidental kind is.
- Every Analytics card carries the same one-line `Across N leagues` subtitle and nothing else. A group whose number looks short is explained here rather than on screen. The one exception is the conditional preseason-projections note, which is an alert rather than a standing explanation.

### Auth, plans and writes

- **Auth is stateless and password-free after login.** `SITE_PASSWORD` gates `api/login.js`, which returns an HMAC-signed 30-day token (`api/lib/auth.mjs`) replayed as a Bearer token on writes. There is no session store. MFL credentials live only on the server and are never sent to the browser.
- **Planning values sync through `api/plans.js`; everything else the page stores is device-local.** Contract lengths, salaries, cuts and result overrides round-trip through Upstash Redis over its REST API with plain `fetch`, so the no-dependency property holds. It must be Upstash rather than the marketplace's "Redis" entry, which hands back a `redis://` string needing a client library. `resolveStore` accepts either credential naming. `myfflView`/`myfflLeagueType` and the auth token stay device-local.
- **A merge is a union, so it cannot express a deletion — that is the axis the whole design turns on.** A device merges exactly once (its introduction to the store) and reads with a plain GET every load after, recording that in `myfflPlanSynced`. Merging on *every* load makes a cleared plan impossible to propagate, and the device that made the clear looks correct the whole time, which is why a single-device test cannot see it. `localStorage` is the store's cache plus `myfflPlanPending`, a persisted log where `''` is a tombstone, laid back over every answer the store gives. `doLogout` drops the pending log but keeps `myfflPlanSynced`. Pinned by `test-plans.mjs` and `test-plan-sync.mjs`, the latter driving two page instances against one store — the two-device cases are the only ones that can see this class of bug.
- **The login gate is an intended access measure on Analytics, Admin, the ECR column and the lineup checkboxes. Keep it there, and don't weaken it.** `isLoggedIn()` decides which cards render, and hiding those from a logged-out viewer is the point, not incidental tidiness. Every one of those gates is deliberate; adding a card that reads roster, ranking, finance or lineup data means gating it the same way. **History is the deliberate exception**, ungated since it never bought real privacy to begin with — see its own entry above.
- **Know its limit, though, and don't mistake it for a hard boundary.** It deters the realistic threat — a league mate opening the URL — and nobody willing to look further, because the same data sits in `config/leagues.json` and `data/rosters.json`, committed to a public repo and served openly. Accepted deliberately. Two consequences pulling in opposite directions on purpose: **don't re-file the public-file part as a bug or move that data behind `api/` on privacy grounds**, and equally **don't put anything genuinely sensitive behind this gate alone**.
- **Plans are the one exception, and the reason for it is different.** They are not kept in the repo the way `config/leagues.json` is: a plan is strategy about leagues other people play in, so it goes to Upstash rather than into a public file. That distinction — plans out of the repo, everything else in it — is the whole of the privacy model.

## Verifying changes

Network egress from a cloud sandbox is restricted: **`myfantasyleague.com` and `api.sleeper.app` are unreachable here, though `api.github.com` is.** You therefore cannot run `node scripts/fetch-rosters.mjs` end-to-end locally, which is exactly why the manual workflows exist. Verify against real providers by dispatching `test-set-lineup.yml` or `test-login-endpoint.yml` from GitHub Actions, or by triggering `sync-fantasy-rosters.yml`.

What *does* work locally:

```bash
node --check scripts/fetch-rosters.mjs        # syntax
for f in scripts/test-*.mjs; do node "$f"; done   # all but test-set-lineup (network write)
python3 -m http.server 8000                   # then open /myffl.html
```

Serve over HTTP rather than opening the file directly — `myffl.html` fetches `data/rosters.json` with a relative URL, which fails under `file://`. The committed `data/rosters.json` is real synced data, so the page renders fully offline; pure rendering changes can be checked this way without any provider access.

To exercise the logged-in UI (the lineup editors and the whole Admin tab) without the site password or any network access, set the token the page looks for before loading it — `isLoggedIn()` only checks that one exists:

```js
localStorage.setItem('mflAuthToken', 'anything');
```

Everything renders and behaves normally; only the calls that actually reach Vercel will fail. This is the practical way to drive the Admin tab in a headless browser. Chromium is available for that; install Playwright with `--no-save` and remove `node_modules` afterwards, since the repo is dependency-free by design. (`.gitignore` covers `node_modules/` so a forgotten cleanup can't be committed, but the repo is still meant to have none.)

## Working through the Tasks card

The manager tracks bugs and site-enhancement ideas for Claude to act on in the Tasks card (`renderTasksCard` in `myffl.html`) rather than describing them fresh in every conversation. Two rules when asked to work through it:

- **Pull the task list with `scripts/fetch-tasks.mjs` instead of asking the user to retype or paste it.** It reads the same shared store the page does (`api/plans.js`) and needs `SITE_PASSWORD` in the environment — see the script's own header for why it never filters by category itself. When the sandbox's network egress doesn't allow `shamrock84-github-io.vercel.app` (the usual case — see "Verifying changes"), dispatch `fetch-tasks.yml` instead: it runs the same script on a GitHub Actions runner using a `SITE_PASSWORD` repo secret and prints the result to the job log.
- **Only act on tasks categorized `Bugs` or `Site Enhancement`.** The card is the manager's general-purpose task list, not a Claude inbox — other categories are there for reasons that have nothing to do with this codebase, and picking one up unasked would mean acting on an instruction the user never gave this session.
- **Once a task's code has merged, mark it done with `scripts/mark-tasks-done.mjs` (or its `mark-tasks-done.yml` counterpart) rather than leaving the card to say otherwise.** It writes to the same store, matched by a task's exact `text` — there's no id to pass from a shell or a workflow input. It has to POST with `mode: 'replace'`: `api/plans.js`'s default `merge` mode has the already-`stored` copy win on any key that exists on both sides (see `mergeTasks`), which would silently no-op an update to a task the store already has. `replace` mode replaces the *whole* plans document, so the script fetches the current one first and changes only the matched tasks' `done`/`completedAt`, round-tripping every other task and every other plan kind (`contractPlans`/`salaryPlans`/`cutPlans`/`resultOverrides`) unchanged.

## Front-end conventions

`myffl.html` is a single ~14,500-line file: vanilla JS, no framework, no bundler, styles and markup and logic all inline. Match the existing idiom rather than introducing a framework or a build step — the no-toolchain property is what lets GitHub Pages serve this directly.

Rendering is a set of `renderCard` / `renderStandingsCard` / `renderScoringCard` / `renderAnalyticsCard` / `renderInjuryExposureCard` / `renderTopAvailableCard` / `renderPowerRankCard` / `renderTeamNeedsCard` / `renderResultsCard` / `renderFinancesCard` functions, driven by a tab and sub-tab system built from the league list at runtime. The sub-tab strip is derived at render time from the `data-league-type` of the cards actually present, so a group with no leagues simply doesn't get a tab. Tabs themselves are derived from the cards that exist, which is why logging out removes the Analytics and Admin tabs with no extra work — History renders (and its tab shows) either way.

Shared machinery, and what is deliberately *not* shared:

- All three Analytics cards share `appendAnalyticsTable` — one paginated table behind a handful of flags rather than three copies free to drift.
- `makeTableSort` and `makePopover` hold the sort and popover machinery for every card that has one. Content stays at the call site.
- The popovers keep separate *instances* — they show unrelated content from unrelated tables — but share their CSS through `.popover`, with `.<name>-popover` left as a per-instance hook.
- Two features sharing a visual form otherwise get separate classes throughout this file (`.results-*` vs `.finances-*`), since there is nothing to gain from coupling them beyond a shape they duplicate on purpose.
- A clickable number that opens a popover is an established idiom: `.salary-link`, `.needs-link`, `.starters-link`, `.finances-link`.

Colour conventions worth knowing: `--accent` purple means "notable" wherever it appears on a player line; gold marks a taxi-squad player, using `--gold-chip-text` (the token for gold text on the card background) rather than `--gold-text` (the dark foreground meant *for* a bright gold chip, which is nearly invisible in dark mode). IR red (`--ir-text`) means "needs a look" — a planned cut, an estimated finish.
