# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A personal static site (`melbostads.com`) whose only real application is **`myffl.html`** — a fantasy football dashboard aggregating ~18 leagues across MyFantasyLeague (MFL), ESPN, and Sleeper. Every other page is a stub, an iframe wrapper around a Google Sheet, or a redirect. `myffl_v1.html` is the retired predecessor, kept for reference.

There is **no build step, no test framework, no linter, and no dependencies**. `package.json` exists only to set `"type": "module"` for the `.mjs`/`.js` files under `scripts/` and `api/`. Do not add `npm test`/`npm run build` scripts expecting them to be wired to anything.

## Two deployment targets, one repository

This is the single most important thing to understand before changing anything:

| Path | Deploys to | Serving |
| --- | --- | --- |
| `*.html`, `data/`, images | GitHub Pages | `melbostads.com` (see `CNAME`) |
| `api/*.js` | Vercel | `shamrock84-github-io.vercel.app` |

`myffl.html` is served from Pages but calls Vercel by **absolute URL** (constants near the top of its script block). That cross-origin hop is why every file in `api/` carries an identical `ALLOWED_ORIGINS` allowlist — add a new endpoint and you must copy that CORS preamble, or the browser blocks it.

Consequences that bite:

- **Secrets exist in two independent places.** GitHub Actions secrets power the scheduled sync; Vercel project environment variables power the API functions. They are not shared. Adding a credential means setting it in both, or deciding which half needs it. (The Upstash Redis credentials for `api/plans.js` are Vercel-only — the sync never touches plans.)
- **`vercel.json`'s `ignoreCommand` skips the Vercel build** unless the commit touched `api/`, `scripts/lib/providers.mjs`, or `config/leagues.json`. If you make `api/` import a *new* shared module (say `scripts/lib/fantasypros.mjs`, which today only the sync uses), you **must** add that path to `ignoreCommand` or Vercel will silently skip deploys that need to ship.

## Two data paths, deliberately separate

**Slow path — snapshot, committed to the repo.** `sync-mfl-rosters.yml` runs every 4 hours (and on demand), executes `scripts/fetch-rosters.mjs`, and commits the result to `data/rosters.json`. This carries rosters, standings, scoring, lineups, the FantasyPros ranking pools and each league's free agents. `myffl.html` fetches that file directly with a cache-buster — the whole file, on every page load, which is the budget any new field is spending.

**Fast path — live, never written down.** `api/live-scoring.js` is polled roughly every 30s while the Scoring tab is open. It only answers requests; it writes nothing. It keeps a module-level cache (MFL cookie ~20 min, franchise names ~1 hour) that survives warm invocations and resets on cold start.

Both paths import the same fetch logic from **`scripts/lib/providers.mjs`** (~37k, the largest source file here). `fetch-rosters.mjs` is orchestration only — provider quirks belong in `providers.mjs`.

`api/trigger-sync.js` bridges the two: the page's "Last synced" link dispatches the sync workflow via a repo-scoped PAT, behind a 2-minute cooldown so the button can't be used to hammer MFL/ESPN.

## `config/leagues.json` is the control plane

Adding, removing, or reclassifying a league is a config edit, never a code edit — and usually not even a repo edit: the **Admin tab** in `myffl.html`, visible once logged in, edits this file through `api/save-leagues.js` and commits it. Prefer pointing the user at that tab over hand-editing on their behalf.

That endpoint is the only write path in the project that **bypasses pull requests entirely and commits straight to `main`**, so the syntax-check workflow never sees it. Its server-side validation is therefore the only guardrail, and `scripts/test-save-leagues.mjs` is what keeps that validation honest — extend the tests alongside any change to the schema. Two properties there are load-bearing and easy to break: `mergeLeague` passes through fields it doesn't recognise (without it, any field added to the config later would be silently erased the first time someone pressed Save), and `serialize` keeps one league per line (so an Admin-tab commit is reviewable as a one-line diff rather than a whole-file reshuffle).

The file's own `_readme` array is the authoritative schema — **read it before touching anything league-shaped, and update it when you change the schema.** It documents `provider`, `type`, `lineupPilot`, `tags`, `rankingType`, `scoring`, `season`, `commishContact`, and the non-obvious rules behind them (for instance: salary-cap leagues intentionally use DRAFT rankings rather than DYNASTY). Array order is display order across every tab.

`type` carries one behaviour beyond display: `salarycap` is what renders the Salary/Yrs columns and the cap summary, and what makes the sync fetch the cap and salary adjustments at all. It used to be a separate `format: 'auction'` field, which always agreed exactly with the type; that field is retired and `api/save-leagues.js` strips it on save via `RETIRED_KEYS`, which is the mechanism for removing any config field permanently (the unknown-key passthrough would otherwise preserve it forever). The `bestball` type was likewise renamed to `draftonly`, since Best Ball is a scoring system that several salary-cap leagues use and now lives only in `tags`.

Three providers are supported: `mfl` (the default when `provider` is omitted), `espn`, and `sleeper`. Provider selection is a three-way ternary repeated at each stage of `fetch-rosters.mjs` (roster, standings, scoring, lineup), so adding a fourth means updating `providers.mjs` *and* each of those call sites.

## Invariants worth preserving

- **A league's display name is `leagueDisplayName(league)`, never `league.name` directly.** `league.leagueName` is the live name synced from the provider; `league.name` is `config/leagues.json`'s static fallback, meant only for a league the provider can't currently be reached for (see that file's `_readme`). Reading `league.name` on its own renders whatever generic placeholder the config happened to be created with — real ESPN leagues in this config default to names like `ESPN League 1` — which shipped to production twice on the Results and Finances cards before being caught. `leagueDisplayName` in `myffl.html` is the one place this fallback is implemented; every card, popover, digest row, or export that names a league should call it rather than inlining `league.leagueName || league.name` again.
- **The sync degrades, it never fails.** `fetch-rosters.mjs` wraps every league in try/catch and falls back to the previous `data/rosters.json` entry (`previousById`), recording an `error` field the page renders. One dead league must never blank out the other seventeen. FantasyPros rankings are layered on last and are likewise never allowed to fail the run — with no `FANTASYPROS_API_KEY` the ECR column simply goes blank. The same enrichment carries each player's FantasyPros profile URL (`ecr.url`), which is what makes a name on the page a link; it is read off the rankings response by `playerPageUrl` and **never built from the player's name** — the site disambiguates two players who share one (`josh-allen.php` is the quarterback, `josh-allen-lb.php` the linebacker) and `normalizePlayerName` deliberately drops the suffixes some slugs keep, so a constructed slug would quietly link to the wrong person. No URL means no link, which is also what every roster synced before this shipped renders. `probe-fantasypros-player-url.yml` is what confirms the field against the real API.
- **The Analytics tab reads rosters two ways, and only one of them is our own roster.** Player Exposure and Injury Exposure look at what we hold; Top Available looks at the *rankings* and asks which of those players nobody in a league has, which needs two things the rosters alone can't supply. First, `rankingPools` at the top level of `data/rosters.json` — the top `RANKING_POOL_SIZE` (250) of each FantasyPros list the sync actually used, kept whole rather than only as the ECR numbers stamped onto our own players, keyed by `rankingPoolKey` (`type|scoring|position`) so a dozen leagues drawing on the same two or three lists store them once. That number is the card's *reach*, not a scroll depth: a twelve-team dynasty league has 300-plus players spoken for, so at the original 150 the top of the list was entirely rostered and the wire read as empty when it was really just unexamined. Depth is paid for by every visitor on every page load, not once at sync time — roughly 40KB per pool at 250, typically three pools — which is why each entry carries only name/position/team/rank/url and the url is stored **site-relative**, the origin repeated 750 times being 40KB of nothing. `team` is the one field there the page cannot derive: a row on that card is by definition a player no roster of ours holds, so there is no roster copy to read an NFL team off, and at three bytes a player it is about 3KB across the three pools — the cost worth watching in this structure is depth, not width. It is normalised to `'FA'` when FantasyPros carries no team, matching what every provider in `providers.mjs` already writes onto a rostered player, so an *absent* `team` means only "synced before this shipped" and the page can print nothing there rather than claiming free agency it hasn't been told about (`scripts/test-ranking-pool.mjs` pins that it is never blank). **Kickers and defenses are dropped from the pool** (`WIRE_EXCLUDED_POSITIONS`, filtered *before* the truncation so all 250 are claimable players, and pinned by `scripts/test-ranking-pool.mjs`): nobody rosters them in a keeper league, so they are structurally always free and were 38% of the Dynasty/Salary Cap card. The objection that this hides the best available defense in a league that starts one doesn't bite, and the numbers are why — `DRAFT|PPR|ALL` carried 16 DST + 15 K and neither of its leagues starts one, `DYNASTY|PPR|ALL` serves the three leagues that start `1 Def` and carried two defenses and no kickers, and `DRAFT|HALF|OP` is offense-only. This filters the pool only, never `buildRankingIndex` — a kicker on your own roster still gets his ECR on the roster card, which is the easy mistake and would blank a column rather than shorten a list. Second, `available` per league: the pool players nobody in that league rosters. Working that out needs a league-wide roster read, and **where that read happens is load-bearing.** It is its own pass in `fetch-rosters.mjs`, after standings, scoring and lineups, per-league best-effort: `fetchMflRosteredNames` / `fetchEspnRosteredNames`. It began as a widening of `fetchLeagueRoster`'s `TYPE=rosters` call from `FRANCHISE=` to the whole league, which looked free — same endpoint, same request count — and wasn't: the league-wide export is a far heavier response, and the first sync to try it spent enough of MFL's rate limit that three scoring fetches and a lineup fetch behind it came back 429 (37s and clean before, 87s and four 429s after). Nothing was lost, since those fall back to the previous sync, but the ordering was backwards. Availability is the least important thing here, so it goes last and it is what gives way under a rate limit. **Don't fold it back into the roster fetch.** Sleeper is exempt from the pass entirely — `sleeperTeamNames` already had every roster in hand, at no extra request — and ESPN needs its own call regardless, since the roster fetch pins `rosterForTeamId` to get its entries populated at all. **The pass also runs once a day, not once a sync**, since even last it cost sixteen heavy exports and took four 429s of its own: `availabilityIsFresh` keeps a list under 20 hours old, so five runs in six skip it and cost what the sync cost before any of this existed. Twenty and not twenty-four is the load-bearing part — with a four-hourly cron a 24h rule is missed by seconds by the run a day later and satisfied by the next, walking the daily read four hours further into the day each day. A league that has never been read, or whose last read failed (`available: null`), is due immediately rather than waiting out a day, which is what stops one 429 from freezing a league's wire; `availableAt` is therefore stamped only on a list actually rebuilt this run, never on one carried forward. `refresh_availability` on the workflow's manual dispatch forces the read. **A league whose draft hasn't finished is skipped entirely**, its `available` cleared rather than carried forward: mid-draft every unpicked player reads as a free agent, which is true at the instant it was read and useless, since they aren't claimable off a wire — they're about to be drafted. `draftStatusFromResults` reads MFL's `TYPE=draftResults`, where an unmade pick comes back with an empty `player` (August Judgment Day: 216 picks, 65 made; four settled leagues returned every pick filled), verified by `probe-draft-status.yml` and pinned by `scripts/test-draft-status.mjs`. Three things are load-bearing there: reading only a *finished* league suggests unmade picks aren't listed at all, and a detector built on that would never fire; zero picks means "couldn't tell" and must never be treated as unfinished, or a league whose draft MFL doesn't carry vanishes permanently on a guess; and every draft unit must be finished, since a league can run one per division. The check runs *before* the roster read, so a drafting league costs less rather than more, and clearing `available` puts it back on the every-sync retry path so a finished draft is picked up within four hours. It also runs **ahead of the once-a-day freshness rule, on every sync** — behind it, a league that started drafting just after its daily read went on serving a stale pre-draft wire for up to twenty hours, which is exactly what happened the first time and was only caught by a manual refresh. That costs nothing in the steady state because **a finished draft never unfinishes**: `draftIsSettled` skips any league already recorded `draftInProgress: false` *against the same season*, so by mid-season the check is free and in August it is one request a sync. Keyed to the season for the same reason `scoringDetected` is — a rolled-over league has a new draft to run, and treating last season's answer as current would hide a live draft for a year. `TYPE=league` cannot answer this — its `draftTimer`/`draft_kind`/`draftLimitHours` are settings, and two long-finished leagues both report `draftTimer: "ONS"` — which is the only reason this costs a request at all. Sleeper answers free on the league object the roster fetch already has (`pre_draft`/`drafting` are the unfinished states); ESPN is exempt and unverified. The cost of caching the *names* rather than the rosters they came from is a one-day lag at the pool's edge — a carried-forward player who has since left the top 150 stops rendering, and one who just entered it isn't known to be available yet. Top Available used to date itself in its subtitle for exactly that reason; that line is gone, along with the two exclusion notes below it, on the grounds that a standing explanation of a known lag costs more room every visit than it buys. **All three Analytics cards now carry the same one-line subtitle, `Across N leagues`, and nothing else** — Top Available's count is simply the narrower denominator described below, and a group whose number looks short is explained here rather than on screen. Caching the rosters instead would mean persisting every league's full rostered-name list, which is the ~150KB this whole design avoids. **A league that hasn't rolled over yet is excluded too, but from the page rather than the sync** — `awaitingRollover` in `myffl.html`, comparing the league's own `season` against the file's top-level `year`. The difference from the mid-draft case is why it lives on the other side: a drafting league's `available` has to be *cleared*, since carrying it forward would serve a pre-draft wire as players are being taken off it, whereas a trailing league's list is a perfectly correct answer about a season that is over — nothing needs clearing, the card simply must not use it. Type-gated on purpose (`REDRAFTING_TYPES`): a dynasty or salary-cap league carries its roster across the offseason, so one trailing during the rollover window — MFL leagues reopen anywhere from February to April — is stale rather than wrong, and excluding those would empty the card for weeks every spring over nothing. For a league that redrafts it *is* wrong, in the same direction the mid-draft exclusion guards against: the handful of names left unrostered at the end of last season are not this season's wire, because this season's wire is everybody until the draft runs. Both halves of the comparison must be present to mean anything — a `rosters.json` written before leagues carried their own `season` yields `NaN < year`, which is false, so nothing is dropped on missing data — and the two exclusions are counted as separate, mutually exclusive states (rollover wins) so they partition the missing leagues instead of double-counting one. Those counts no longer print a note each — they survive because the card returns null only when nothing is left *and* nothing was excluded (a group entirely mid-draft still renders, saying so in place of a table), and because the empty-state sentence names the reasons that actually apply. Four properties are load-bearing and pinned by `scripts/test-top-available.mjs`: `available: null` means "couldn't tell" and `[]` means "nothing free", and only the second belongs in the card's denominator — ESPN's league-wide read fails quietly, and counting a league that was never asked would report a free agent as available in 1 of 2 leagues; the card's two counts (**Free In** and **Own In**) share that one denominator on purpose, so a row reads as a partition of the same leagues — free in X, ours in Y, the rest somebody else's — and a league excluded from the denominator is excluded from *both* counts rather than printing two fractions with different bottoms; a group spanning two ranking lists medians the ranks per league, the same way the exposure cards do, since Dynasty/Salary Cap holds dynasty leagues reading `DYNASTY` beside cap leagues reading `DRAFT`; and `normalizeName` in `myffl.html` must agree with `normalizePlayerName` in `scripts/lib/fantasypros.mjs`, since that name is the join between a pool entry and a rostered player — the page carries a deliberate second copy because it has no build step and no imports, and the only alternative would be shipping every player's name twice in the JSON. A drift there is invisible: the player is simply shown as one you don't hold.
- **The automatic ranking set is on a calendar, not a constant.** A league with no `rankingType` gets `ROS` from kickoff (the Thursday after Labor Day) through the Super Bowl (the second Sunday in February), and `DYNASTY`/`DRAFT` the rest of the year — `nflSeasonPhase`/`automaticRankingType` in `scripts/lib/fantasypros.mjs`, pinned by `scripts/test-season-phase.mjs`. Two consequences: the FantasyPros season year is *not* `YEAR` between New Year and the Super Bowl (asking for next season's ROS list returns nothing), and `myffl.html` carries a deliberate second copy of the in-season rule purely to word the Admin tab's note — the sync is the side that decides, the page only describes. Setting `rankingType` is the manual override and opts that league out of the flip entirely.
- **The season is per league, resolved by availability, not by the calendar.** Leagues roll over on their own commissioner's schedule — MFL anywhere from February to April, redraft later still — so a single global year is wrong for somebody for months, and wrong *silently*: every card falls back to its previous entry and a stale roster renders exactly like a fresh one. `resolveSeason` in `fetch-rosters.mjs` aims at `nflSeasonPhase().season` and only moves a league once that season actually exists at the provider, recording the answer back into `data/rosters.json` so the next sync knows. Six properties are load-bearing and pinned by `scripts/test-season-rollover.mjs`: a league *settled* on the target — recorded against it **and** fetching cleanly — is never probed (so this costs nothing in-season), while a league carrying an `error` is always re-checked, which is what stops an unverified season from becoming permanent; movement past a known-good season is one-way (last season still answers a probe happily, so a "yes" must never pull a rolled-over league backwards); with no known-good season to sit on, the resolver walks back up to `SEASON_LOOKBACK` seasons until one answers, so a league whose new site isn't up yet lands on the one it actually last played rather than an empty one; the probes are tri-state — `true`, `false` (definitively absent, i.e. a 404 or a 200 with no league record), `null` (couldn't tell) — and only `false` may move a league, since acting on a 429 or an ESPN 401 would walk a healthy league backwards silently; the probe is `TYPE=league`, never `TYPE=rosters` (a rolled-over redraft league has no players until its draft, so an empty-roster test would strand exactly those leagues all summer); and Sleeper is never probed at all, since a new season there is a new league id and the old one answers forever. `seasonOf(league)` in `providers.mjs` is how every league-scoped call picks this up — which is why none of them take a year. Global lookups (player map, byes, injuries) stay on `YEAR` deliberately. MFL answers a league-season that doesn't exist with a clean **HTTP 404** — verified against the real API by `probe-league-season.yml`, which is worth re-running whenever leagues look stuck on the wrong season, since the whole mechanism rests on that answer. ESPN answers the same way — a 404 carrying a JSON `GENERAL_NOT_FOUND` body — verified in the same run. The caveat that survives is ESPN-only: its reads are cookie-authenticated, so expired `espn_s2`/`SWID` make every season read as absent and an ESPN league would silently never roll over. That is why the probe treats a false *control* season as a hard failure rather than a tidy negative.
- **Scoring format is read from the league, not assumed.** `detectScoringFormat` in `providers.mjs` resolves PPR/HALF/STD from what a reception is worth — MFL `TYPE=rules` (`event.$t === 'CC'`, XML-derived so every leaf is `{$t}`), ESPN `mSettings` statId 53, Sleeper `scoring_settings.rec` — all three verified by `probe-league-scoring.yml`. Three things are load-bearing, pinned by `scripts/test-scoring-format.mjs`: a rate that isn't exactly 1, 0.5 or 0 returns `null` rather than rounding to the nearest list (FantasyPros publishes three, and guessing puts the ECR column silently on the wrong one); MFL's base rate is chosen by counting **receiving positions**, not rules, since nine of these leagues carry a TE premium as a second `CC` rule and a rule-count tie would be decided by nothing; and detection is cached per league per season in `data/rosters.json` (`scoringDetected`), re-run only when the season changes or the league errored, because it is one more request on a sync that already brushes MFL's rate limit. In `config/leagues.json`, blank `scoring` **used to mean PPR and now means "detect it"** — pin `PPR` explicitly to get the old behaviour.
- **`submit-lineup.js` uses an allowlist, not a denylist.** It accepts a league only if `lineupPilot` is set *and* the provider is MFL or unset. Sleeper leagues can carry `lineupPilot: true` (their starters render read-only, since Sleeper's public API has no write endpoint). The in-file comment explains the reasoning: a future read-only provider must fail closed by default. Do not invert this.
- **The manual workflows are `workflow_dispatch`-only, deliberately.** `test-set-lineup.yml` exercises a write against a real MFL team; `test-login-endpoint.yml` probes the deployed login endpoint; `probe-league-season.yml` asks MFL and ESPN what they return for a league in a season that may not exist; `probe-draft-status.yml` asks MFL what it exposes about a running draft; `probe-league-scoring.yml` reports what a reception is worth in each league; `probe-fantasypros-player-url.yml` dumps a ranked player's fields; `probe-fantasypros-sleepers.yml` confirmed `type=SLEEPERS` on the consensus-rankings endpoint is real, reachable data (see the Studs/Sleepers bullet above); `probe-injury-detail.yml` asks MFL and Sleeper what they carry about an injury beyond its designation; `probe-league-history.yml` asks all three providers how far back a league's history goes and whether a past season's response carries a final standing/placement, for the History tab's Results card. Never add a `schedule` trigger to any of them. Every one of them exists because the API it asks about is unreachable from a sandbox — reaching for a new field on a provider response starts with a probe here, not with code that assumes the field is there.
- **The problems digest flags only what would change what you do.** The strip above the grid (`computeLeagueProblems`/`computeProblemsDigest`/`renderProblemsDigest` in `myffl.html`) collects everything across every league that needs a human — a starter who is Out, on bye, or filling a lineup slot from the taxi squad or a league IR slot, a lineup left short or empty, a league whose roster sync is failing — so eighteen leagues don't have to be walked to find the card that's on fire. It is computed entirely on the page from fields the snapshot already carries; the sync ships nothing for it. Its failure mode is noise rather than error — a strip that opens on fourteen benign rows trains the eye to skip the one that matters — and every judgement call below is a noise decision, pinned by `scripts/test-problems-digest.mjs`. `scoringError`/`standingsError`/`lineupError` never appear ("No live scoring available yet" is the normal preseason state on nearly every league, and MFL 429s heal on the next sync; each renders on its own card already); only the roster-level `error` does, because that one means the league's whole card is stale fallback rendering exactly like fresh data — which is also where a dead ESPN cookie finally becomes visible. Questionable starters are not flagged (the floor is `DIGEST_INJURY_FLOOR`, Doubtful), an unrecognised designation ranks below the floor rather than above it, and `RET` — deliberately absent from `INJURY_SEVERITY` — is caught via `INJURY_SETTLED`. Absence of lineup data must read as "not asked", never as an empty lineup: checks run only where `starters` is an array *and* `lineupWeek` is set, which naturally scopes them to the lineup-pilot leagues. A mid-draft league and a league still on last season get no lineup checks at all — the season comparison is the same one `awaitingRollover` makes but deliberately *not* type-gated, since a lineup for a week already played is stale whatever the league type does with rosters, and the NaN-is-false rule keeps pre-`season` snapshots checked rather than silently switching every league off. Each starter yields at most one row, worst problem first (the slot beats the injury beats the bye), and a starter id that doesn't resolve against the roster is skipped silently — a same-sync race between MFL's two exports, with nothing useful to say about a player we can't name. The required-starters check uses the *minimum* implied by `startingLineup` (flex slots count their lower bound), so it can miss a one-short lineup but can never flag a legal one, and best-ball `0-N` strings sum to zero and never fire. When nothing is wrong the strip is absent entirely — an all-clear banner would train the eye to skip the spot where real problems appear. Clicking a row jumps to the league's Rosters card (`data-league-id`, stamped in `renderCard`), because that card carries the lineup editor where lineup-shaped problems actually get fixed.
- **Roster-limit violations are computed, never read off a verdict — because MFL doesn't hand one over.** MFL lets a franchise sit *over* its roster-size, taxi-squad, injured-reserve, or per-position limits for a while (it enforces them at specific deadlines — a post-draft cutdown, the day after a trade window closes — rather than blocking the roster move itself), and its own site flags that. `probe-roster-validity.yml` established there is no field anywhere that says so: every key on both `TYPE=league` and `TYPE=rosters` was dumped by name against a league confirmed to be over its limit at the time (OSD, August 2026 — `rosterSize` 28, actually carrying 29) and none of them read as a verdict — the same finding `probe-fantasypros-power-rank.yml` made about power rankings, arrived at the same way. So this is computed exactly like the power score is: from raw counts against raw limits. `parseRosterLimits` in `scripts/lib/providers.mjs` reads `rosterSize`/`taxiSquad`/`injuredReserve`/`rosterLimits.position[]` off the same `TYPE=league` response `fetchLeagueRoster` already fetches every run for franchise info, nulling out any piece that's missing or unparseable individually rather than failing the whole object — a redraft league with no IR slot at all still has a real `rosterSize` worth checking. `rosterLimitProblems` in `myffl.html` then counts the league's own `players` by `status` (and, for the per-position check, position) and reports every limit actually *exceeded* — sitting exactly at a limit is not a violation of it, and a roster can be over more than one limit at once (too many taxi-squad stashes and too many IR players simultaneously), so each gets its own row rather than one collapsed line. The check runs from inside `computeLeagueProblems` but *before* the lineup-data early return, deliberately: a salary-cap or draft-only league with no lineup pilot still has a roster that can go over its limits, so gating this behind `starters`/`lineupWeek` the way the lineup checks are gated would silently turn it off for fifteen of eighteen leagues. It shares the lineup checks' other two gates instead — mid-draft (a roster built up from zero hasn't gone over anything yet, and a rookie draft landing on top of a full veteran roster is expected to push over until the post-draft cutdown, not urgent the instant a pick lands) and trailing-season (last year's count isn't this week's problem) — using the same raw `Number(league.season) < Number(year)` comparison the lineup checks use, not the type-gated `awaitingRollover`. `league.rosterLimits` is absent for Sleeper and ESPN, both of which enforce their limits at the moment a roster move is made, so there is nothing to check there and the caller's truthiness check on `rosterLimits` is the whole gate — no provider branch needed. **A `"0-0"` position entry means the cap isn't configured, not that the position is capped at zero** — the same sentinel `startingSlotCounts` already treats as an off-switch for the starting-lineup node, one function up in the same file. This shipped without it once already: the first sync under this feature flagged Wise Guys and Super Cap — both auction/salary-cap leagues, where MFL doesn't apply per-position rules at all — for carrying "3 over the 0 limit" at every skill position, live on the real site, until a second probe run against Wise Guys (confirming the "0-0" shape on a second league, not just inferred from the first) caught it. `parseRosterLimits` drops any position entry whose min *and* max both parse to zero before it ever reaches `rosterLimitProblems`, exactly mirroring `startingSlotCounts`'s existing `if (min === 0 && max === 0) continue`. A real per-position cap — Iron Bank's `"0-18"` on every skill position, still correctly enforced — looks nothing like this: only a range that is zero at *both* ends is the sentinel.
- **Power ranks are homegrown, and the FantasyPros question is settled.** `probe-fantasypros-power-rank.yml` established that nothing team-shaped exists behind the partner API key — every candidate endpoint answered 403 (`Missing Authentication Token` is API Gateway for "no such route") while the consensus-rankings control answered 200 with the same key — and that **projections are reachable**, each row carrying all three scoring variants at once plus an `mflid`. So the Power Rankings card on the Analytics tab is computed by the sync: every franchise in a league graded by its best legal starting lineup under FantasyPros season projections, plus a `depth` number — the projected points of everyone that lineup could not seat (`fetchProjections`/`computePowerScore`/`computeLeaguePower` in `scripts/lib/fantasypros.mjs`, pinned by `scripts/test-power-rank.mjs`). The judgement calls: **MFL joins by player id** — roster ids *are* the projections' `mflid` — while Sleeper and ESPN join by normalized name, and a Sleeper id must never touch the id join (both id spaces are small numeric strings, so a wrongly-joined Sleeper league renders a plausible column crediting franchises with other people's players); a name collision tombstones to null, crediting nobody, same rule as `buildRankingIndex`. The score fills dedicated slots before flex (most-constrained first) and is a *floor*, not a roster valuation — bench depth deliberately counts for nothing, kicker/defense slots are dropped from the valuation (their minimums still count against MFL's `starters.count`, or their slots would be handed to flex), and scores are comparable only *within* a league, which is why the page shows the rank ordinal and keeps the score in a tooltip. Slot shapes come from each provider's own data (`startingSlotCounts` parsing MFL's raw starters node — the flex is the gap between `starters.count` and the accounted minimums, eligible to skill positions with range headroom, and with no count the minimums stand alone, an undercount but the *same* undercount for every franchise, which is all an ordinal needs; `slotsFromSleeperRosterPositions` mapping Sleeper's `roster_positions`) except ESPN, which is valued against `DEFAULT_POWER_SLOTS` because its real slot counts live in an mSettings view this project has never probed — uniform-across-the-league is the property that matters, and reaching for the real counts starts with a probe. The per-franchise rosters ride the availability pass — the *same* league-wide read, parsed one level deeper, never a second request — so power inherits its cadence (Sleeper every sync for free, MFL/ESPN once a day), its mid-draft skip (a half-drafted league's power is cleared like its wire — it would rank who drafted earliest), and its carry-forward on the five runs in six that skip the daily read. The raw per-franchise rosters and slot shapes are working fields deleted before `data/rosters.json` is written; only the computed `power` object ships, a few hundred bytes per league. On the page (`leaguePowerRanks`/`computeMyPowerRows`/`renderPowerRankCard` in `myffl.html`) this renders first in each Analytics sub-tab, ahead of Bye Weeks, Top Available, Player Exposure and Injury Exposure — one row per league we hold a team in, best overall rank first, with Starters and Depth as separate rankings of the same teams — which is what tells a 3rd-overall roster whether it is a contender with no bench or a farm system with no lineup. Overall is starters plus depth; ties share a rank; depth is ranked only when every team in the league carries the number, and overall degrades to the starters ordering when it doesn't. A redraft league still on last season (`awaitingRollover`, type-gated exactly as on Top Available) has its ranks **suppressed rather than skipped** — it appears as a row of TBDs saying what it is waiting for. The distinction is the point: that league generally *does* carry power data, computed from last season's rosters, and that data is a perfectly correct answer about a season that has ended, so rendering it would state last year's standings as this year's outlook. A trailing dynasty league keeps its real ranks, since its roster carried over and they still describe something. **This deliberately does not render on the Standings cards, where it first shipped** — standings are a record of what happened, not a predictor — and the raw scores render nowhere at all: points compare only within a league, and the per-league ordinal is the part that survives being read across leagues, which is also why the dynasty/salary-cap sub-tab sharing is safe here despite the cross-list hazard that constrains the other Analytics cards. **What `week=0` returns in-season is the open question hanging over the whole feature, and it is not yet answered.** The season *year* is already phase-aware (it comes from `nflSeasonPhase().season`), but the week is not: `fetchProjections` asks for FantasyPros' preseason slot, and once games are played that either keeps serving frozen August numbers, starts serving rest-of-season numbers, or empties out. The first is the dangerous one and is silent — projections that predate every injury and breakout of the season, rendered as perfectly plausible ranks — and it is worth knowing that **rest-of-season projections, not accumulated stats, are the right in-season input**: a power rank built on what already happened is the standings with extra steps, whereas ROS folds the season to date in by itself (the breakout's number rises, the injured player's goes to ~0), which also happens to be the only fix available for the fact that the league-wide roster read carries no injury status for anybody but us. **Both bases are computed every run and shown side by side.** The card's `Proj` and `ECR` columns are the same franchises ranked twice, independently, and a team leading one while trailing the other is the point rather than a discrepancy to reconcile: projections value a roster by the points it should score, while rankings value it by where consensus places its players — which for a dynasty league is a bet on the next several years. A roster that is 1st projected and 4th by ECR is a win-now team with an aging asset base; the reverse is a rebuild. Computing both costs nothing at the provider (projections are fetched once per sync, the pools were already fetched for Top Available) and the snapshot grows by one small `teams` array per league. Where the two *converge* is worth knowing too: in season `automaticRankingType` serves `ROS`, so the ECR side becomes a short-horizon measure much like projections, and the columns mostly agree — the pair earns its keep most in the offseason for dynasty leagues, where the horizons genuinely differ. A basis that couldn't be computed renders **`TBD`**, not a dash: the number is not missing, it is not computable yet, and it will be. Only `Proj` and `ECR` are doubled — `Starters` and `Depth` exist on both bases too, but showing four would put seven columns on a table that has to survive a phone, so they follow one basis card-wide (`powerDetailBasis`: projections when the card has any, rankings otherwise) with the choice named in the header tooltips. The card carries a sixth column, **`Avg`** — the mean of `ECR`, `Starters` and `Depth` (`powerRowAverage`) — and is ordered by it. Those two columns are **labelled `Start` and `Ben`** on screen, abbreviated so six columns fit a phone without wrapping, with the full words carried in the header tooltips; this file uses the long names throughout because it is describing the measures rather than the layout. `Proj` is deliberately *outside* that average even though it sits beside it: `Starters` and `Depth` are the projections basis decomposed and `Proj` is those same halves recombined, so including it would let projections outvote consensus three to one in a number meant to summarise both. Leaving it out still leaves projections ahead two to one, which is the honest cost of the detail columns following one basis. The average is taken over whatever a row actually has, so a league missing a basis is not pushed down by an accident of arithmetic, and it is null only for a row with nothing at all — which is exactly the TBD rows. Ordering by it rather than by projections is what makes the two bases equals; ties fall to the projections rank, then to config order. The consequence to accept is that no single column reads monotonically down the page, which is the honest presentation of a composite order — mitigated by every column being clickable. **Click-to-sort copies the shared analytics table's three rules rather than inventing its own** (three states: natural → reverse → back to the card's order; ties falling back to that order; a missing value staying at the bottom in *both* directions), but does not reuse `appendAnalyticsTable`, whose rows are players with different columns and pagination this card doesn't need. The missing-last rule is the silent one — the obvious implementation reads correctly ascending and then hands the unranked leagues the top rows on the reverse click — and `scripts/test-power-rank.mjs` drives a DOM stub to pin it, the same way `test-analytics-sort.mjs` does for the shared table. **The Start number is itself a button, the same idiom Team Needs' per-position ranks and Salary by Year already use**: clicking it pops up who the actual starting lineup is — one row per seated player, name and the position that seated him — via its own separate `.starters-popover` instance (`openStartersPopover`/`toggleStartersPopover`), kept apart from `needsPopover` and `salaryPopover` for the same reason those two are apart from each other. This exists because the valuation has no concept of taxi-squad ineligibility — a taxi-squad stash can outscore a real bench player and get counted as a starter in the score, which is fine for the ordinal but was surfacing as an unexplained low Bench rank until a manager could see who was actually seated. The list comes from `computePowerScore`'s own greedy fill (`starters: [{name, position}]`, appended to each fill in seating order) rather than a second computation, so the popover can never disagree with the number that opened it — and, matching `keepMyStarters` in `fetch-rosters.mjs`, it only ever exists on the row's own franchise (every other team's list is stripped before the sync ships, to avoid paying for rosters the card never displays), so a league that hasn't resynced since this shipped falls back to plain text rather than a dead-looking button. `League` is sortable here where the shared table leaves the player name unsortable: there a name is not a measure, here it is the row's identity. A league with *neither* basis still gets a row — four TBDs — and sorts last, because a league silently vanishing from a card headed "my teams" is the failure this avoids. Such a row carries its own tooltip (`powerUnrankedReason`: still on last season, mid-draft, roster sync failing, **no rosters yet**, or nothing from the last sync). The empty-roster case is the commonest of those by far and is worth its own wording rather than the generic one, which read as a sync fault: a league nobody has drafted holds nobody, so there is nothing to value. It deliberately does *not* arrive through the mid-draft branch — a draft that has not **started** is not a draft in progress, since MFL returns zero picks for a league with no draft scheduled (`draftStatusFromResults` calls that "couldn't tell", not "unfinished") and ESPN is exempt from the draft check altogether. An empty roster is the one observation covering all of those without guessing at a cause. It is checked *after* `error`, because an errored league falls back to a previous entry that may itself be empty and would otherwise be reported as "hasn't drafted" because a row of TBDs with no explanation reads as a bug, and it has no league size to print. Two consequences follow. There is nothing further to sort those rows by — **`Starters` and `Depth` are sub-metrics of these same two bases, not a third measure**, so a row missing both ranks is missing its Starters too — and they fall to config order among themselves. And the missing-basis note must test "ranked on one basis but not the other", never "missing this basis", or a single mid-draft league would announce that projections aren't published for the season while every other league on the card is using them. The card as a whole still returns null when *nothing* could be ranked, which is what keeps an absent card and a TBD row meaning different things: absent says the sync produced no power data for this group, a TBD row says this league in particular couldn't be ranked — legible only when something beside it was. The league size rides with the league name as a muted `(12)` rather than being folded into a rank as `1/12`, which lets every rank column be a bare number and — the part that was previously impossible — shows the size on a league whose ranks are all TBD, where it had nowhere to go. One judgement call worth keeping: a basis that is *present but suspect* — the frozen-preseason-projections case — still prints its number rather than a `TBD`, because until the post-kickoff probe settles what `week=0` serves in season, hiding a number that may be perfectly good would lose more than it protects; the card's one-line note carries that caveat instead. If the probe shows it frozen, switching that case to `TBD` is a one-line change.
- **The Power Rankings card also carries two sub-lines under each league name — "Studs" and "Sleepers" — each naming rostered players who rank in that league's own top 25 on a different FantasyPros list.** Both are rendered by one shared function, `powerPlayersLine(label, players, rankLabel)` in `myffl.html`, the mirror image of the two exposure cards' `leagueLine` under a *player's* name (`.exposure-leagues`) reused for their own two sub-lines ("Free in"/"Own in") — there the line names the leagues a player belongs to, here it names the players a league is strong in, and both lines here share one CSS pair (`.power-players`/`.power-players-label`) the same way. Either line is omitted entirely rather than printed empty when nothing qualifies, and each name carries its rank as a tooltip.
  - **Studs** (`leagueStuds`, `STUDS_RANK_THRESHOLD = 25`) reads `p.ecr.rank` — the same per-player field the Rosters tab's ECR column already reads — so "adjusted to ROS during the season" is free: that field is already computed once at sync time under whichever ranking set `automaticRankingType` currently serves (ROS in season, DYNASTY/DRAFT off it, or a league's own pinned `rankingType`), and there is nothing new to compute beyond the filter itself.
  - **Sleepers** (`leagueSleepers`, `SLEEPER_RANK_THRESHOLD = 25`) reads a *second, independent* FantasyPros list — undervalued/breakout picks, editorial content rather than a full positional ranking — attached sync-side by `attachSleepers` in `scripts/lib/fantasypros.mjs` as `p.sleeper` (pinned by `scripts/test-sleepers.mjs`). `probe-fantasypros-sleepers.yml` established this is real, reachable data: `type=SLEEPERS` (plural, always) on the exact same `consensus-rankings` endpoint `attachRankings` already calls for `Proj`/`ECR` — 79 players and 17 experts the run it was probed, shaped identically to every other consensus-rankings response, so the join reuses `buildRankingIndex`/`lookupPlayer` unchanged. **`type=SLEEPER` (singular) is not an error** — FantasyPros silently serves the Draft list back instead of 4xx-ing an unrecognized `type`, so a typo here would ship a column that quietly means something else rather than failing loud; re-run the probe before ever touching that literal string. One fetch for the whole sync rather than one per league (unlike the primary rankings, which vary by league type and scoring): Sleepers is a single curated list, not a scoring-sensitive positional ranking, so every league joins against the same response — and it carries no seasonal flip the way `automaticRankingType` gives `Proj`/`ECR`, since FantasyPros publishes it as one list year-round rather than a DRAFT/DYNASTY/ROS-style rotation.
  - Both thresholds are separate named constants on purpose (not one shared value), since each is independently expected to move once real leagues show what 25 actually catches on that particular list — a display filter, not a computed statistic, so retuning either is a one-line change with no knock-on effects on the other.
  - Both are suppressed the same way `Proj`/`ECR`/`Avg` already are: a row with neither basis — a trailing league still on last season, or one with no power data at all — gets empty studs *and* sleepers lists even when its roster genuinely has qualifying players sitting right there, because that row's whole framing is "wait for it," and naming anybody underneath would contradict it. The two lists are also independent of each other: a player can be a stud, a sleeper, both, or neither, and one list is never derived from or gated by the other.

- **Team Needs renders right after Power Rankings and is built entirely from data that card already computes — no new fetch, no new valuation.** The greedy lineup fill in `computePowerScore` already knows which real position filled every slot it seated, dedicated or flex (`bestPos`), so the only new work is keeping that instead of discarding it: each team's `byPosition` now carries a `{score, depth}` pair per `POWER_POSITIONS` entry, normalized to all four even when a roster spent nothing at one of them — an empty TE room is a real `{score: 0, depth: 0}`, not a missing key, because a position nobody rostered is exactly the case this card exists to surface. `myffl.html`'s `leaguePowerRanks` ranks each position the same way it already ranks Overall: `score + depth`, blended into one number and ranked with `competitionRanks`, because a need reads as a single verdict ("weakest at RB") rather than a starters number and a depth number a reader has to weigh by hand. `renderTeamNeedsCard` doesn't build its own rows — it calls `computeMyPowerRows` outright, since `proj`/`ecr` already carry `byPosition` and every gate that function applies (the `awaitingRollover` suppression, the mid-draft/error/no-roster reasons, the single active `powerDetailBasis`) has to apply here identically or the two cards would disagree about which leagues are rankable. Two guards carry over for the same reason they exist on the whole-roster columns: `hasByPosition` requires *every* team in a league to carry the new shape before any position is ranked there, the same "half a league on an older power object must not be ranked" rule `hasDepth` already enforces for Depth — a league that hasn't resynced since this shipped has old-shape team entries, and ranking four positions off half of them would manufacture a column that means nothing rather than say so; and the card itself is absent, not a wall of TBDs, when nothing in the group has `byPosition` yet, the same bootstrap gap Power Rankings' own card-level check already covers. The card shows no raw point values anywhere, matching Power Rankings' existing rule that those numbers only compare within a league — a rank column here is that same within-league ordinal, one position at a time. Each row flags every position ranked below the league's own average — worse than half the field, e.g. rank 6+ of 10, 7+ of 12, 8+ of 14 (`.needs-weakest`) — rather than only whichever single position happens to be worst. That replaced an earlier version that highlighted just the uniquely-worst cell and showed nothing on a tie: a real league (Game On, 14 teams) turned up dead last at both WR and TE simultaneously, and picking one over the other to flag would have implied a difference the numbers don't support, while flagging neither for lack of a unique worst hid a roster that was actually hurting in two places at once. The average-based line has no such blind spot — a team can clear zero, one, or all four positions, and each clears independently. **A team clearing the average at every position falls back to its own weakest position(s) instead of going unflagged** — a genuinely strong roster still has a position that is relatively thinner than its others, and leaving that row with nothing to say would mean a contender never gets an answer while a mediocre team's row fills with flags every week. The fallback only fires when there is an actual worst to point at: a team tied at the identical rank across all four positions (the two-team-league case, where "leads every position" and "is tied everywhere" are the same fact) has nothing relatively weaker, and flagging all four just because they share the max would call an evenly-strong roster needy everywhere — so that case is left unflagged, matching the average-based rule's own zero-flags outcome. A tie for the team's own worst under the fallback is treated exactly like a tie under the average rule: both positions flagged, never an arbitrary pick. Rows keep `computeMyPowerRows`' own order (the row average) rather than a Team-Needs-specific resort, so the two cards read as paired views of the same leagues in the same order; every position column is still independently clickable for "who's weakest at RB across my leagues," following the shared three-state sort rules — clicking a column *header* sorts by it, which is a separate gesture from clicking a *rank number*, covered next. **Every rank number is itself a button, the same idiom `.salary-link` uses for Salary by Year on the Rosters tab: clicking it pops up the Starters and Bench ranks behind the blended number on screen**, via one shared `.needs-popover` instance (`openNeedsPopover`/`toggleNeedsPopover`, mirroring `openSalaryPopover`/`toggleSalaryPopover` structurally but kept as its own separate instance rather than shared code, since the two pop up unrelated content from unrelated tables and there's nothing to gain from coupling them beyond the CSS shape they already duplicate on purpose). `leaguePowerRanks` computes this by giving each position the same three-way split the whole roster already gets — `{overall, starters, depth}` rather than a bare number — so the popover reads real, independently-computed ranks rather than re-deriving them from the one number already on screen; the card itself still prints only `overall`. Positioned exactly like the salary popover: `position:fixed`, anchored to the clicked button's own rect, pulled back from the right edge of the viewport, dismissed on scroll/resize/Escape/outside-click rather than tracked, since it's a quick reference a click away again and a stale position left behind by a scroll would be worse than it just closing. **Each of a row's flagged positions also carries its own sub-line, under the league name — the same slot and `.power-players`/`.power-players-label` styling Studs and Sleepers already use, not inside the flagged cell itself.** It was tried inside the cell first, and that was wrong: a roster's worth of names growing one cell taller than its neighbors threw off every column's alignment on that row, which is exactly the "columns disrupted" failure the name-column placement avoids — only the first column ever grows, and every position column stays a plain, aligned number no matter which ones are flagged. `needsRosterLine` (reading `rosterByPosition` — the roster split into `POWER_POSITIONS` groups by `rosterPlayersByPosition`, gated the same `proj || ecr` way `studs`/`sleepers` already are) names every rostered player at a flagged position with their overall ECR in parens, best-ranked first and an unranked player last with an em dash — the same missing-value convention `buildEcrCell` uses on the Rosters tab. It is the *whole* group, not just starters, matching the fact that the rank above already blends starters and bench: a deep dynasty roster's flagged position can print a long line, which is the honest shape of "here's everyone you have there" rather than a curated top few. A row with two flagged positions gets two separate lines, one per position, rather than one merged list — Game On's real WR-and-TE case reads as two distinct groups because that's what they are. A row with nothing flagged at all — the tied-everywhere fallback case, or a row with no rank data — gets no sub-line, because there is nothing for the line to point at. The rank rides inline in parens rather than in a hover title the way Studs/Sleepers show theirs, since the question this line answers ("who do I have, and how good are they") wants the number visible without a hover. Each name on the line carries its own color now, rather than the whole line inheriting one the way it first shipped: a name only reads as "notable" (`.needs-players-top`, `--accent` purple) when that specific player clears `NEEDS_ROSTER_TOP_ECR_THRESHOLD` (50); everyone else prints in the line's own plain color, the same muted default Studs/Sleepers already use, including the `"RB "` label itself — most names on a line usually won't be purple, so a label permanently colored to answer "why is that number purple" would read as attached to nothing. A taxi-squad player (`.needs-players-taxi`) is called out separately, in gold, regardless of his own rank: he isn't on the active roster, so he's a real asset at the position without being a lineup-slot cost the way his listed teammates are, worth knowing without a click into the roster. The color is `--gold-chip-text` — the same token Bye Weeks' `.bye-player-mid` already uses for gold text sitting directly on the card background, not `--gold-text`: that token is meant as the dark foreground *for* a bright `--gold`/`--gold-chip-bg` chip, and is itself a dark color in dark mode, so using it as a standalone text color made it nearly invisible there. `--gold-text` was the original choice and had to be swapped out once real dark-mode use surfaced the problem. **Unlike every other player line on the page, a taxi-squad player's team suffix is pulled into that gold too** (`.needs-players-taxi .team-suffix { color: inherit; }`), rather than staying at `.team-suffix`'s usual unconditional muted grey: a taxi-squad player reads as one highlighted fact — name, team, and rank all describing the one asset — not a name with unrelated grey metadata hanging off it. **The two rules collide when a taxi-squad player also clears the top-50 threshold** — good enough to start, sitting somewhere he can't — and when they do, the name itself stays gold rather than switching to purple: he's still not on the active roster, and that fact doesn't change just because his rank says he should be playing. What changes instead is the rank number in parens, which goes purple (`.needs-players-promote`, `--accent`) — the same color `.needs-players-top` uses for an active-roster player who clears the identical threshold, so purple means "top-50" wherever it lands on this line, whether that's a whole name or just a number. This shipped once already as a bespoke warning-amber token (`--gold-warn-text`), on the reasoning that "maybe promote him" was a distinct signal from "notable" and deserved its own color — and was reverted in favor of purple once real use showed the opposite: applying the *same* top-50 rule twice (once to a whole name, once to just a rank number) reads more consistently than teaching the line a second color for a signal that's really the first one recurring.

- **Projections are not available year-round, so the score has a second basis.** FantasyPros publishes them per season, and `nflSeasonPhase` rolls the target year over at the Super Bowl, so from February until the next season's list appears there is simply nothing to ask for: every position returns empty and `fetchProjections` throws. Without a fallback the card would carry January's ranks through to July — against rosters that have since traded and drafted — and stay *silent* while doing it, because a carried-forward power object still reports the phase and slot it was originally computed under, which is the safe-looking combination. So when projections are dark the sync values players from the ranking pools it already stores for Top Available (`ecrValue`/`buildEcrIndex`): rankings exist year-round by design (`automaticRankingType` serves DYNASTY/DRAFT in the offseason and ROS in season), so the fallback is always current in exactly the window the primary basis is not. The index it builds is the *same shape* as the projections one — `byMflId` deliberately empty, since pool entries carry no MFL id and `computeLeaguePower` already falls through to the name index — so nothing downstream knows which basis it has. Rank becomes value through a logarithm (`log(poolDepth / rank)`): steep at the top, flat through the middle, exactly zero at the pool edge, no tuned constants, and only the *ordering* it produces is ever shown, so it needs to be monotone and roughly right rather than calibrated. Pool depth is measured as the **deepest rank present, not the entry count** — identical for a pool as stored, but they come apart the moment anything filters it, and the count is the one that silently zeroes every player past it. Two properties are worth knowing rather than discovering: this curve is steeper than raw projected points (which carry a baseline every startable player earns), so **the two bases can order the same teams differently** — which is why `powerUsesRankings` puts a line on the card saying which ruler was used, so a rank that moves in February is explainable; and the pool is `RANKING_POOL_SIZE` deep where projections cover every ranked player, so depth on this basis counts only pool players and reads a bench of unranked stashes as empty rather than thin (against real rosters the join rate is around 84%, the misses being exactly those stashes). Three things guard the gap until `probe-fantasypros-power-rank.yml` is re-run after kickoff. `fetchProjections` **throws** on a position that comes back empty rather than computing on it, since every franchise would score zero, every zero would tie, and the card would rank all twelve teams first. `computeLeaguePower` returns **null** when not one franchise in a league seated a single player — the same failure arriving through a broken join or slot shape — and the caller skips the league, so the previous sync's ranks stand rather than being overwritten by a uniform lie. And each power object records the *slot it was computed from and the phase it was computed in* (`{season, week, inSeason}`), which `powerUsesPreseasonProjections` in `myffl.html` turns into the card's one conditional line when `inSeason` is true and `week` is still `0`. That line is conditional on purpose — the five Analytics cards carry one identical subtitle and nothing else, and this is an alert rather than a standing explanation. **It is phase-and-slot rather than a freshness date because the probe established that the projections endpoint carries no `last_updated` at all** (unlike consensus-rankings, where the field does exist): a date-based staleness check there would never fire while looking exactly like a working guard, which is the failure mode this whole section exists to avoid. The other thing the probe established, and the reason a fix is likely to be simple: **`week=N` is honoured but empty in the preseason** — the endpoint echoes the week back and returns zero players for weeks 1 and 2 in August — so weekly projections are a real slot that fills in-season rather than a parameter the API ignores, and summing the remaining weeks is a live option once the post-kickoff probe confirms what each week returns.
- **The header login control renders unconditionally.** It used to appear only when some league had a lineup editor. It must not go back to that: logging in is now also what reveals the Admin tab, so gating the control on league data would mean switching lineups off everywhere hides the login box, which hides the Admin tab, which is where you'd go to switch them back on.
- **The History tab sits right after Analytics in `VIEW_ORDER`/`VIEW_LABELS`, gated behind login the same way and for the same reason Analytics is** — dues owed, payouts, and past finishes read as strategy, not public schedule data. Unlike every other tab, it does **not** split by league type: one Results card and one Finances card span every league at once (`renderResultsCard`/`renderFinancesCard` in `myffl.html` each take the whole league list, no `data-league-type` and no sub-tab strip), on the reasoning that a dynasty league's finish and a draft-only league's finish are the same kind of fact — where did this roster place that year — so splitting them into tabs would just be more clicks to see the same leagues. Both cards also only ever show a league that has at least one backfilled year (`results.length > 0` after the `startYear` filter): a league still waiting on its first backfill doesn't get a placeholder row, it simply isn't listed yet, the same way an absent card elsewhere on this page means "nothing here" rather than "not yet". Each league name carries a two-badge strip underneath it (`historyBadgesNode`) — provider (gold) and type (purple), the same two facts `buildCardHead`'s Rosters-card strip leads with, deliberately never season or tags — since combining every type into one card is exactly what makes naming each row's type worth doing here. That strip sits on its own row under the name rather than beside it the way `buildCardHead` places it (there's a headline number — Avg Finish / Total — occupying the space to the right), and deliberately opts out of `.badges`' narrow-screen width cap (`.history-badges` in the CSS): that cap exists to leave room for a *title* squeezed beside the badges, which doesn't apply to a badge row with the full card width to itself.
- **The Results card needed data nothing in the sync had ever parsed: a final, playoff-adjusted placement for a past, completed season.** `data/rosters.json` only ever carried the current season's live standings, and — confirmed against the real API via `probe-league-history.yml` — MFL's `TYPE=leagueStandings` order is regular-season seeding only: a real league's top row by `h2hwlt` had exactly `lastRegularSeasonWeek` games played, meaning playoff weeks aren't folded into it at all, and that same league's actual 2025 champion was a team that entered the bracket as the 3-seed, not the team with the best record. Using regular-season order as "finish" would have been silently wrong in the one case this feature exists for. ESPN, by contrast, already computes and exposes the answer directly: `rankCalculatedFinal` on each team from `view=mStandings`, confirmed to form a clean 1..N permutation across every team (including non-playoff ones) and independent of `playoffSeed` — no derivation needed there, and `rankFinal` (a same-shaped but always-zero field on the same response) is a decoy, never used. Sleeper is out of scope for now — its bracket endpoints (`winners_bracket`/`losers_bracket`) return `null` before a season's bracket is generated, and no Sleeper league in this config has a finished season to confirm the shape against yet.
- **MFL's real mechanism, found by probing rather than guessed at (see `scripts/probe-league-history.mjs`'s own header for the full run-by-run history): `TYPE=playoffBrackets` (plural) lists every bracket a league ran that season** — `{id, name, bracketWinnerTitle, startWeek, teamsInvolved}` — and `TYPE=playoffBracket&BRACKET_ID=<id>` (the parameter name is `BRACKET_ID`; `ID`, `bracket_id`, and `bracketId` all fail with the same "Invalid or missing playoff bracket id" the plain endpoint gives with no id at all — confirmed by trying all four against a bracket id the listing had just proven valid) returns that bracket's actual game tree: rounds keyed by week, each game an id plus `home`/`away`, each side a `franchise_id`, `points`, and either a `seed` (a bye team entering that round) or a `winner_of_game` (advanced from an earlier one). A single-elimination tree funnels to exactly one game in its last round, which is the bracket's final.
- **Bracket names are commissioner-chosen free text, not an enum, so classification is by keyword rather than a name list** (`bracketFamily`/`isConsolationBracket` in `scripts/lib/history.mjs`): anything containing "toilet" (case-insensitive) in the bracket's `name` OR its own `bracketWinnerTitle` is the bottom/loser family, everything else defaults to the top/winner family — real names seen across leagues in this config for that SAME top bracket include "Fantasy Bowl", "Sole Survivor" (Dynasty Survivors), "Championship Bracket" (Super Cap), and "Champions Bracket" (Game On), which is exactly why enumerating names would be fragile where "not the toilet bowl" is not. A bracket whose name contains "consolation" is that family's second-tier decider rather than its main bracket. **`bracketWinnerTitle` is checked because `name` alone isn't always enough**: MNMx Dynasty's 2006 season ran its loser's bracket as "MNMx Dynasty Losers Bracket" — no "toilet" anywhere in the name — so name-only classification put it in the SAME family as the winners bracket. Structurally it's a full second bracket with its own five franchises, a disjoint set from the winners bracket's own five, not a subset — so it also failed the secondary-bracket subset test one level down (see the "3rd Place Game"/"7/8 position" fix below) and was dropped entirely: all five of its franchises fell back to a plain regular-season-order guess despite the bracket data fully determining two of them. Its `bracketWinnerTitle`, "Toilet Bowl Champion", said what `name` didn't, and MFL provides that field on every bracket in the same `TYPE=playoffBrackets` listing `name` already comes from — no extra request. **Both families are scored identically — a Toilet Bowl is not scored backwards**: confirmed explicitly rather than assumed, since "winning" a joke bracket is a real, could-go-either-way ambiguity by league culture. In both, the main bracket's final winner takes the family's best open rank and the loser the next; the consolation's final winner/loser take the next two. A team that played in the main bracket but reached neither final — a bye-less team eliminated in an early round with no consolation game to catch it — gets its rank by elimination when there is exactly one such team (the common shape: a 5-team bracket with one consolation game accounts for 4 of the 5, leaving the fifth with nothing left to assign, not a guess). **Two or more such leftovers, or a family with no bracket at all, is a genuine gap bracket data cannot resolve on its own** — those teams are ordered by regular-season standing instead and the result is flagged `guessed: true`, which `renderResultsCard` renders in red (`.results-guessed`, the same `--ir-text` token the rest of the page uses for "needs a look") rather than presenting an estimate as settled fact.
- **The backfill is explicitly a one-time cost, run last in the sync and separately budgeted from everything else** (`backfillLeagueHistory` in `fetch-rosters.mjs`, `HISTORY_MFL_REQUEST_BUDGET`/`HISTORY_ESPN_REQUEST_BUDGET`) — this is bonus historical data for a secondary tab, and must never compete with rosters/standings/scoring for MFL's rate limit the way the availability pass's own history already warns against. A **confirmed** season (`guessed: false`) once recorded in a league's `results` array is never re-fetched, because a completed season's placement never changes; a league's full history (one real league in this config goes back to 2006) is expected to take several syncs to fully backfill under a modest budget, and costs nothing on every sync after that — this is the intended shape, not a bug to fix by raising the budget. MFL answers "how far back does this league go" from its own `TYPE=league` response's `history.league[]` field — `{year, url}` for every season on record, with that year's own league id embedded in the url — which is exactly what a walk-back (the mechanism `resolveSeason` already uses for rollover detection) can't give for free: one real league in this config changed id four times between 2006 and 2016 before settling on the one config carries today, and `history.league[]` handles that with one call, no walking required. **ESPN has no equivalent list, so its backfill is a capped walk-back** (`ESPN_HISTORY_LOOKBACK_YEARS`) from the league's own resolved season using the same `espnLeagueExists` probe `resolveSeason` uses, remembering a confirmed absence (`historyBoundaryYear`) so future syncs never re-probe a year a league is now known not to reach — a `null` (couldn't tell, likely a stale cookie at that vintage) halts the walk for that run without moving the boundary, exactly mirroring how `resolveSeason` itself never acts on an unknown. Every year-boundary check is anchored to the league's OWN resolved `season`, never the sync's global target — a trailing league's currently-active season must never be mistaken for a completed year to backfill, which would compute a "final" placement from a bracket that hasn't happened yet.
- **A `guessed: true` result stays eligible for retry — only a confirmed one permanently blocks re-fetching a year, and this distinction is load-bearing, not decorative.** By the time this backfill pass starts, MFL is often already near its rate limit from the main sync's own roster/standings/scoring/lineup requests for every other league, so a bracket fetch here hitting a 429 is a real, observed failure mode (confirmed against two actual sync runs, both showing dozens of consecutive 429s the moment the backfill pass began). `computeMflSeasonPlacements` cannot tell a bracket that's genuinely absent from one that merely failed to fetch — both look like "nothing here" from its side — so it correctly falls back to regular-season order and flags the year `guessed: true` either way. The bug this produced in production: a rate-limited year got written into `results` as a permanent, "resolved" guess, and because the whole point of this backfill is that a recorded year is never re-fetched, that bad guess could never self-correct (this is exactly what happened to Iron Bank's 2020 and 2025 entries — both wrong, with 2024 missing entirely, because the real bracket fetches for those years were swallowed as 429s rather than surfaced). The fix has two halves. First, `fetchMflSeasonBracketData` in `providers.mjs` re-throws on `err.status === 429` from a per-bracket fetch instead of swallowing it and continuing with whatever brackets happened to survive — a 429 must abort that year's computation entirely rather than quietly starve it down to a guess. Second, `yearsNeedingHistoryBackfill` only treats `guessed: false` entries as permanently resolved; a `guessed: true` entry — including one already sitting in `data/rosters.json` from before this fix — remains in the retry set on every future sync until a run with rate-limit headroom actually settles it, at which point `backfillLeagueHistory` replaces the stale guessed entry for that year rather than appending a duplicate. Third, once a 429 is confirmed (as opposed to swallowed), the rest of that sync's MFL backfill work is abandoned for the run (`mflRateLimited`, checked before every remaining league and year) rather than continuing to spend the remaining budget on requests just as likely to fail — a real run once logged spending 27 requests against a budget of 24 chasing exactly this. None of this applies to ESPN: `espnSeasonPlacement` is read directly off `rankCalculatedFinal` and never produces a `guessed: true` result, so there is nothing there for a rate limit to corrupt.
- **`backfill-history.yml` runs the History backfill on its own, outside the regular sync, for exactly the contention the previous bullet describes.** By the time `fetch-rosters.mjs`'s own backfill pass starts, MFL has already absorbed the main sync's roster/standings/scoring/lineup requests for every league — the retry-eligibility fix keeps that contention from corrupting data permanently, but it doesn't make the backfill any faster; a league with years of history still needing every one of them, or a run that's genuinely rate-limited, still crawls at 24 MFL requests per *sync's* worth of backfill. `scripts/backfill-history.mjs` calls the exact same `backfillLeagueHistory` (exported from `fetch-rosters.mjs` for this reason, rather than duplicated) with a cookie of its own and nothing else competing for MFL's rate limit, so its 24/8 request budgets are effectively uncontested. It deliberately does not re-derive anything from `config/leagues.json` or re-resolve any league's season: `data/rosters.json`'s own `leagues[]` already carries id/name/type/provider/franchiseId/season for every league, and reading the file directly is what lets this touch only `results`/`historyBoundaryYear` per league rather than reproducing the whole roster-fetch pipeline. The one consequence: it trusts whatever season is already on record, so a league that rolled over since the last regular sync won't have its just-finished season backfilled here — a bounded gap the next regular sync closes on its own. Workflow-dispatch-only like the probe workflows above, but for a different reason — this doesn't ask about an API unreachable from a sandbox, it exists because the regular sync's own rate-limit contention is the bottleneck, not the code. `sync-mfl-rosters.yml` and `backfill-history.yml` share one GitHub Actions concurrency group (`rosters-data-write`) because both commit to `data/rosters.json` — queuing them, rather than letting a scheduled sync and a manual backfill run land at the same time, is what keeps one commit from clobbering the other.
- **A single MFL league can starve every other league's turn in a backfill run, and this is a second, distinct problem from the rate-limit one two bullets up.** `backfillLeagueHistory` iterates leagues in `config/leagues.json` order and, per league, works through *all* of that league's missing years before moving to the next. Once the retry-eligibility fix (above) made every `guessed: true` year retryable, the queue of "missing" years got much longer — and a league sitting early in that order with a long tail of guessed years can legitimately spend the entire run's budget on itself, every run, before any league behind it gets a single request. Confirmed live on the very first `backfill-history.yml` dispatch: the first MFL league in the file had over a dozen guessed/missing years, consumed the whole 24-request budget correcting four of them, and the other fourteen leagues — including the one the run was meant to fix — got zero requests. `HISTORY_MFL_PER_LEAGUE_BUDGET` (8) caps how much of a run's budget any one league can spend, enforced alongside the run-wide `HISTORY_MFL_REQUEST_BUDGET` rather than instead of it, so a bad-luck league further down the list is guaranteed at least a few other leagues' worth of headroom rather than none. It does not fix that first league's *own* backfill speed — it still needs as many runs as it always would to fully clear its own tail — it only stops that tail from crowding out everyone behind it. This is a mitigation, not a guarantee: several leagues each sitting near the per-league cap can still fill the whole run-wide budget before reaching a league further back, which is exactly why `backfill-history.mjs` also accepts `LEAGUE_ID` (comma-separated, wired to `backfill-history.yml`'s `league_id` dispatch input) — naming a league id skips the queue entirely and hands that league the whole run's budget, which is the direct answer to "backfill this league now" rather than waiting for a fair-but-not-immediate turn.
- **The per-league cap does not apply when `LEAGUE_ID` targets exactly one league — and this isn't optional, it's required for `LEAGUE_ID` to mean anything.** `HISTORY_MFL_PER_LEAGUE_BUDGET` exists to protect *other* leagues from one league's turn; with only one league in `leagues`, there is no other league to protect, so `backfillLeagueHistory` gives that league the full `HISTORY_MFL_REQUEST_BUDGET` instead (`perLeagueMflBudget = leagues.length === 1 ? HISTORY_MFL_REQUEST_BUDGET : HISTORY_MFL_PER_LEAGUE_BUDGET`). This surfaced live, fixing Iron Bank's history: 2022 turned out to be a genuinely unresolvable bracket gap (two-plus leftover teams with no consolation game to place them — see `computeMflSeasonPlacements`), which by design never confirms and so is retried every single run, sitting at the front of that league's queue forever. Capped at 8, a `LEAGUE_ID`-targeted run for Iron Bank kept re-spending most of its budget reconfirming the same unresolvable 2022 guess and never got far enough to reach 2020, sitting right behind it. There was nothing wrong with the retry logic — 2022 is correctly not confirmable — the cap was just fighting the one thing `LEAGUE_ID` exists to do.
- **`draftonly` leagues run no playoff bracket at all, so `computeMflSeasonPlacements` has nothing to walk for them — confirmed live and directly by the user** after every `draftonly` league backfilled under the bracket path came back as an unbroken string of `guessed: true` years (its own honest gap-filling fallback, correctly triggered every time by a genuinely empty bracket listing). These leagues decide placement by total points scored through week 17 instead — the same cutoff and reasoning as the season-total high-score award (`SEASON_HIGH_SCORE_WEEKS`, see the weekly/season high-score bullet below) — so `backfillLeagueHistory`'s per-year loop branches on `league.type === 'draftonly'` and calls `computeMflSeasonPlacementsByPoints` (`scripts/lib/history.mjs`) instead: every franchise ranked by its own summed points, highest first, over `weeklyScoresByWeek` fetched the same way `backfillLeagueScoringRecords` already fetches it for the scoring pass — `fetchMflSeasonMeta` once for that year's `endWeek`/franchise-id list (`nameById`'s keys fill the role `leagueStandings` plays for the bracket path, at no extra request, since `fetchMflSeasonMeta` already fetches `TYPE=league` for exactly this), then `fetchMflWeekScores` once per week through `min(17, endWeek)`. **Unlike the bracket path, this is never a guess** — `guessed` is hardcoded false, since every rank is a hard sum over real fetched data rather than a regular-season-order fallback — so a `draftonly` league's existing `guessed: true` years (retry-eligible per `yearsNeedingHistoryBackfill`) self-correct into confirmed ones the next time the backfill reaches them, with no separate migration needed. All-or-nothing per year, same discipline `backfillLeagueScoringRecords` already applies to this identical per-week fetch: any single week's fetch failing (a 429, most likely) discards the whole year rather than computing a placement from a partial set of weeks, which would misrank whoever it happened to miss. The cost is what forced a new budget constant: a single year can take up to 18 requests (1 + 17) against `HISTORY_MFL_PER_LEAGUE_BUDGET`'s 8, which could never complete even one year — `HISTORY_MFL_DRAFTONLY_PER_LEAGUE_BUDGET` (20) is used instead for these leagues specifically (via `Math.max`, so it only ever raises the cap, never shrinks the existing single-league-targeted case back down from 24). Pinned in `scripts/test-history.mjs`.
- **The Results card's average is the mean of `rank`, never the raw fraction** (`leagueResultsSummary` in `myffl.html`) — a 12-team league's numbers must not be able to swamp a 10-team league's within the same average just because the denominators differ. Rows render most-recent-first, matching how a manager actually thinks about "how have I done" (last year first, not first year first). Leagues sort by best (lowest) average finish, the same convention every other ranked card on this page uses; a league with a backfilled year but no *resolvable* rank on any of them (still possible in principle, though not in practice once every placement is either a real bracket result or a hard points sum — see the two bullets above and below) sorts last and still gets a row, since it has real years to show, just no average to summarize them with. A league with zero backfilled years is a different case entirely and doesn't reach this card at all — see the History tab's own bullet above.
- **Weekly/season high-score payouts are a second, independent axis from Finish, and their backfill deliberately never runs inside the regular sync.** Several leagues here pay for the highest-scoring week and the highest total points across weeks 1-17, regardless of final placement, so a last-place team can still have banked a weekly win. These are two DIFFERENT KINDS of award, not two versions of the same one — **this shipped wrong once already**: an earlier version treated "weekly high" as a single once-a-season record (one winner, one week, computed as a season-wide max), on the same shape as "season high." The user corrected this directly: the weekly-high prize is awarded fresh EVERY week — week 1's top scorer wins it, week 2's top scorer wins it again independently, and so on through week 18 — so a single season pays it out up to 18 times, and the same franchise can win it several times over. `results[].scoring` therefore holds `{ weeklyHighs, seasonHigh }`: `weeklyHighs` is an array, one entry per week fetched (`{franchiseId, teamName, week, points}`), while `seasonHigh` stays a single record (`{franchiseId, teamName, points}`) since that award really is once-a-season. `payoutWeeklyHigh`/`payoutSeasonHigh` in `config/leagues.json` are a second pair of dollar amounts alongside payout1/2/3, same $0-when-unset convention, editable from the Admin tab; `leagueFinancesSummary` in `myffl.html` adds them into a year's Won whenever `league.franchiseId` matches, on top of (never instead of) the placement payout — but for weekly-high, "matches" means counting every entry in `weeklyHighs` with this franchise's id and summing `payoutWeeklyHigh` once per entry, not a flat one-or-nothing amount. The Won cell itself renders only the total: `leagueFinancesSummary` returns `breakdown`, a `{label, amount}` line item per contributing reason (place, then one row per weekly-high week won, then season high) rather than the flat `labels` string array this shipped with first — spelling every reason inline (`$525 (1st, Weekly High (Wk 3, Wk 9, Wk 12))`) got long fast once a franchise could rack up several weekly-highs in one season, which the real MNMx 2025 data did immediately (seven wins). The amount is a `.finances-link` button — same idiom `.salary-link`'s "Salary by Year" popover uses on the Rosters tab — that reveals `breakdown` in a popover (`openFinancesPopover`/`toggleFinancesPopover`, its own separate instance rather than sharing code with the salary/needs popovers, matching this page's standing rule for those: unrelated content from unrelated tables). A year with nothing to explain (won $0, or a rank outside the top 3 with no payout field) stays plain text — only a real breakdown earns the button. Both halves are computed by `computeSeasonScoringRecords` in `scripts/lib/history.mjs` — a hard max/sum over a season's fetched weeks, never a guess the way a gap in the placement bracket walk can be, so there's no retry-eligibility concept here: once a year has `scoring`, it's simply done (`yearsNeedingScoringBackfill`). Each week's per-franchise total is summed from that franchise's own starting lineup (`player.status === 'starter'` on MFL's `TYPE=weeklyResults`) rather than trusted off a franchise-level convenience field, since a team's score for a week IS the sum of its starters' scores by definition — correct regardless of whichever other total field the response may or may not also carry. `probe-weekly-scores.yml` confirmed this against real data (league 26696, 2025): every franchise's own `score` field on that endpoint matched the summed-starters total exactly, every matchup, every week — so the two are provably interchangeable and this reads correctly regardless of which one a caller trusts — but that probe only ever checked weeks 1..lastRegularSeasonWeek, and a second round caught a real bug living in exactly the weeks it never looked at. **A franchise with no active head-to-head game in a given week — a bye, an eliminated team, anything past its own bracket's final — does not appear inside `weeklyResults.matchup` at all.** MFL instead reports it as a flat entry directly under `weeklyResults.franchise`, sibling to `matchup` rather than nested in it, still carrying a completely real score (the lineup still counts even with nobody to play). `fetchMflWeekScores` originally only ever read `matchup`, so that franchise's week vanished from `computeSeasonScoringRecords` silently — confirmed live on MNMx's 2021 week 15, where six of ten franchises were flat entries and one of them (142.5) was the actual weekly high, quietly replaced by a matchup entry at 90.3. `parseMflWeekScores` now reads both shapes and merges them (pinned with this exact fixture in `scripts/test-weekly-scores.mjs`), and the probe's own missing-franchise check is kept as a standing regression guard — a week that comes up short again after this fix is worth a third look, not assumed away. The same probe is also why the fetch window is a fixed **weeks 1-18**, not `lastRegularSeasonWeek` (the field the placement backfill uses): `leagueStandings.pf` was seriously considered as a free shortcut for the season-total number, since it's already fetched during placement backfill, but the probe showed `pf` running well above even the weeks-1-14 regular-season sum for every franchise (one franchise: 1960.10 summed vs. 2424.00 on `pf`) — MFL folds playoff-week scoring into `pf` with no fixed cutoff this feature could rely on, and several real leagues here run their bracket through week 17 or later, so a payout scoped to `lastRegularSeasonWeek` would silently exclude the playoff weeks those leagues' payouts are meant to cover. `WEEKLY_HIGH_SCORE_WEEKS` (18) in `fetch-rosters.mjs` is therefore hardcoded rather than read off any per-league field, capped only by that season's own `endWeek` for the rare season that never reached 18. Within that fetched range the two halves diverge, though: a weekly-high award can be won on any week including 18, but a season-total award only ever sums weeks 1-`SEASON_HIGH_SCORE_WEEKS` (17) — `computeSeasonScoringRecords` takes that cutoff as its own third argument and filters the season sum by it while still scanning every fetched week for the weekly max, rather than the caller fetching two different ranges (which would double-request every week 1-17 has in common with both halves). This isn't a guess at NFL scheduling convention (an earlier version of this comment reasoned that week 18 is "generally unplayed" once teams rest starters, and excluded it from both halves on that basis) — it's a direct instruction from the user that weekly-high awards in these leagues are explicitly paid through week 18 while season-total awards are not, so the two cutoffs are asserted, not inferred. **Gated on a season already having a `results[]` entry** (guessed or confirmed — a guess still means the season genuinely happened and ended, which is all this needs) so it can never run against a season still in progress, which would compute a "final" total that keeps changing week to week. **Deliberately its own backfill pass, `backfillLeagueScoringRecords`, dispatched only via `scripts/backfill-scoring.mjs`/`backfill-scoring.yml` — never wired into the regular 4-hourly sync the way `backfillLeagueHistory` is.** A season's placement costs roughly 2 + (a few brackets) MFL requests; a season's weekly totals cost one request PER week fetched, since there's no bulk endpoint — up to 18 requests for a typical season (the fixed weeks-1-18 fetch window above), which would risk the exact 429 cascade documented above if it ran automatically on top of a sync that already brushes MFL's rate limit. `SCORING_MFL_REQUEST_BUDGET`/`SCORING_MFL_PER_LEAGUE_BUDGET` size a run to roughly one or two league-seasons, same "many runs to fully backfill, zero cost once done" shape as the placement backfill. Every week in a season must succeed or none of it is recorded — a season half-summed from surviving weeks would silently understate both numbers, which is worse than retrying next run. One correctness fix this required in `backfillLeagueHistory` itself: when a retried `guessed: true` placement is reconfirmed, the replaced `results[]` entry now explicitly carries forward any `scoring` that year already had — without it, a year whose scoring was backfilled first and whose placement guess got reconfirmed in the same run would silently lose that scoring data again. MFL only; ESPN/Sleeper are out of scope, same as the placement backfill, and it happens every league in this config that pays for a high score is MFL anyway.
- **`startYear` is a manager-declared floor on how far back a league's history is actually theirs, not the sync's or the provider's answer to give.** A league's `results[]` is keyed to `league.franchiseId` for every backfilled year, but that franchise slot routinely predates the current manager — MFL/ESPN don't reassign a new id when a franchise changes hands, they just keep scoring under the same one — so a year before the manager actually joined shows somebody else's roster, somebody else's finish, somebody else's high-score win, under this manager's own name. Unlike almost everything else the sync degrades gracefully around, this isn't a gap to fill in or a guess to flag: it's a real, correctly-computed answer about the wrong person, which makes it worse than missing data rather than merely incomplete. Set from the Admin tab (`field('Start Year', ...)` in `myffl.html`, right below Season since it's a companion concept — a manual pin, not something the sync ever resolves on its own) and validated server-side in `api/save-leagues.js` with the same four-digit-year range check `season` already gets, since a bad value here fails exactly as silently: it just quietly hides or shows years nobody asked about. Applied in two places, both load-bearing: `isBeforeStartYear` in `myffl.html`, shared by `leagueResultsSummary` and `leagueFinancesSummary`, filters `results[]` before either card's rows/average/Total are computed — the authoritative gate, since it works even against data backfilled before `startYear` was ever set; and `yearsNeedingHistoryBackfill`/`yearsNeedingScoringBackfill` in `fetch-rosters.mjs` (both take it as an optional trailing argument, undefined by default so every existing call site keeps backfilling a league's whole known history unchanged) skip fetching a year before it in the first place, which is a budget optimization rather than a correctness requirement — MFL/ESPN requests are the scarce resource this whole History feature economizes around everywhere else, and a year nobody can ever see on the page is the cheapest kind to simply never ask for. The ESPN walk-back's own `floor` (`backfillLeagueHistory`) takes the max of the lookback cap and `startYear`, so the two floors compose rather than one silently overriding the other. Blank (the default, and every league before this field existed) excludes nothing, at either layer.
- **Auth is stateless and password-free after login.** `SITE_PASSWORD` gates `api/login.js`, which returns an HMAC-signed 30-day token (`api/lib/auth.mjs`) that the client replays as a Bearer token on writes. There is no session store — the token carries its own expiry and signature. MFL credentials live only on the server and are never sent to the browser.
- **Planning values sync through `api/plans.js`; everything else the page stores is device-local.** Planned contract lengths, salaries, and (for Dynasty leagues) cuts used to live only in `localStorage`, which is per browser per device — an iPad and a phone kept separate copies and neither knew about the other, which reads as data loss even though nothing is lost. They now round-trip through an Upstash Redis store connected to the Vercel project (Storage → Marketplace → Upstash → Redis; Vercel's own first-party "KV" product is retired and no longer appears in that dialog), spoken to over its REST API with plain `fetch` so the no-dependency property holds. It has to be Upstash rather than the marketplace's "Redis" entry, which hands back a `redis://` connection string that would require a client library. `resolveStore` accepts the credentials under either `KV_REST_API_URL`/`KV_REST_API_TOKEN` or `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN`, since the integration has injected both over time. This is the project's only persistent per-user state; `myfflView`/`myfflLeagueType` and the auth token are still deliberately device-local. `cutPlans` is the third and newest kind — a two-option dropdown (`—`/`CUT`) rather than a checkbox, deliberately: the lineup editor's pilot leagues already spend a checkbox column on who's starting, which Submit Lineup reads straight off, and a second checkbox column right next to it doing nothing of the sort is exactly the pair a quick glance can mix up, with a mis-click on the wrong one being a real MFL write. Marked rows are styled in IR red rather than the purple Yrs/Sal turn once planned, since a cut is a player leaving the roster, not a value going official. Gated to Dynasty leagues and to `duringWeeks1Through17` (`showCutPlanning` in `renderCard`) — its own boundary, deliberately narrower than the `nflInSeason` boolean the Admin tab's rankings note reuses: that one runs through the Super Bowl for the FantasyPros ranking-set flip, which has nothing to do with when a cutdown makes sense, so cut planning stays open through the NFL playoffs on the strength of the user's own stated boundary, the last game of Week 17. Getting Week 17's end date right takes more than nflInSeason's single-year trick: it lands 116 days after kickoff, and kickoff itself moves across a 7-day range depending on where Labor Day falls, so the landing date crosses the new year in some seasons and not others — pinned by `scripts/test-cut-planning-window.mjs`, which is also where that boundary math is spelled out in full. The target moves once more inside that window: from Week 17's end through the Super Bowl (`duringIrClearingWindow` — the same two-calendar-year kickoff walk as `duringWeeks1Through17`, but closing at the following February's Super Bowl rather than staying open all the way to next kickoff), `cutsNeededFor` counts `INJURED_RESERVE` players against `cutdownRosterSize` alongside `ROSTER` ones, and the Cut dropdown itself extends onto the Injured Reserve table to match (`showCutColumn` in `renderCard`) — a target with no row anywhere to mark against it would be worse than the plain ROSTER-only count it replaces. This is the one stretch of the offseason where the ROSTER-only count reads clean when it isn't: the rookie draft that actually balloons a roster is still weeks off, so a franchise already sitting at exactly `cutdownRosterSize` on the active roster with two players parked on IR shows 0 cuts needed under the plain count, when both IR spots still have to be resolved by cutting before Week 1 — there's no such thing as a planned "activation" with nowhere on the roster for the activated player to land. Past the Super Bowl the window closes and the count reverts to ROSTER alone: the rookie draft is close enough by then that ROSTER-only cuts are expected regardless, and nothing left distinguishes "already cleared IR" from "hasn't drafted yet." `cutCountableStatuses`/`cutsNeededFor`/`cutsPlannedFor` are pulled out of `renderCard`'s own closures for exactly this reason — so the counting rule is pinned directly, alongside the boundary itself, in `scripts/test-cut-planning-window.mjs`, rather than only reachable through the DOM. This is gated opposite Salary Cap's contract/salary planning (`isAuction`), which never expires. Its card-level banner mirrors the contract banner's shape — a target and a count, gold until met — but the target is deliberately **not** `league.rosterLimits.size`, the field `rosterLimitProblems` reads off MFL's `TYPE=league`: a Dynasty commissioner routinely raises that limit for the offseason specifically so a roster swollen with rookie picks doesn't get flagged on MFL's own site, so it describes what MFL will currently tolerate, not what the league's rules actually require once the season starts. That real number lives nowhere any provider exposes it, so it's `config/leagues.json`'s `cutdownRosterSize` — a manual per-league override, set by hand from each league's own rules document (MNMx and OSD have no shared one at all; Survivors' is private) and expected to stay static for years at a time, changing only on a league vote. Without it the dropdown still renders — still useful for pre-marking candidates — but the banner has no target to count against and stays hidden. There is no commissioner to email: cutting a player is something a manager executes themselves on MFL, not something recorded elsewhere. Three properties are load-bearing and pinned by `scripts/test-plans.mjs`: `localStorage` stays the working copy and the page renders and accepts edits with the store unreachable, exactly as before it existed; a first load posts in **merge** mode, because a device that has never synced posts an empty document and a replace would wipe the other device's plans — the precise failure this exists to fix; and every change after that first successful merge posts in **replace** mode, which is what lets a cleared plan actually go away rather than being unioned straight back. **A merge is a union, so it cannot express a deletion**, and that is the axis the whole design turns on. The page therefore merges exactly once per device — the introduction for a device the store has never heard from, where taking the store wholesale would lose local plans and replacing it would lose the other device's — and reads with a plain **GET** every load after, recording that it has synced in `myfflPlanSynced` so the answer survives a reload. Merging on *every* load is what made a cleared plan impossible to propagate: a plan cleared on the iPad is *absent* from the store, so the phone's next load unioned its own stale copy back in and re-uploaded it, undoing the clear for every device at once — and the device that made the clear looked correct the whole time, which is why a single-device test cannot see it. `localStorage` is now the store's cache plus `myfflPlanPending`, a persisted log of edits not yet confirmed upstream, where `''` is a tombstone; it is laid back over every answer the store gives (so an edit made offline, or while the read was in flight, is not overwritten) and cleared only by a push that confirms it. `planSyncDone` is read back off that flag at load, so a returning device pushes in **replace** mode from its very first edit rather than re-entering merge mode until its sync lands, and `planPushGeneration` discards a read whose answer predates a push that has since landed. `doLogout` drops the pending log but deliberately keeps `myfflPlanSynced` — the store has met this device, and that is what sends the next login to a read rather than back to a merge. One consequence worth knowing: each device performs its one-time merge on its first load after this shipped, which can resurrect a deletion made before that load, so a clear made while another device had not yet been reloaded needs making once more. `scripts/test-plan-sync.mjs` pins all of this by evaluating `myffl.html`'s own script block in a `vm` with the browser stubbed and `fetch` as the seam, driving two page instances against one store running `api/plans.js`'s real `mergePlans` — the two-device cases are the only ones that can see this class of bug. The plans are **not** kept in the repo the way `config/leagues.json` is: this repository is public, and a plan is strategy — the same reason the page withholds plans from logged-out viewers.

## Verifying changes

Network egress from a cloud sandbox is restricted: **`myfantasyleague.com` and `api.sleeper.app` are unreachable here, though `api.github.com` is.** You therefore cannot run `node scripts/fetch-rosters.mjs` end-to-end locally, which is exactly why the manual workflows exist. Verify against real providers by dispatching `test-set-lineup.yml` or `test-login-endpoint.yml` from GitHub Actions, or by triggering `sync-mfl-rosters.yml`.

What *does* work locally:

```bash
node --check scripts/fetch-rosters.mjs        # syntax
python3 -m http.server 8000                   # then open /myffl.html
```

Serve over HTTP rather than opening the file directly — `myffl.html` fetches `data/rosters.json` with a relative URL, which fails under `file://`. The committed `data/rosters.json` is real synced data, so the page renders fully offline; pure rendering changes can be checked this way without any provider access.

To exercise the logged-in UI (the lineup editors and the whole Admin tab) without the site password or any network access, set the token the page looks for before loading it — `isLoggedIn()` only checks that one exists:

```js
localStorage.setItem('mflAuthToken', 'anything');
```

Everything renders and behaves normally; only the calls that actually reach Vercel will fail. This is the practical way to drive the Admin tab in a headless browser.

## Front-end conventions

`myffl.html` is a single ~2000-line file: vanilla JS, no framework, no bundler, styles and markup and logic all inline. Rendering is a set of `renderCard` / `renderStandingsCard` / `renderScoringCard` / `renderAnalyticsCard` / `renderInjuryExposureCard` / `renderTopAvailableCard` functions driven by a tab and sub-tab system built from the league list at runtime. All three Analytics cards share `appendAnalyticsTable` — one paginated table behind a handful of flags rather than three copies free to drift, which is also why click-to-sort on every column but the player's name was one implementation and not three. **The card's own order is a fourth sort state, not something the first click destroys**: each header cycles natural direction → reverse → back to default, because those defaults are the considered view (Injury Exposure's encodes the live/settled split) and a two-state toggle would strand a reader in a sort with no way back short of reloading. Three properties there are pinned by `scripts/test-analytics-sort.mjs`, which drives a DOM stub since the sort state lives in the rendered table's closure rather than in a pure function: ties fall back to the card's own order, so sorting by Pos doesn't scramble the exposure ordering *within* a position; an unranked player stays at the bottom in **both** directions, since the obvious `rankOrLast` treatment reads correctly ascending and then hands him the top row on the reverse click, and no ECR means the rankings didn't have him rather than that he is the worst player alive; and only columns actually on screen are sortable, so a logged-out visitor has no ECR header to click and Top Available has no Pct one. The n/total counts sort too, which is redundant on the exposure cards — exposure is count/total against a denominator fixed for the whole card, so Pct and the count are the same ordering — and is the *only* way to sort Top Available by reach, since that card has no Pct column. Its two counts are also the one place the numbers genuinely differ, and sorting by **Own In** there is what surfaces a player you already hold in several leagues and could still claim in others. Sorting is per card and per visit — deliberately not persisted, since a sort set last Tuesday silently overriding the default order is worse than clicking again — and the two exposure cards additionally share `exposureLeagues`, so both percentages have the same denominator. They do **not** share a page size, and that difference is load-bearing: Player Exposure pages eight (`PLAYER_EXPOSURE_PAGE_SIZE`) where Injury Exposure pages six (`ANALYTICS_PAGE_SIZE`), because an injury row is three lines deep — name, the injury under it, then the leagues — against the player card's two, so six of the taller rows stand about as tall as eight of the shorter ones and the two cards come out level side by side on desktop rather than one trailing a third of a table below the other. **The two numbers are a pair**: anything that changes how many lines a row of either card takes — dropping the injury detail line, adding a sub-line to the player card — has to move both, or the alignment quietly goes away. They do **not** share a sort either, and that is deliberate rather than drift: Player Exposure leads on exposure because "where am I concentrated" is a portfolio question, while Injury Exposure leads on **`INJURY_SETTLED` — whether the designation is still a question — and only then on `INJURY_SEVERITY`**. It used to lead on severity alone, on the reasoning that the card is triage and an IR outranks a Questionable however many leagues the Q spans. That has a hole in it: **an IR is triage once.** The week it lands you drop somebody; every week after, it is a fact about a roster slot you already settled, still holding the top row. In August the Dynasty card opened with a one-league IR on an ECR-287 player and a holdout — two of six first-page rows spoken for before a game was played, and it would have been the same two in February. A sort nothing can displace has stopped sorting. So `IR`/`PUP`/`NFI`/`SUSP`/`HOL`/`RET` are demoted below everything still developing, and **demoted rather than dropped**, because a *newly* placed IR is real news and a card that hid them would never show it. Within each half the old order is untouched (severity, exposure, then the better player), which means the old design's flaw survives in miniature at the bottom: a one-league IR still tops a five-league suspension, which was wrong at the top of the card and is harmless there. An unrecognised code is absent from `INJURY_SETTLED` on purpose, landing it at the foot of the *live* half — it neither leads the card nor gets filed as season-ending on the strength of a string nobody has read. `INJURY_SEVERITY` is emphatically **not** re-ranked to achieve any of this, because it still has to mean severity for its other job: picking which designation a player shows when two providers disagree, where a real IR must still beat a Questionable. Two questions, two lists — editing either moves rows, and editing severity also changes labels; `HOL` (a holdout, ranked above `O` and below `SUSP`) is the one entry in it that isn't an injury, arriving from MFL as an unmapped passthrough rather than through `INJURY_STATUS_MAP`, and an unrecognised code ranks `-1` on purpose so it can neither mask a real IR nor lead the card. That last rule is a backstop, not a plan: `IR-PUP` and `IR-NFI` used to reach it by accident, because `normalizeInjuryStatus` turns the hyphen into a space and the length fallback then sliced `IR PUP` down to `"IR "` — a trailing-space string that rendered as a convincing `IR`, ranked `-1`, and so sorted a season-long reserve designation *below* a Questionable and lost every provider disagreement to one. `PUP` and `NFI` were already in `INJURY_SEVERITY` waiting for them. `RETIRED` maps to `RET` and is deliberately left out of that list — a retired player is a roster problem but not a triage one, and ranking him above `IR` would put him at the top of a card whose first row should be the thing you can still act on. **Under the name, not in a column, sits the injury itself** — body part and expected return, from MFL's `details`/`exp_return`, both of which `probe-injury-detail.yml` found filled on 325 of 325 rows. It is a sub-line for the same reason the NFL team is a suffix: the shared table already carries six columns and a seventh of variable-length prose is the first thing to break on a phone. Three judgement calls there, pinned by `scripts/test-injury-detail.mjs` and `scripts/test-injury-exposure.mjs`: `Undisclosed` is dropped at sync time rather than printed, since it is the feed saying it doesn't know and a line that says nothing still costs a line; `exp_return` crosses the sync as MFL's own string rather than a parsed date, because the page is the side that decides whether to show it; and it is shown only inside `INJURY_RETURN_HORIZON_DAYS` (45), because MFL fills that field on *every* row and the far dates are a season-end sentinel for retired and season-ending cases — 17 distinct dates covered all 325 rows — so "back Feb 15" in August claims a precision the feed hasn't got. Sleeper is not consulted for any of this: its `injury_body_part` duplicates MFL's `details` at a lower fill rate (87% vs 100%), and the fields that would have made a genuine *news* line possible — `practice_participation`, `practice_description`, `injury_start_date` — came back empty on all 586 of its injured players. There is no beat-writer text in either feed, which is why the card says what the injury is and never claims to be an update. MFL leagues get the detail by player id in `fetchLeagueRoster`; every ESPN and Sleeper roster reaches the same global report **by name**, through `attachInjuryDetail` in `fetch-rosters.mjs` — a free in-memory pass, since both the report and the id-to-name map were already fetched. It lives there and not in `providers.mjs` for a concrete reason: the join needs `normalizePlayerName` from `fantasypros.mjs`, `api/` imports `providers.mjs`, and `vercel.json`'s `ignoreCommand` doesn't list `fantasypros.mjs` — so that import would silently skip Vercel deploys that need to ship. Two properties there are load-bearing: it only ever *fills in* a detail and never replaces the exact by-id one (a name is the weaker key, and two players sharing one collide exactly as they would in a FantasyPros slug), and it attaches nothing to a player carrying no designation, since the detail annotates a designation rather than standing in for one — a stale MFL row must not put somebody on the card that his own league's provider calls healthy. Every table that names a player — rosters, the lineup editor, all three Analytics cards — appends the NFL team through `appendTeamSuffix` rather than spending a column on it, so a name reads the same wherever it appears; on the exposure cards it comes off the rostered player (so the provider's own spelling shows, `LVR` from MFL beside `LV` from Sleeper, exactly as on the Rosters tab) and on Top Available off the ranking pool, which is the only source for a player nobody holds. `scripts/test-injury-exposure.mjs` and `scripts/test-top-available.mjs` pin their cards' judgement calls by running the page's own script block in a `vm`; note that these cards' mistakes are all silent ones, so nothing on screen tells you a denominator is off. Sub-tabs come from one grouping, `SUBTAB_GROUP`, in every view: dynasty and salary-cap share a sub-tab, redraft and draft-only each get their own. Analytics briefly had a second grouping (`ANALYTICS_GROUP`) that folded redraft in with dynasty and salary-cap as a single "Active" tab, on the grounds that exposure is a portfolio question and a redraft roster is as much a share of the portfolio as a dynasty one. **Don't reintroduce it.** That reasoning holds for the two exposure cards and breaks for Top Available, which is *ordered by consensus rank*: a group spanning dynasty and redraft leagues spans two FantasyPros lists that disagree by a hundred places about the same player — one is a bet on five years, the other on five months — and the median across them describes neither. Because that median weights by league count, the merged tab also meant a portfolio holding more redraft leagues silently ranked its dynasty leagues' wire on redraft logic. Some spread survives inside Dynasty/Salary Cap, since cap leagues deliberately read DRAFT rankings (see `automaticRankingType`), but those two lists at least share a horizon. The sub-tab strip is derived at render time from the `data-league-type` of the cards actually in the current view, so a group with no leagues simply doesn't get a tab. Match the existing idiom rather than introducing a framework or a build step — the no-toolchain property is what lets GitHub Pages serve this directly.
